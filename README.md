# TileMatcher

## 项目目标

本项目使用 Godot 4.6.1 Mono 版本复刻一款参考 Vita Mahjong 的手机端麻将配对消除游戏。

第一版目标不考虑正式美术资源，优先使用占位图形与基础 UI，在最短时间内打通单关卡完整流程：

- 首页
- 进入单关
- 游戏内拖拽配对消除
- 胜利/失败结算页
- 可在本地运行与调试

当前约束：

- 引擎路径：`D:\GodotCSharp\Godot_v4.6.1-stable_mono_win64\Godot_v4.6.1-stable_mono_win64.exe`
- 技术栈：Godot 4.6.1 Mono + C#
- 第一版不追求美术还原
- 第一版不做多关卡生成器
- 第一版只做一个可玩、可验证的关卡闭环

## 参考目标

参考 Vita Mahjong 的核心体验，但第一版只保留最重要的玩法骨架：

- 多层麻将堆叠
- 麻将错位排列
- 玩家可拖拽自由麻将
- 与同类自由麻将接触后配对消除
- 消除后重新计算剩余麻将的可移动状态
- 全部消除则胜利
- 无可用匹配或无可移动麻将时可判定失败

第一版不处理的内容：

- 正式和风美术
- 完整 20 关
- 高级动画特效
- 商业化系统
- 复杂新手引导

## 第一版交付范围

### 页面流程

第一版只实现以下三个页面：

1. 首页
2. 游戏页
3. 结果页

### 首页

首页职责：

- 显示游戏标题
- 显示“开始游戏”按钮
- 点击后进入固定单关

首页为占位 UI，不做正式视觉还原。

### 游戏页

游戏页职责：

- 加载一个固定关卡
- 渲染多层麻将堆叠
- 支持鼠标和触摸拖拽
- 支持相同麻将吸附配对消除
- 显示基础 HUD
- 根据结果跳转到结算页

基础 HUD 仅保留：

- 当前关卡编号
- 当前分数
- 当前已完成匹配数
- 返回首页或重开按钮

### 结果页

结果页职责：

- 显示胜利或失败
- 显示基础统计
- 支持重新开始当前关卡
- 支持返回首页

## 核心玩法定义

### 1. 麻将数据

每张麻将至少包含以下逻辑字段：

- `Id`：唯一标识
- `Type`：牌面类型
- `GX`：逻辑横坐标
- `GY`：逻辑纵坐标
- `GZ`：逻辑层级
- `Removed`：是否已被消除
- `Movable`：当前是否可移动

第一版不直接用像素坐标做逻辑判定，而是使用逻辑网格坐标。

### 2. 关卡布局

第一版只做一个固定关卡，采用预定义布局。

布局要求：

- 至少 3 层堆叠
- 同层麻将有错位
- 存在一部分被压住的麻将
- 存在一部分侧向卡住的麻将
- 关卡可解

### 3. 可移动判定

第一版采用简化且稳定的规则，先保证手感清晰、可实现。

一张麻将不可移动的条件：

- 上层存在与其重叠的麻将
- 同层左右两侧都被相邻麻将阻挡
- 同层上下两侧都被相邻麻将阻挡

否则视为可移动。

说明：

- 第一版允许后续根据试玩继续调整“卡住”规则
- 目标是先得到一个稳定、可解释的版本，而不是第一天就完全逆向原作全部细节

### 4. 匹配消除

第一版采用“拖拽接近吸附”而非真实物理碰撞。

规则如下：

- 玩家只能拖动 `Movable = true` 的麻将
- 只有 `Movable = true` 的麻将可以作为匹配目标
- 若拖拽中的麻将接近另一张同类型且可匹配的麻将，则触发吸附
- 吸附成功后，两张麻将同时消除
- 消除后重新计算所有剩余麻将的 `Movable` 状态

### 5. 胜负条件

胜利条件：

- 牌桌上的所有麻将被消除

失败条件，第一版可先采用以下任一方案：

- 牌桌上不存在任何可匹配组合
- 或者暂时不判失败，只支持重开

建议第一版先实现胜利流程，失败判定作为次优先级。

## 技术方案

## 场景划分

建议使用以下场景结构：

- `Main.tscn`：场景切换入口
- `scenes/home/HomeScene.tscn`
- `scenes/game/GameScene.tscn`
- `scenes/result/ResultScene.tscn`
- `scenes/tile/Tile.tscn`

## 脚本职责

建议使用以下核心脚本：

- `Main.cs`
  - 管理首页、游戏页、结果页切换

- `GameScene.cs`
  - 管理单局游戏流程
  - 初始化关卡
  - 接收胜负结果

- `BoardController.cs`
  - 管理麻将实例
  - 负责布局生成
  - 负责重新计算可移动状态
  - 负责匹配判定

- `Tile.cs`
  - 管理单张麻将的显示、输入与拖拽状态

- `LevelData.cs`
  - 描述固定关卡数据

- `GameResult.cs`
  - 定义结算所需的数据结构

## 节点建议

页面建议采用以下分层：

- 页面 UI 使用 `Control`
- 牌桌区域使用 `Node2D`
- 单张麻将使用 `Node2D`

原因：

- 游戏页中的麻将更适合用 2D 世界坐标控制层级、阴影、拖拽与动画
- HUD 和按钮更适合用 UI 容器布局

## 数据表示建议

为了支持错位与多层重叠，建议使用逻辑网格单位而不是直接摆像素。

推荐方案：

- 一张麻将占用 `2 x 2` 逻辑单位
- 同层麻将允许半格错位
- 渲染时由逻辑坐标换算为屏幕坐标

这样可以更容易处理：

- 上层压住下层
- 邻接阻挡
- 关卡配置
- 后续可解性检测

## 单关卡最小闭环

第一版验收标准如下。

### 功能验收

- 可以启动 Godot 项目
- 可以进入首页
- 可以从首页进入单关
- 单关能正确生成麻将堆叠
- 可以拖动自由麻将
- 可以和同类麻将触发匹配消除
- 可以在全部消除后进入胜利页
- 可以从结果页重开或返回首页

### 交互验收

- 鼠标可在编辑器中正常游玩
- 触摸输入逻辑兼容手机
- 拖拽无明显穿模或层级错误
- 匹配成功有明确视觉反馈

### 稳定性验收

- 单局流程可反复重开
- 不出现已消除麻将残留点击区域
- 不出现可移动状态未刷新的问题

## 风险与应对

### 风险 1：卡住规则不准确

风险：

- 原作的“卡住”判定可能比当前观察更复杂

应对：

- 第一版先采用简化规则
- 使用固定关卡验证手感
- 后续根据试玩录像调整

### 风险 2：拖拽体验不稳定

风险：

- 纯碰撞检测容易出现擦边误判

应对：

- 第一版采用接近吸附
- 使用阈值判定而非真实物理碰撞

### 风险 3：关卡无解

风险：

- 手工摆关卡可能导致无解

应对：

- 第一版只做一个人工验证过的固定关卡
- 暂不引入自动生成器
