# 配对牌局构造与评估系统设计

## 文档目标

本文档用于整合当前项目围绕“配对牌局构造与评估系统”的设计共识，明确后续自动化关卡内容生产的目标、边界、术语、离线流程和评估方向。

它不是最终定稿，也不是实现说明，而是一份当前阶段的主设计文档，用于指导后续边实现、边验证、边调整。

本文档重点回答以下问题：

- 我们到底要构造什么，而不只是“摆一桌牌”
- 什么叫可玩、可解、不会轻易卡死
- 难度为什么不能只靠单一分数衡量
- 为什么系统应当以离线预计算为主，而不是运行时即时生成
- 为什么需要一套面向策划和开发的 Web 分析台

## 当前结论

当前项目不再把相关能力称为“自动布局”，而正式称为：

**配对牌局构造与评估系统**

这样命名的原因是：

- “布局”只强调牌怎么摆
- “牌局”强调完整游玩过程
- “构造”强调这是一个受约束的生产过程
- “评估”强调生成结果必须经过分析、筛选和分档，而不是生成即通过

如果进一步强调使用方式，本系统也可以被理解为：

**离线配对牌局构造、评估与筛选流水线**

## 系统目标

本系统的目标不是简单生成一份看起来像堆叠配对牌的布局，而是离线构造一批候选牌局，对它们进行可解性和难度评估，再筛选出适合作为正式关卡的数据。

系统至少要满足以下目标：

1. 生成的牌局在几何上合法
2. 生成时就保证至少存在一种玩家操作顺序可以消除全部牌块
3. 尽量保证不止一条持续可推进路径，避免牌局退化成过度脆弱的唯一顺序题
4. 对候选牌局给出多维度难度指标，而不是单一“好/坏”判断
5. 支持在同一结构牌局上叠加不同难度变种，例如盖牌
6. 支持离线批量预计算，并把结果提供给策划和开发快速浏览与筛选

## 设计原则

### 1. 可解性优先于随机性

系统首先要保证牌局可通关，其次才谈结构变化和随机性。

如果一份牌局在视觉上很自然，但没有完整通关路径，它就不应进入候选集。

### 2. 评估优先于产出

不是“生成一局牌桌就结束”，而是“生成候选，再评估，再筛选，再产出正式关卡”。

### 3. 离线优先

当前关卡数据以离线构造为主，因此可以接受：

- 更重的搜索
- 更长的预计算时间
- 更多候选淘汰
- 更复杂的统计和筛选

这意味着系统不必过早为了运行时性能牺牲评估质量。

### 4. 结构难度与认知难度分离

同一份结构牌局，在规则不变的情况下，可能通过“牌面被盖住”这种信息层变化显著提升难度。

因此难度不能只看结构，还应区分：

- 结构难度
- 信息难度
- 规则修正难度

### 5. 先可分析，再可视化，再可调参

系统的第一价值是让牌局可分析，第二价值是让结果可被人快速理解，第三价值才是让参数逐步可配置。

## 系统范围

本系统当前覆盖以下内容：

- 候选结构牌局构造
- 牌面分配
- 可解性验证
- 解空间分析
- 多维度难度评估
- 候选牌局筛选
- 正式关卡数据产出
- Web 端分析结果展示

本系统当前不直接覆盖以下内容：

- 运行时在线即时生成
- 玩家端动态求解提示
- 最终商业化关卡投放策略
- 完整后台内容管理系统

## 与 Godot 运行时的解耦原则

当前正式采用以下原则：

- 离线侧工具链应尽量与 Godot 运行时解耦

这里的“解耦”不是说离线侧永远不能复用任何现有逻辑，而是指：

- 离线侧负责构造、求解、评估、筛选与导出
- Godot 侧负责按关卡编号读取约定位置的数据并在运行时加载

### 1. Godot 侧的职责

Godot 运行时当前应尽量只承担以下职责：

- 定义第几关使用哪一份关卡数据
- 定义关卡数据文件放在什么位置
- 按约定路径读取数据文件
- 把读取到的数据转换为当前牌桌运行时对象
- 驱动局内交互、视觉表现和页面流程

Godot 侧不应成为：

- 候选牌局批量生成器
- 大规模状态空间分析器
- 自动筛选主执行环境
- Web 分析台的直接后台

### 2. 离线侧的职责

离线侧工具链当前建议独立承担：

- 批量生成候选牌局
- 验证可解性
- 运行自动筛选
- 输出候选池与评估结果
- 导出正式关卡数据文件
- 为 Web 分析台提供预计算结果

这样做的好处是：

- 离线工具可以自由选择更适合批处理和数据分析的技术栈
- 不必被 Godot 场景树和运行时生命周期绑定
- 更容易做批量导出、批量评估和数据版本管理
- Web 分析台可以直接围绕导出的数据文件工作，而不是依赖 Godot 进程

### 3. 推荐的数据流向

当前推荐的数据流向是：

1. 离线侧构造候选牌局
2. 离线侧运行求解与评估
3. 离线侧自动筛选并产出正式关卡数据文件
4. 将正式关卡数据文件写入约定目录
5. Godot 侧只按关卡配置读取这些数据文件并加载

这意味着当前应把“离线生产”和“运行时消费”视为两个独立阶段，而不是把两者揉进同一个执行环境。

### 4. 对关卡配置的影响

在这个原则下，后续 Godot 侧的关卡配置更适合描述为：

- 当前关卡编号
- 当前关卡对应的数据文件路径
- 当前关卡使用的规则或表现变种

也就是说，Godot 侧的重点是：

- 这一关加载什么

而不是：

- 这一关在运行时怎么生成

### 5. 对 MVP 的影响

这条解耦原则会直接影响 MVP 的实现顺序。

当前 MVP 更合理的目标不是：

- 先在 Godot 内部把离线系统硬接进去

而是：

- 先把离线侧最小链路独立跑通
- 先能稳定导出正式关卡数据文件
- 再让 Godot 侧增加一层“按文件加载关卡”的消费能力

这样可以保证：

- 工具链边界清楚
- 运行时逻辑保持轻量
- 后续 Web 分析台和离线评估系统不被 Godot 运行时绑定

## 核心术语

### 1. 结构牌局

只描述牌块的空间结构和牌面分配结果，不包含额外的玩法修饰。

它至少包括：

- 每张牌块的位置
- 层级关系
- 牌面类型
- 初始可交互关系

### 2. 候选牌局

由系统离线生成的一份待评估牌局。

候选牌局不等于正式关卡。只有通过评估和筛选后，才可能进入正式关卡库。

### 3. 正式关卡

已经经过筛选、标注和确认，最终进入游戏资源的牌局数据。

### 4. 解路径

从初始状态出发，通过一系列合法消除操作，最终清空全部牌块的一条完整操作序列。

### 5. 解路径森林

把所有可能的玩家操作通关顺序按搜索展开后形成的树状集合。

它强调“顺序视角”，适合描述玩家操作分支。

### 6. 牌局状态图

如果把操作历史不同但剩余状态相同的节点合并，则解空间可视为一张有向无环图。

它强调“状态视角”，适合做统计、去重和评估。

### 7. 死局状态

当前状态还未清空全部牌块，但已经不存在任何合法推进操作。

### 8. 持续可推进路径

指从初始状态出发，在一段连续操作过程中始终存在合法下一步，并最终保持可通向终局的路径。

### 9. 难度变种

建立在同一结构牌局之上的附加难度条件，例如：

- 牌面被盖住
- 信息不完全可见
- 后续可能加入的额外规则压力

## 可解性与“不会轻易卡死”的定义

### 1. 基础可解性

当前项目对可解性的最低硬约束是：

> 至少存在一种玩家操作顺序能够消除所有牌块。

只要不满足这一点，牌局就不应进入正式候选集。

### 2. 严格生成约束

系统不接受“生成完以后玩家再试试看能不能玩通”这种弱保证，而是要求：

> 在离线构造阶段就验证至少存在若干条持续可推进路径。

这里的“若干条”不是承诺所有分支都能通关，而是要求系统尽量避免把牌局收敛成只有一条极度脆弱的路径。

### 3. 不会轻易卡死

当前阶段，“不会轻易卡死”不定义为“玩家任意乱走都不会死”，而定义为：

- 牌局至少有一条完整通关路径
- 牌局不应过度依赖单一极窄顺序
- 牌局在前期和中期应尽量保留合理的推进分支

后续如果需要更严格，可以进一步引入容错率指标，而不是把“不会卡死”扩大为所有操作都安全。

## 牌局状态分析模型

## 1. 为什么要引入状态空间

如果只看一桌牌的静态摆放，很难评估：

- 这局到底有多少种走法
- 是否很容易走进死局
- 难度究竟是来自结构，还是来自信息压力

因此系统需要从静态布局，转向对“状态空间”的分析。

## 2. 节点

一个节点表示某个时刻的剩余牌块状态。

节点应能表达：

- 还剩哪些牌块
- 当前哪些牌块可参与消除
- 当前是否处于终局或死局

## 3. 边

一条边表示一次合法消除操作。

当前阶段，边的语义先以“运行时规则允许的一次合法配对消除”为准，不在定义中加入额外的人类识别难度。

这样做的原因是：

- 结构评估应先基于客观规则
- 认知难度应放到信息层单独修正

## 4. 终止状态

如果当前状态已经清空全部牌块，则这是成功终局。

## 5. 死局状态

如果当前状态未清空，但不存在任何合法消除操作，则这是非终局死局。

## 6. 森林视角与图视角

系统分析时允许同时使用两种视角：

- 解路径森林
  - 适合讨论玩家操作顺序
  - 适合描述分支数、操作路径和人为可理解性

- 牌局状态图
  - 适合做去重
  - 适合做统计指标
  - 适合控制分析成本

第一阶段不要求精确枚举全状态空间，可以先采用：

- 受限深度展开
- 限定分支宽度展开
- 启发式采样
- Monte Carlo 抽样

## 难度模型

## 1. 为什么不能用单一分数

单一分数很难同时表达这些维度：

- 是否可解
- 有多少分支
- 是否容易误走进死局
- 结构是否压迫
- 信息是否被遮挡

因此当前系统应采用多维度评估，再在需要时合成为面向策划的难度标签或总分。

## 2. 结构难度

结构难度由牌局本身的状态空间和空间结构决定，不考虑额外信息遮挡。

建议重点关注：

- 是否存在完整解
- 解路径数量估计
- 初始可操作分支数
- 平均分支数
- 最小分支数
- 非终局死局比例
- 随机推进后仍可解的概率
- 各阶段可移动牌数量变化
- 各阶段可匹配对数量变化
- 层级压迫与横纵向卡住比例

## 3. 信息难度

信息难度由玩家可见信息是否完整决定。

例如后续出现：

- 牌面被盖住
- 牌面需要翻开
- 局部信息不完全可见

这种变化在结构层可能不改变牌局本身，但客观上会增加玩家认知负担。

## 4. 规则修正难度

除了结构和信息，还可能存在后续规则变种带来的额外难度，例如：

- 限步
- 限时
- 连续操作要求
- 错误惩罚

当前阶段先不落地这些规则，但文档上预留这一层，避免未来把所有难度都塞进结构评估里。

## 5. 当前推荐的最小指标集

为了避免第一版系统过重，建议先保留以下最小指标集：

- `HasSolution`
  - 是否至少存在一条完整解

- `SolutionCountEstimate`
  - 解路径数量估计值

- `InitialBranchCount`
  - 初始局面的合法操作数

- `AverageBranchCount`
  - 搜索过程中的平均分支数

- `DeadEndRate`
  - 搜索中进入非终局死局的比例

- `RandomPlaySurvivalRate`
  - 随机走若干步后仍保持可解的比例

这套指标已经足够支持第一版候选牌局筛选与难度分档。

## 难度档案

系统不建议直接只输出“简单/中等/困难”文本，而更适合定义一组目标区间。

例如：

- 简单
  - 解较多
  - 初始分支较大
  - 死局率低
  - 容错高

- 中等
  - 解适中
  - 分支稳定
  - 存在一定风险
  - 容错中等

- 困难
  - 解较少
  - 关键步骤明显
  - 死局率偏高
  - 容错较低，但不应低到接近唯一解

后续正式关卡生成时，不是“随机拿一局”，而是“筛选落在指定难度档案区间内的候选”。

## 难度变种设计

## 1. 变种的目标

难度变种用于在不完全改动结构牌局的前提下，获得更丰富的关卡体验和更细的难度梯度。

## 2. 当前已确认的变种方向

当前最明确的变种方向是：

- 牌面被盖住

这种变种的特点是：

- 对底层关卡数据影响较小
- 对玩家的信息获取和识别成本有显著影响
- 会客观提高实际体验难度

## 3. 变种的系统位置

建议把难度变种视为建立在结构牌局之上的“修饰层”，而不是写进底层结构生成器里。

也就是说：

- 先有结构牌局
- 再叠加信息层变种
- 最后做二次评估

这样同一结构牌局可以派生为：

- 普通版
- 轻度盖牌版
- 中度盖牌版
- 重度盖牌版

## 离线构造与筛选流程

由于当前关卡数据采用离线构造，因此系统推荐采用批量候选生成和预计算筛选模式。

当前推荐的离线主流程如下：

1. 生成一批候选结构牌局
2. 对每份结构牌局分配牌面
3. 验证是否至少存在一条完整解
4. 对可解牌局做受限状态空间分析
5. 提取多维度结构指标
6. 按难度档案和质量阈值做初筛
7. 对部分候选再叠加难度变种并二次评估
8. 将合格候选导出为正式关卡资源

这种流程的特点是：

- 允许大量候选被淘汰
- 允许评估时间远大于运行时可接受范围
- 允许先积累候选池，再由策划选择

## 自动筛选流程设计

当前系统希望尽量减少“策划从海量候选里手工挑牌局”的负担，因此筛选应尽量自动化。

这里的“自动化”不等于完全黑盒地替代人工，而是指：

- 系统自动完成初筛、评分、排序和分桶
- 人工主要负责定义筛选规则、复核边界样本和做最终关卡选择

推荐把自动筛选分为三层：

### 1. 硬约束层

这一层只做“能否进入候选池”的自动判断，不做风格偏好判断。

凡是不满足硬约束的候选，直接淘汰。

当前建议硬约束至少包括：

- 不存在完整通关路径
- 结构不合法
- 牌数不在目标区间
- 层数不在目标区间
- 初始合法操作数低于最低阈值
- 死局率高于可接受上限
- 明显不符合当前关卡主题要求

这一层的输出应当明确且可解释，例如：

- `AutoReject`
- `RejectReasons`

### 2. 评分与排序层

通过硬约束的候选，不应直接等同于“适合做正式关卡”。

系统需要进一步对候选做综合评分与排序，用于回答：

- 同一档候选中哪些质量更高
- 哪些牌局更适合作为简单关
- 哪些牌局虽然合格，但体验风险较高

当前建议评分至少考虑以下维度：

- 结构难度分
- 分支健康度
- 容错度
- 死局风险
- 节奏稳定性
- 视觉结构质量
- 变种适配性

评分阶段不一定要求一开始就形成最终唯一总分，但至少应能生成：

- 一个综合推荐分
- 多个子分项
- 在目标难度档中的相对排序

### 3. 分桶与标签层

评分之后，系统应自动把候选归入不同桶和标签，而不是只给一个排序。

当前建议至少支持以下几类自动分类：

- 难度桶
  - `easy_core`
  - `normal_core`
  - `hard_core`

- 用途标签
  - `good_for_intro`
  - `good_for_cover_variant`
  - `good_for_visual_shape`
  - `needs_review`

- 风险标签
  - `low_branch_risk`
  - `high_dead_end_risk`
  - `low_tolerance`

这样策划和开发看到的就不是一堆原始候选，而是一组已被整理过的候选池。

## 自动筛选输入

自动筛选器的输入不是原始几何牌桌本身，而应是“候选牌局 + 预计算评估结果”的组合。

第一阶段建议输入至少包含以下信息：

### 1. 结构信息

- CandidateId
- 牌数
- 层数
- 底层大小
- 层级收缩情况
- 关键结构标签

### 2. 可解性信息

- 是否存在完整通关路径
- 解路径数量估计
- 受限搜索深度
- 搜索是否提前截断

### 3. 状态空间统计

- 初始分支数
- 平均分支数
- 最小分支数
- 死局率
- 随机推进存活率
- 可移动牌数量曲线摘要

### 4. 变种适配信息

- 是否适合盖牌
- 盖牌后预计难度增幅
- 是否会因盖牌导致可读性过差

### 5. 人工与系统标签

- 系统自动打的主题标签
- 人工补充标签
- 上次筛选状态

## 自动筛选输出

自动筛选器的输出建议分为三档：

### 1. AutoAccept

表示：

- 满足硬约束
- 综合质量高
- 与当前目标难度档案匹配度较好

这类候选可以直接进入推荐池。

### 2. NeedsReview

表示：

- 没有明显硬伤
- 但部分指标接近边界
- 或者画像特殊，需要人工复核

这类候选是策划最应该重点查看的一组。

### 3. AutoReject

表示：

- 不满足硬约束
- 或虽然可解，但整体质量明显不适合当前目标

同时必须输出明确的淘汰原因，而不是只给一个拒绝结果。

当前建议输出结构至少包括：

- CandidateId
- FilterDecision
- RejectReasons
- DifficultyBucket
- RecommendationScore
- KeyMetrics
- Tags
- NeedsManualReview

## 自动筛选的建议顺序

为了让系统行为清晰且可解释，建议固定采用以下顺序：

1. 读取候选牌局与预计算评估结果
2. 应用硬约束，先淘汰明显坏局
3. 对剩余候选计算综合评分
4. 根据难度档案自动分桶
5. 为候选附加推荐标签和风险标签
6. 输出推荐池、待复核池和淘汰池
7. 将结果导出给 Web 分析台浏览

这个顺序的好处是：

- 逻辑清晰
- 可追踪
- 易于调试
- 易于和人工复核协作

## 筛选规则集

当前建议不要把自动筛选写死成一套固定逻辑，而应引入“筛选规则集”概念。

筛选规则集用于描述：

- 当前这一轮关卡生产目标是什么
- 适合什么难度区间
- 哪些指标阈值更重要

例如后续可以存在：

- 教学关规则集
- 常规关规则集
- 高难度关规则集
- 盖牌关规则集

这样做的意义在于：

- 同一批候选牌局可以被不同规则集重新筛选
- 系统不必因为关卡主题变化而频繁改底层代码

## 策划与人工复核的角色

即使系统尽量自动化，人工仍然有必要保留，但职责应收缩为：

- 定义目标难度档案
- 制定筛选规则集
- 查看高分样本和边界样本
- 对特殊牌局做人工标注
- 最终确认正式关卡池

不建议把人工继续作为主筛选手段。

更推荐的工作方式是：

- 系统先筛
- 人工只复核

## MVP 原则

当前实现阶段应严格遵守 MVP 原则，避免系统一开始就做成过重的大平台。

第一阶段的 MVP 目标不是“把所有评估、筛选、可视化和后台能力一次做完”，而是：

- 先让离线构造结果可稳定导出
- 先让自动筛选跑通
- 先让 Web 端能浏览与对比最核心的数据

### 当前 MVP 建议优先实现的能力

#### 1. 离线侧

- 批量生成候选牌局
- 验证至少存在一条完整通关路径
- 输出最小指标集
- 跑通自动筛选
- 导出推荐池 / 待复核池 / 淘汰池

#### 2. Web 侧

- 候选列表页
- 基础筛选器
- 单局详情页
- 牌桌静态或半静态预览
- 自动筛选结果展示

### 当前 MVP 暂不强求的能力

- 浏览器内实时重生成
- 全状态图可视化
- 在线编辑规则并实时回算
- 完整协作权限系统
- 复杂三维或准三维预览编辑器

## 推荐开源工具方向

为了让系统更健壮、合理、灵活和清晰，当前明确支持尽量优先使用成熟开源工具，而不是从零重复造轮子。

### 1. 图表与数据对比

用于：

- 指标对比
- 难度分布
- 候选池统计
- 死局率和分支数可视化

推荐：

- `ECharts`

原因：

- 成熟稳定
- 图表类型丰富
- 适合表格联动和交互式筛选
- 很适合做内部分析台

### 2. 表格展示

用于：

- 候选列表
- 多字段排序
- 列筛选
- 行高亮

可优先考虑成熟开源表格组件，而不是手写复杂表格行为。

选择标准应为：

- 支持分页
- 支持排序
- 支持列过滤
- 支持和图表联动

### 3. 牌桌预览

用于：

- 快速查看结构牌局
- 分层观察
- 查看盖牌变种效果

第一阶段优先使用 Web 原生二维渲染能力即可，例如：

- SVG
- Canvas

目标是先把信息表达清楚，而不是追求正式游戏级画面还原。

### 4. 状态与数据获取

Web 分析台第一阶段优先采用简单、透明、易调试的开源方案。

建议优先：

- 静态 JSON 数据加载
- 轻量本地服务
- 常见开源前端状态管理方案

当前阶段不建议一开始就引入过重的后台框架。

### 5. 数据存储

第一阶段候选与评估结果不一定需要复杂数据库。

更推荐按 MVP 原则优先考虑：

- JSON
- CSV
- 轻量嵌入式数据库

选择标准是：

- 易导出
- 易对比
- 易回溯
- 易与 Web 页面接通

## 工具选择原则

对于 Web 分析台和自动筛选配套工具，当前统一采用以下原则：

1. 能用成熟开源工具解决的问题，优先不要手写
2. 先选透明、简单、易替换的方案
3. 第一阶段优先保证可读性和可维护性，而不是追求技术栈复杂度
4. 前后端边界保持清晰，避免把离线构造逻辑直接塞进浏览器
5. 任何工具都应服务于“快速观察、快速筛选、快速迭代”这个目标

## 候选池与正式关卡的关系

建议不要只保留最终选中的关卡，而是维护一份候选牌局池。

候选池的意义在于：

- 便于重新筛选难度
- 便于补充变种
- 便于比较不同结构的优劣
- 便于后续做人工标注和经验积累

同时建议把候选池、评估结果和正式关卡数据视为离线侧产物，而不是 Godot 运行时内部状态。

正式关卡只是候选池中经过筛选和确认的一小部分。

## Web 分析台

## 1. 为什么需要 Web 页面

由于系统会离线预计算大量结果，单靠日志或数据文件并不利于策划和开发快速理解牌局质量。

因此当前推荐为本系统配套一个 Web 分析台，用于：

- 浏览候选牌局
- 查看预计算指标
- 预览牌桌结构
- 比较不同候选
- 做人工筛选和标注

它的定位不是玩家页面，而是内部内容生产工具。

## 2. 当前推荐定位

第一版 Web 页面不建议做成在线实时构造平台，而建议做成：

**离线分析结果浏览器**

也就是：

- 后台离线流水线负责生成与评估
- Web 页面负责展示、筛选、对比和人工标注

这与“离线侧工具链与 Godot 运行时解耦”的原则保持一致：

- Web 分析台优先消费离线导出的结果
- Godot 侧优先消费正式关卡数据
- 三者通过数据文件约定协作，而不是直接进程耦合

## 3. 第一版建议能力

Web 分析台第一版建议至少支持以下能力：

- 候选牌局列表
- 多条件筛选
- 单局详情页
- 牌桌结构预览
- 难度与指标展示
- 人工标注与保留状态

## 4. 第一版不强求的能力

当前阶段可以不急着支持：

- 浏览器内实时重新生成牌局
- 浏览器内完整状态图可视化
- 在线编辑规则并即时重算全部结果
- 完整后台权限与协作系统

## 数据产物建议

当前系统建议至少沉淀三类数据产物：

### 1. 候选牌局数据

用于描述牌局本身。

### 2. 评估结果数据

用于描述求解分析与难度指标。

### 3. 正式关卡数据

用于进入游戏运行时资源。

如果后续落地 Web 分析台，还应考虑保留：

### 4. 人工标注数据

用于保存策划和开发对候选的人工判断，例如：

- 保留
- 淘汰
- 待观察
- 适合简单关
- 适合盖牌变种
- 视觉结构优秀

## 与当前项目的关系

当前项目已经具备以下基础能力：

- 第二代网格和完整支撑规则
- 随机堆叠生成骨架
- 至少存在一条可通关路径的基础验证方向
- 正式游戏页和外围流程骨架

因此“配对牌局构造与评估系统”并不是从零开始，而是在现有布局生成能力之上继续演进。

这说明当前应把它理解为：

- 现有布局生成能力的系统化升级

而不是：

- 完全推翻当前生成逻辑另起炉灶

但与此同时，后续工具链在实现层面仍应尽量与 Godot 运行时保持解耦：

- Godot 侧保留“消费正式关卡数据”的职责
- 离线侧承担“生产正式关卡数据”的职责

下一阶段的重点不是立刻推翻已有实现，而是逐步完成以下升级：

- 从“有一条可解路径”升级到“有若干持续可推进路径”
- 从“生成即可”升级到“生成后可评估、可筛选”
- 从“开发自用脚本”升级到“策划可浏览的离线分析台”
- 从“结构唯一版本”升级到“结构牌局 + 难度变种”

## 当前暂不定死的内容

以下内容当前先保留为开放问题，不在本设计文档中定死：

- 解空间是否需要全量精确枚举
- 状态图是否要在第一版就去重合并
- 难度总分的最终公式
- 盖牌变种的具体表现规则
- 候选池持久化采用何种文件格式或数据库
- Web 分析台具体使用什么技术栈
- 自动筛选总分的最终公式和权重
- 表格组件与前端状态管理的最终开源方案选择

这些问题都应在实现过程中结合真实数据、性能和策划反馈继续迭代。

## 推荐推进顺序

当前建议按以下顺序推进：

1. 先补齐“结构牌局构造 + 至少一条完整解”的稳定离线流程
2. 再引入受限搜索和最小指标集
3. 再建立候选池与正式关卡筛选流程
4. 再做自动筛选器与推荐池输出
5. 再做 Web 分析台第一版
6. 最后再加入盖牌等难度变种并做二次评估

## 当前结论总结

当前项目已经明确以下设计方向：

- 系统正式命名为“配对牌局构造与评估系统”
- 核心目标不是自动摆牌，而是离线构造可玩牌局
- 生成阶段必须保证至少存在完整通关路径
- 后续目标是进一步保证存在若干持续可推进路径
- 评估应采用多维度指标，而不是单一难度分
- 结构难度与信息难度必须分离
- 牌面被盖住属于信息层难度变种
- 筛选流程应尽量自动化，人工主要负责规则制定与复核
- 系统结果应通过 Web 分析台提供给策划和开发快速浏览与筛选
- Web 分析台中的图表、表格和数据展示应优先使用成熟开源工具搭建

这份文档作为当前阶段的主设计依据，后续应随着真实实现和真实评估结果持续修订。
## 当前 MVP 落地状态补充

为了让后续实现和文档保持一致，这里补充当前已经落地的最小链路状态。

### 1. 离线侧与 Godot 运行时解耦

当前正式原则已经明确为：

- 离线侧工具链独立负责牌局构造、评估、筛选、导出
- Godot 运行时不承担批量构造与筛选职责
- Godot 只需要知道“第几关对应哪份数据文件”以及“去哪里加载”
- 离线导出的正式关卡数据放到约定目录后，由 Godot 直接消费

这条原则的意义是：

- 保持运行时链路轻量
- 保持离线工具链可以独立演进
- 后续 Web 分析台也可以直接围绕导出数据工作

### 2. 当前已跑通的最小离线链路

当前默认批次配置已经调整为：

- `candidateCount = 120`
- `maxAcceptedLevels = 20`

当前一批离线结果已经成功生成并同步，得到：

- 候选总数 `120`
- 自动通过 `20`
- 待复核 `5`
- 自动淘汰 `91`

对应的正式关卡产物已经输出为：

- `level-catalog.json`
- `levels/level_001.json` 到 `levels/level_020.json`

这意味着“前 20 关正式离线关卡”已经可以作为后续运行时和调试消费的稳定输入。

### 3. 当前 Godot 正式消费方式

Godot 侧当前已经支持两类离线消费入口：

- 单关 JSON 直读
- 目录索引 `level-catalog.json` + `levels/*.json` 消费

其中默认正式链路已经切到目录索引消费，重点是：

- 默认关卡目录资源使用模板化配置
- 默认不再要求手工维护大量单关 `.tres`
- 运行时按关卡号解析目录项，再读取对应正式关卡 JSON

### 4. 当前调试辨识约定

为了让调试时能明确知道当前游玩内容来自哪条链路，调试面板应显式展示：

- `离线正式关卡`
- `调试随机关卡`
- `原型关卡`

这属于运行时可观测性的一部分，目的是减少“当前到底在玩什么”的认知成本。

### 5. 下一阶段对自动化筛选的要求

既然离线侧已经能稳定导出正式关卡，后续自动化筛选需要继续强化为：

- 批量生成候选
- 批量评估最小指标集
- 批量自动分类为 `AutoAccept / NeedsReview / AutoReject`
- 自动导出正式运行时目录
- 自动同步到 Godot 生成目录
- 自动产出给 Web 分析台消费的数据文件

也就是说，人工主要参与：

- 调整筛选阈值
- 复核边界案例
- 做最终关卡编排

而不是人工逐局搬运和拼装运行时数据。
