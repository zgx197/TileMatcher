# 麻将牌局构造与评估系统设计

## 文档目标

本文档用于整合当前项目围绕“麻将牌局构造与评估系统”的设计共识，明确后续自动化关卡内容生产的目标、边界、术语、离线流程和评估方向。

它不是最终定稿，也不是实现说明，而是一份当前阶段的主设计文档，用于指导后续边实现、边验证、边调整。

本文档重点回答以下问题：

- 我们到底要构造什么，而不只是“摆一桌牌”
- 什么叫可玩、可解、不会轻易卡死
- 难度为什么不能只靠单一分数衡量
- 为什么系统应当以离线预计算为主，而不是运行时即时生成
- 为什么需要一套面向策划和开发的 Web 分析台

## 当前结论

当前项目不再把相关能力称为“自动布局”，而正式称为：

**麻将牌局构造与评估系统**

这样命名的原因是：

- “布局”只强调牌怎么摆
- “牌局”强调完整游玩过程
- “构造”强调这是一个受约束的生产过程
- “评估”强调生成结果必须经过分析、筛选和分档，而不是生成即通过

如果进一步强调使用方式，本系统也可以被理解为：

**离线麻将牌局构造、评估与筛选流水线**

## 系统目标

本系统的目标不是简单生成一份看起来像麻将堆叠的布局，而是离线构造一批候选牌局，对它们进行可解性和难度评估，再筛选出适合作为正式关卡的数据。

系统至少要满足以下目标：

1. 生成的牌局在几何上合法
2. 生成时就保证至少存在一种玩家操作顺序可以消除全部麻将
3. 尽量保证不止一条持续可推进路径，避免牌局退化成过度脆弱的唯一顺序题
4. 对候选牌局给出多维度难度指标，而不是单一“好/坏”判断
5. 支持在同一结构牌局上叠加不同难度变种，例如盖牌
6. 支持离线批量预计算，并把结果提供给策划和开发快速浏览与筛选

## 设计原则

### 1. 可解性优先于随机性

系统首先要保证牌局可通关，其次才谈结构变化和随机性。

如果一份牌局在视觉上很自然，但没有完整通关路径，它就不应进入候选集。

### 2. 评估优先于产出

不是“生成一局牌桌就结束”，而是“生成候选，再评估，再筛选，再产出正式关卡”。

### 3. 离线优先

当前关卡数据以离线构造为主，因此可以接受：

- 更重的搜索
- 更长的预计算时间
- 更多候选淘汰
- 更复杂的统计和筛选

这意味着系统不必过早为了运行时性能牺牲评估质量。

### 4. 结构难度与认知难度分离

同一份结构牌局，在规则不变的情况下，可能通过“牌面被盖住”这种信息层变化显著提升难度。

因此难度不能只看结构，还应区分：

- 结构难度
- 信息难度
- 规则修正难度

### 5. 先可分析，再可视化，再可调参

系统的第一价值是让牌局可分析，第二价值是让结果可被人快速理解，第三价值才是让参数逐步可配置。

## 系统范围

本系统当前覆盖以下内容：

- 候选结构牌局构造
- 牌面分配
- 可解性验证
- 解空间分析
- 多维度难度评估
- 候选牌局筛选
- 正式关卡数据产出
- Web 端分析结果展示

本系统当前不直接覆盖以下内容：

- 运行时在线即时生成
- 玩家端动态求解提示
- 最终商业化关卡投放策略
- 完整后台内容管理系统

## 核心术语

### 1. 结构牌局

只描述麻将的空间结构和牌面分配结果，不包含额外的玩法修饰。

它至少包括：

- 每张麻将的位置
- 层级关系
- 牌面类型
- 初始可交互关系

### 2. 候选牌局

由系统离线生成的一份待评估牌局。

候选牌局不等于正式关卡。只有通过评估和筛选后，才可能进入正式关卡库。

### 3. 正式关卡

已经经过筛选、标注和确认，最终进入游戏资源的牌局数据。

### 4. 解路径

从初始状态出发，通过一系列合法消除操作，最终清空全部麻将的一条完整操作序列。

### 5. 解路径森林

把所有可能的玩家操作通关顺序按搜索展开后形成的树状集合。

它强调“顺序视角”，适合描述玩家操作分支。

### 6. 牌局状态图

如果把操作历史不同但剩余状态相同的节点合并，则解空间可视为一张有向无环图。

它强调“状态视角”，适合做统计、去重和评估。

### 7. 死局状态

当前状态还未清空全部麻将，但已经不存在任何合法推进操作。

### 8. 持续可推进路径

指从初始状态出发，在一段连续操作过程中始终存在合法下一步，并最终保持可通向终局的路径。

### 9. 难度变种

建立在同一结构牌局之上的附加难度条件，例如：

- 牌面被盖住
- 信息不完全可见
- 后续可能加入的额外规则压力

## 可解性与“不会轻易卡死”的定义

### 1. 基础可解性

当前项目对可解性的最低硬约束是：

> 至少存在一种玩家操作顺序能够消除所有麻将。

只要不满足这一点，牌局就不应进入正式候选集。

### 2. 严格生成约束

系统不接受“生成完以后玩家再试试看能不能玩通”这种弱保证，而是要求：

> 在离线构造阶段就验证至少存在若干条持续可推进路径。

这里的“若干条”不是承诺所有分支都能通关，而是要求系统尽量避免把牌局收敛成只有一条极度脆弱的路径。

### 3. 不会轻易卡死

当前阶段，“不会轻易卡死”不定义为“玩家任意乱走都不会死”，而定义为：

- 牌局至少有一条完整通关路径
- 牌局不应过度依赖单一极窄顺序
- 牌局在前期和中期应尽量保留合理的推进分支

后续如果需要更严格，可以进一步引入容错率指标，而不是把“不会卡死”扩大为所有操作都安全。

## 牌局状态分析模型

## 1. 为什么要引入状态空间

如果只看一桌牌的静态摆放，很难评估：

- 这局到底有多少种走法
- 是否很容易走进死局
- 难度究竟是来自结构，还是来自信息压力

因此系统需要从静态布局，转向对“状态空间”的分析。

## 2. 节点

一个节点表示某个时刻的剩余麻将状态。

节点应能表达：

- 还剩哪些麻将
- 当前哪些麻将可参与消除
- 当前是否处于终局或死局

## 3. 边

一条边表示一次合法消除操作。

当前阶段，边的语义先以“运行时规则允许的一次合法配对消除”为准，不在定义中加入额外的人类识别难度。

这样做的原因是：

- 结构评估应先基于客观规则
- 认知难度应放到信息层单独修正

## 4. 终止状态

如果当前状态已经清空全部麻将，则这是成功终局。

## 5. 死局状态

如果当前状态未清空，但不存在任何合法消除操作，则这是非终局死局。

## 6. 森林视角与图视角

系统分析时允许同时使用两种视角：

- 解路径森林
  - 适合讨论玩家操作顺序
  - 适合描述分支数、操作路径和人为可理解性

- 牌局状态图
  - 适合做去重
  - 适合做统计指标
  - 适合控制分析成本

第一阶段不要求精确枚举全状态空间，可以先采用：

- 受限深度展开
- 限定分支宽度展开
- 启发式采样
- Monte Carlo 抽样

## 难度模型

## 1. 为什么不能用单一分数

单一分数很难同时表达这些维度：

- 是否可解
- 有多少分支
- 是否容易误走进死局
- 结构是否压迫
- 信息是否被遮挡

因此当前系统应采用多维度评估，再在需要时合成为面向策划的难度标签或总分。

## 2. 结构难度

结构难度由牌局本身的状态空间和空间结构决定，不考虑额外信息遮挡。

建议重点关注：

- 是否存在完整解
- 解路径数量估计
- 初始可操作分支数
- 平均分支数
- 最小分支数
- 非终局死局比例
- 随机推进后仍可解的概率
- 各阶段可移动牌数量变化
- 各阶段可匹配对数量变化
- 层级压迫与横纵向卡住比例

## 3. 信息难度

信息难度由玩家可见信息是否完整决定。

例如后续出现：

- 牌面被盖住
- 牌面需要翻开
- 局部信息不完全可见

这种变化在结构层可能不改变牌局本身，但客观上会增加玩家认知负担。

## 4. 规则修正难度

除了结构和信息，还可能存在后续规则变种带来的额外难度，例如：

- 限步
- 限时
- 连续操作要求
- 错误惩罚

当前阶段先不落地这些规则，但文档上预留这一层，避免未来把所有难度都塞进结构评估里。

## 5. 当前推荐的最小指标集

为了避免第一版系统过重，建议先保留以下最小指标集：

- `HasSolution`
  - 是否至少存在一条完整解

- `SolutionCountEstimate`
  - 解路径数量估计值

- `InitialBranchCount`
  - 初始局面的合法操作数

- `AverageBranchCount`
  - 搜索过程中的平均分支数

- `DeadEndRate`
  - 搜索中进入非终局死局的比例

- `RandomPlaySurvivalRate`
  - 随机走若干步后仍保持可解的比例

这套指标已经足够支持第一版候选牌局筛选与难度分档。

## 难度档案

系统不建议直接只输出“简单/中等/困难”文本，而更适合定义一组目标区间。

例如：

- 简单
  - 解较多
  - 初始分支较大
  - 死局率低
  - 容错高

- 中等
  - 解适中
  - 分支稳定
  - 存在一定风险
  - 容错中等

- 困难
  - 解较少
  - 关键步骤明显
  - 死局率偏高
  - 容错较低，但不应低到接近唯一解

后续正式关卡生成时，不是“随机拿一局”，而是“筛选落在指定难度档案区间内的候选”。

## 难度变种设计

## 1. 变种的目标

难度变种用于在不完全改动结构牌局的前提下，获得更丰富的关卡体验和更细的难度梯度。

## 2. 当前已确认的变种方向

当前最明确的变种方向是：

- 牌面被盖住

这种变种的特点是：

- 对底层关卡数据影响较小
- 对玩家的信息获取和识别成本有显著影响
- 会客观提高实际体验难度

## 3. 变种的系统位置

建议把难度变种视为建立在结构牌局之上的“修饰层”，而不是写进底层结构生成器里。

也就是说：

- 先有结构牌局
- 再叠加信息层变种
- 最后做二次评估

这样同一结构牌局可以派生为：

- 普通版
- 轻度盖牌版
- 中度盖牌版
- 重度盖牌版

## 离线构造与筛选流程

由于当前关卡数据采用离线构造，因此系统推荐采用批量候选生成和预计算筛选模式。

当前推荐的离线主流程如下：

1. 生成一批候选结构牌局
2. 对每份结构牌局分配牌面
3. 验证是否至少存在一条完整解
4. 对可解牌局做受限状态空间分析
5. 提取多维度结构指标
6. 按难度档案和质量阈值做初筛
7. 对部分候选再叠加难度变种并二次评估
8. 将合格候选导出为正式关卡资源

这种流程的特点是：

- 允许大量候选被淘汰
- 允许评估时间远大于运行时可接受范围
- 允许先积累候选池，再由策划选择

## 候选池与正式关卡的关系

建议不要只保留最终选中的关卡，而是维护一份候选牌局池。

候选池的意义在于：

- 便于重新筛选难度
- 便于补充变种
- 便于比较不同结构的优劣
- 便于后续做人工标注和经验积累

正式关卡只是候选池中经过筛选和确认的一小部分。

## Web 分析台

## 1. 为什么需要 Web 页面

由于系统会离线预计算大量结果，单靠日志或数据文件并不利于策划和开发快速理解牌局质量。

因此当前推荐为本系统配套一个 Web 分析台，用于：

- 浏览候选牌局
- 查看预计算指标
- 预览牌桌结构
- 比较不同候选
- 做人工筛选和标注

它的定位不是玩家页面，而是内部内容生产工具。

## 2. 当前推荐定位

第一版 Web 页面不建议做成在线实时构造平台，而建议做成：

**离线分析结果浏览器**

也就是：

- 后台离线流水线负责生成与评估
- Web 页面负责展示、筛选、对比和人工标注

## 3. 第一版建议能力

Web 分析台第一版建议至少支持以下能力：

- 候选牌局列表
- 多条件筛选
- 单局详情页
- 牌桌结构预览
- 难度与指标展示
- 人工标注与保留状态

## 4. 第一版不强求的能力

当前阶段可以不急着支持：

- 浏览器内实时重新生成牌局
- 浏览器内完整状态图可视化
- 在线编辑规则并即时重算全部结果
- 完整后台权限与协作系统

## 数据产物建议

当前系统建议至少沉淀三类数据产物：

### 1. 候选牌局数据

用于描述牌局本身。

### 2. 评估结果数据

用于描述求解分析与难度指标。

### 3. 正式关卡数据

用于进入游戏运行时资源。

如果后续落地 Web 分析台，还应考虑保留：

### 4. 人工标注数据

用于保存策划和开发对候选的人工判断，例如：

- 保留
- 淘汰
- 待观察
- 适合简单关
- 适合盖牌变种
- 视觉结构优秀

## 与当前项目的关系

当前项目已经具备以下基础能力：

- 第二代网格和完整支撑规则
- 随机堆叠生成骨架
- 至少存在一条可通关路径的基础验证方向
- 正式游戏页和外围流程骨架

因此“麻将牌局构造与评估系统”并不是从零开始，而是在现有布局生成能力之上继续演进。

下一阶段的重点不是立刻推翻已有实现，而是逐步完成以下升级：

- 从“有一条可解路径”升级到“有若干持续可推进路径”
- 从“生成即可”升级到“生成后可评估、可筛选”
- 从“开发自用脚本”升级到“策划可浏览的离线分析台”
- 从“结构唯一版本”升级到“结构牌局 + 难度变种”

## 当前暂不定死的内容

以下内容当前先保留为开放问题，不在本设计文档中定死：

- 解空间是否需要全量精确枚举
- 状态图是否要在第一版就去重合并
- 难度总分的最终公式
- 盖牌变种的具体表现规则
- 候选池持久化采用何种文件格式或数据库
- Web 分析台具体使用什么技术栈

这些问题都应在实现过程中结合真实数据、性能和策划反馈继续迭代。

## 推荐推进顺序

当前建议按以下顺序推进：

1. 先补齐“结构牌局构造 + 至少一条完整解”的稳定离线流程
2. 再引入受限搜索和最小指标集
3. 再建立候选池与正式关卡筛选流程
4. 再做 Web 分析台第一版
5. 最后再加入盖牌等难度变种并做二次评估

## 当前结论总结

当前项目已经明确以下设计方向：

- 系统正式命名为“麻将牌局构造与评估系统”
- 核心目标不是自动摆牌，而是离线构造可玩牌局
- 生成阶段必须保证至少存在完整通关路径
- 后续目标是进一步保证存在若干持续可推进路径
- 评估应采用多维度指标，而不是单一难度分
- 结构难度与信息难度必须分离
- 牌面被盖住属于信息层难度变种
- 系统结果应通过 Web 分析台提供给策划和开发快速浏览与筛选

这份文档作为当前阶段的主设计依据，后续应随着真实实现和真实评估结果持续修订。
