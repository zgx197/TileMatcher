# 堆叠框架与网格规则设计

## 文档目标

本文档定义 TileMatcher 下一阶段采用的通用堆叠框架，用于替代第一版以 `2 x 2` 固定占位为核心的网格方案。

新的目标不是只服务于当前原型，而是为后续这些需求提供统一基础：

- 支持长方形牌块，而不是固定正方逻辑占位
- 支持同一种形状在不同错位下自然出现“两牌支撑”或“四牌支撑”
- 支持从几何覆盖关系中推导合法放置，而不是先写死支撑模式
- 支持未来扩展更多矩形尺寸，甚至进一步扩展到非矩形 shape
- 保持逻辑层稳定、可调试、可验证，不依赖浮点判定

## 核心结论

第二代方案采用以下正式定义：

- 基础逻辑空间仍然使用整数离散网格
- 网格最小单位不再等价于“一张牌块的位置”，而是“更细粒度的几何微单元”
- 每张牌块在逻辑层由一个矩形 footprint 描述
- 上层牌块是否合法，不再通过“二支撑 / 四支撑”这样的业务术语直接判定
- 合法性由“该牌块底面投影在下一层是否被完整覆盖”决定

一句话总结：

> 不把“支撑模式”作为底层规则，而把“底面覆盖关系”作为底层规则，让两支撑和四支撑自然成为分析结果。

## 为什么第一代 `2 x 2` 方案不再足够

第一代方案解决的是：

- 半格错位的整数化表达
- 基于交点的多层叠放
- 固定玩法下的快速原型验证

它的优势是简单、稳定、好实现。

但它有明显边界：

- 一张牌的逻辑形状被固定为对称的 `2 x 2`
- 上层牌的候选落点几乎等同于下层四牌交点
- “四点支撑”不是结果，而是被坐标系统隐含写死
- 很难表达更接近参考游戏的长方形牌面与非对称覆盖关系

因此，第一代方案更适合作为历史原型，而不再适合作为最终通用框架。

## 第二代框架的三层抽象

### 1. 基础网格层

基础网格层负责定义最小逻辑微单元。

建议：

- 使用整数坐标
- 使用统一的三维离散坐标 `(x, y, z)`
- `z` 仍表示层级
- `x, y` 表示平面上的微单元坐标

这一层不表达具体题材牌块，只表达空间。

### 2. 形状层

形状层负责定义一张牌在逻辑层的 footprint。

第一版采用矩形：

```csharp
public sealed class TileShape
{
    public int WidthUnits { get; init; }
    public int HeightUnits { get; init; }
}
```

推荐第一版标准牌块形状：

- `WidthUnits = 4`
- `HeightUnits = 6`

选择 `4 x 6` 的原因：

- 它天然表达“长比宽更长”
- 宽高都是整数，便于离散化
- 它比 `2 x 2` 有更高表达能力
- 它仍然足够简单，便于当前项目快速落地

后续如果需要更高分辨率，可以升级到：

- `6 x 9`
- `8 x 12`

但第一版不建议一开始就使用过细粒度。

### 3. 放置与覆盖层

这一层负责定义：

- 一张牌放到某层后覆盖哪些微单元
- 这张牌的底面投影在 `z - 1` 层需要哪些覆盖
- 当前放置是否合法

核心规则只有一条：

> 一张牌在某层的底面投影区域，必须被下一层已存在牌的 footprint union 完整覆盖。

## 为什么不再把“支撑”作为底层概念

“支撑”更适合做调试语言或玩法解释，不适合作为底层建模起点。

原因：

- 支撑是结果，不是几何输入
- 两支撑、四支撑、本质都是底面投影被若干下层牌共同覆盖后的统计结论
- 如果先写死支撑模式，会让系统变碎，不利于扩展

在第二代方案中：

- 程序先计算覆盖关系
- 然后再从覆盖关系中分析“被几张牌共同覆盖”
- 最后才把结果解释成人类熟悉的“两支撑 / 四支撑”

## 基础数据定义建议

### 基础单元

```csharp
public readonly struct GridCell
{
    public readonly int X;
    public readonly int Y;
    public readonly int Z;
}
```

### 牌形状

```csharp
public sealed class TileShape
{
    public int WidthUnits { get; init; }
    public int HeightUnits { get; init; }
}
```

### 牌放置

```csharp
public sealed class TilePlacement
{
    public int Id { get; init; }
    public string Type { get; init; } = string.Empty;
    public int GX { get; init; }
    public int GY { get; init; }
    public int GZ { get; init; }
    public TileShape Shape { get; init; } = null!;
}
```

第一版建议使用左上角锚点：

- `GX` 表示 footprint 左上角 X
- `GY` 表示 footprint 左上角 Y
- `GZ` 表示层级

这样矩形计算最直接，也最容易调试。

## footprint 与底面投影

对于一张牌块：

- footprint 是它在当前层覆盖的矩形区域
- 底面投影是同一个矩形投影到 `z - 1` 层的区域

例如：

- 标准牌块 shape 为 `4 x 6`
- 放置坐标为 `(10, 12, 3)`

那么：

- 当前层 footprint 为 `[10, 14) x [12, 18)` at `z = 3`
- 需要的底面覆盖区域为 `[10, 14) x [12, 18)` at `z = 2`

## 合法性定义

第二代第一版采用最严格、最清晰的规则：

> 全底面都必须支撑。

即：

- 上层牌底面投影中的每一个逻辑微单元
- 都必须被下一层某张牌的 footprint 覆盖

不使用面积阈值，不使用模糊比例判定。

这样做的好处：

- 规则明确
- 调试容易
- 生成器可以直接反推底层缺什么
- 不会因为阈值设置引入歧义

## 为什么同一套形状可以自然产生两支撑和四支撑

当一张长方形牌块放到上层时，它底面投影可能出现不同覆盖结果：

- 如果底面投影只落在左右两张牌的 footprint union 内，那么它就是“两牌共同覆盖”
- 如果底面投影横跨四张牌的 footprint union，那么它就是“四牌共同覆盖”

因此：

- 两支撑不是规则
- 四支撑也不是规则
- 它们都是“底面投影被几张下层牌覆盖”的统计结果

## 生成器的思考方式

第二代生成器不应再从“交点”出发，而应从“矩形覆盖”出发。

### 自底向上

1. 已知下一层哪些 footprint 已存在
2. 枚举当前层矩形可能的放置位置
3. 检查该位置的底面投影是否被完整覆盖
4. 如果覆盖完整，则该位置合法

### 自顶向下

1. 先决定某个高层位置要放一张牌
2. 计算它底面投影需要哪些单元
3. 反推下一层至少需要放哪些牌来覆盖这些单元
4. 递归往下生成

对关卡构造来说，第二种方向未来更有潜力；对当前实现来说，可以先从第一种做起。

## 关于同层落点步长

虽然基础网格是细粒度整数网格，但不建议允许完全任意坐标放置。

更合理的做法是：

- 基础网格足够细
- 真实落点使用更高层的离散步长约束

例如在 `4 x 6` 牌形下，可以进一步定义允许的候选步长：

- X 方向步长候选：`2`
- Y 方向步长候选：`3`

这样既保留表达能力，又不会把候选空间炸得过大。

注意：

- 这是生成层约束
- 不是底层几何系统限制

底层几何系统仍然应支持任意整数锚点。

## 第二代方案推荐的最小落地版本

当前建议采用以下默认参数：

### 基础设置

- 基础微单元：整数格
- 锚点：左上角
- 标准牌块形状：`4 x 6`

### 合法性设置

- 上层牌底面投影必须被下一层完全覆盖
- 不使用支撑面积阈值
- 不区分“两支撑规则”与“四支撑规则”

### 分析输出

建议为每张牌提供派生结果：

- footprint rect
- required support rect
- 支撑它的下层牌列表
- 参与覆盖的牌数量
- 当前是否合法

这样调试层就能直接显示：

- 这张牌为什么合法
- 这张牌为什么被两张牌共同覆盖
- 这张牌为什么横跨四张牌

## 对现有系统的影响

第二代方案落地后，以下模块都需要逐步升级：

- `GridMath`
  - 从固定 `2 x 2` footprint 升级为可配置矩形 footprint
- `TileData / TilePlacement`
  - 从默认固定大小升级为显式 shape 引用
- `LayoutValidator`
  - 从“规则解释”升级为“覆盖合法性判定”
- `RandomStackLayoutGenerator`
  - 从交点候选点生成升级为矩形候选区域生成
- 调试工具窗
  - 需要增加 footprint / support area / 覆盖来源的可视化

## 实施顺序建议

### 阶段 1：文档与模型定型

- 固定 `4 x 6` 标准牌块 shape
- 固定左上角锚点
- 固定全底面完全覆盖规则

### 阶段 2：底层几何工具升级

- 新增 `TileShape`
- 新增矩形 footprint 计算
- 新增底面投影查询
- 新增覆盖 union 判断

### 阶段 3：业务层接入

- 更新布局校验器
- 更新随机生成器
- 更新固定原型

### 阶段 4：调试能力升级

- 在调试工具窗显示当前牌 footprint 信息
- 显示底面覆盖结果
- 标记哪些牌由 2 张下层牌覆盖
- 标记哪些牌由 4 张下层牌覆盖

## 当前正式结论

TileMatcher 下一阶段的通用堆叠框架正式采用以下方向：

- 逻辑层仍然使用整数离散网格
- 每张牌块第一版使用矩形 shape 表达
- 推荐标准牌块逻辑尺寸为 `4 x 6`
- 上层合法性以“全底面投影必须被下一层完整覆盖”为准
- “两支撑 / 四支撑”不再作为底层规则，而作为覆盖分析结果

这套方案比第一代 `2 x 2` 固定占位方案更通用，也更接近目标游戏后续可能需要的堆叠表达能力。
