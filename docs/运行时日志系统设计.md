# 运行时日志系统设计

## 文档定位

本文档用于定义项目内统一的运行时日志系统方案，目标是解决以下问题：

- Windows 导出包运行后出现闪退或启动失败时，缺少稳定、可直接查看的日志落点
- Android 真机运行时虽然可能存在 `logcat` 输出，但项目层日志没有统一格式、统一入口和统一存储位置
- 当前代码中大量使用 `GD.Print / GD.PushWarning / GD.PushError`，但它们尚未形成稳定的日志文件体系
- 后续准备在调试面板中加入日志区域，因此需要先明确日志系统的职责、接口、文件结构和平台差异

本文档是后续实现日志系统的主设计依据。

## 目标

本次日志系统优先满足以下目标：

- 提供统一的项目级日志入口，而不是继续散落使用 `GD.Print`
- 在 Windows 导出包运行后，优先在可执行文件所在目录生成 `logs/` 文件夹
- 在 Android 运行时，稳定写入 `user://logs/`，并同步输出关键内容到 `logcat`
- 在调试面板中提供统一日志区域，便于 Windows 与 Android 共用操作入口
- 为后续排查“启动即闪退”“资源加载失败”“存档异常”“流程切换异常”提供足够上下文
- 保持第一阶段实现简单、稳健，不引入过重的日志框架依赖

## 非目标

本阶段不以以下内容为目标：

- 远程日志上传
- 云端聚合检索
- 完整埋点分析平台
- 覆盖所有原生层崩溃日志
- 做成复杂的可视化日志浏览器

需要明确：

- 项目日志系统主要解决“C# 与项目逻辑已经开始运行后”的日志记录问题
- 如果崩溃发生在 Godot 原生进程或 C# 程序集还未成功启动之前，项目日志不一定能覆盖
- 这类更底层的崩溃，后续需要再补“引擎级日志”或“启动包装层”方案

## 当前问题

当前项目已经具备一定数量的调试输出，但存在以下明显缺口：

- 输出入口不统一
  - 目前主要依赖 `GD.Print`、`GD.PushWarning`、`GD.PushError`
  - 很难统一控制格式、级别、文件落盘与冗余信息

- 日志落点不稳定
  - Windows 导出后，用户无法在程序目录稳定找到项目日志
  - Android 上没有明确的项目日志文件路径和查看方式

- 启动阶段缺少统一初始化
  - 如果异常发生得很早，当前没有“会话开始”日志和环境头信息

- 调试面板没有日志功能入口
  - 无法在导出包中快速查看最近日志、复制日志、清空日志或打开日志目录

## 总体方案

日志系统分为两个层级：

### 1. 项目级运行时日志

由项目自己的 C# 代码负责，覆盖：

- 启动流程
- 场景切换
- 资源加载
- 存档读写
- 页面流转
- 棋盘生成
- 关键交互状态
- 已捕获异常与未处理托管异常

这是本次优先实现的部分。

### 2. 引擎级或进程级日志

由 Godot 引擎、.NET 运行时或启动包装层负责，覆盖：

- C# 程序集加载前的失败
- 进程启动即退出
- 更底层的原生崩溃

这一层不在本阶段直接实现，但需要在设计上预留接口与文档说明。

## 平台策略

### Windows

Windows 侧采用“可执行文件目录优先，失败后回退到 `user://logs/`”的策略。

优先路径：

- `<exe所在目录>/logs/`

回退路径：

- `user://logs/`

这样做的原因：

- 用户最容易在导出包目录直接找到日志
- 免安装 zip 包天然适合这种模式
- 如果用户把程序放进 `Program Files` 之类的只读目录，则需要自动回退

### Android

Android 侧不使用“APK 同目录日志”方案，而统一写入：

- `user://logs/`

同时需要同步输出关键日志到 `logcat`。

原因：

- APK 安装目录不可写
- 安装目录对用户通常不可直接访问
- `user://` 是 Godot 跨平台中最稳定的项目私有可写目录

Android 的“可见性”不应依赖文件管理器直接访问，而应依赖：

- 调试面板中的日志区域
- 应用内查看/复制日志
- `adb logcat`

## 日志文件目录结构

统一约定如下：

```text
logs/
  latest.log
  latest-error.log
  session-20260406-101522.log
  session-20260406-101522-error.log
```

说明：

- `latest.log`
  - 始终指向当前或最近一次运行的完整日志内容
  - 便于快速定位

- `latest-error.log`
  - 只保留 `Warning / Error / Fatal` 级别
  - 便于在大日志中快速查错

- `session-*.log`
  - 每次启动一个新文件
  - 便于保留历史记录

- `session-*-error.log`
  - 对应会话的错误摘要

### 保留策略

建议第一阶段保留最近 20 次会话日志：

- 超出数量后，按时间删除最旧文件
- `latest.log` 与 `latest-error.log` 不计入普通会话数量限制

## 日志级别

统一定义五个级别：

- `Trace`
  - 最细粒度调试信息
  - 默认不在发布版大量开启

- `Info`
  - 正常流程日志

- `Warn`
  - 可恢复问题、回退路径、配置缺失

- `Error`
  - 当前操作失败，但进程可能仍继续运行

- `Fatal`
  - 无法继续执行的错误或未处理异常

第一阶段建议默认记录：

- `Info` 及以上到完整日志
- `Warn` 及以上到错误日志

## 日志格式

建议统一文本格式如下：

```text
2026-04-06 10:15:22.134 [INFO] [AppRoot] startup begin
2026-04-06 10:15:22.287 [INFO] [RuntimeLog] platform=Windows, version=0.1.5, scene=res://scenes/app/AppRoot.tscn
2026-04-06 10:15:23.104 [WARN] [PlayerProgressStore] load failed, fallback to default progress
2026-04-06 10:15:24.918 [ERROR] [GameScene] offline level load failed: level=7, path=...
System.InvalidOperationException: ...
```

格式要素包括：

- 本地时间戳，精确到毫秒
- 级别
- 分类
- 正文
- 异常堆栈

分类建议直接使用模块名：

- `RuntimeLog`
- `AppRoot`
- `GameScene`
- `BoardController`
- `PlayerProgressStore`
- `OfflineLevelJsonLoader`
- `PetCatalog`

## 初始化时机

日志系统必须尽可能早初始化。

建议顺序：

1. 在 `AppRoot._EnterTree()` 中调用日志初始化
2. 在日志初始化完成后立刻写入“会话头信息”
3. 注册全局异常钩子
4. 后续各页面与控制器再正常使用日志接口

### 为什么不用 `_Ready()`

`_Ready()` 太晚。

如果一些异常发生在：

- 节点树刚进入时
- 配置资源加载时
- 页面切换链路中

那么 `_Ready()` 之后才初始化日志会丢失关键线索。

## 启动头信息

每次启动都应记录如下信息：

- 时间
- 平台
- 是否为导出环境
- 版本号
- 包名
- 当前主场景
- `OS.GetExecutablePath()`
- `ProjectSettings.GlobalizePath("user://")`
- 日志根目录最终解析结果
- Godot 渲染方式与基础环境信息

示例：

```text
2026-04-06 10:15:22.287 [INFO] [RuntimeLog] session begin
2026-04-06 10:15:22.288 [INFO] [RuntimeLog] platform=Windows
2026-04-06 10:15:22.288 [INFO] [RuntimeLog] version=0.1.5, package=com.zgx197.tilematcher
2026-04-06 10:15:22.289 [INFO] [RuntimeLog] exe_dir=D:\Games\TileMatcher
2026-04-06 10:15:22.289 [INFO] [RuntimeLog] user_dir=C:\Users\...\AppData\Roaming\Godot\app_userdata\TileMatcher
2026-04-06 10:15:22.289 [INFO] [RuntimeLog] log_dir=D:\Games\TileMatcher\logs
```

## 异常捕获策略

日志系统至少需要注册以下异常入口：

- `AppDomain.CurrentDomain.UnhandledException`
- `TaskScheduler.UnobservedTaskException`

用途：

- 抓取未处理的托管异常
- 在闪退前尽量留下 `Fatal` 级别日志

同时建议在关键入口显式包裹异常并重新抛出或回退：

- `AppRoot` 启动链路
- `GameScene.StartLevel`
- 离线关卡读取
- 存档读写

## 建议的代码结构

建议新增如下文件：

- `godot/scripts/logging/LogLevel.cs`
- `godot/scripts/logging/RuntimeLog.cs`
- `godot/scripts/logging/RuntimeLogConfig.cs`
- `godot/scripts/logging/LogSnapshot.cs`

职责建议如下：

### `LogLevel.cs`

定义日志级别枚举。

### `RuntimeLog.cs`

统一对外入口，负责：

- 初始化
- 文件写入
- 同步到 Godot 输出
- 日志轮转
- 最近日志读取
- 错误日志单独写入
- 线程安全控制

建议对外接口：

```csharp
public static class RuntimeLog
{
    public static bool IsInitialized { get; }
    public static string LogDirectoryPath { get; }
    public static string LatestLogPath { get; }
    public static string LatestErrorLogPath { get; }

    public static void Initialize();
    public static void Shutdown();
    public static void Flush();

    public static void Trace(string category, string message);
    public static void Info(string category, string message);
    public static void Warn(string category, string message);
    public static void Error(string category, string message, Exception? exception = null);
    public static void Fatal(string category, string message, Exception? exception = null);

    public static string ReadLatestLogText(int maxChars = 12000);
    public static string ReadLatestErrorLogText(int maxChars = 12000);
    public static IReadOnlyList<LogSnapshot> ListRecentSessions();
    public static void ClearAllLogs();
}
```

### `RuntimeLogConfig.cs`

用于集中保存日志策略配置，例如：

- 会话保留数量
- 单文件大小上限
- 是否同步镜像到 Godot 输出
- 是否开启 `Trace`

### `LogSnapshot.cs`

供调试面板读取最近日志列表时使用。

## 文件写入策略

### Windows

解析顺序建议：

1. `OS.GetExecutablePath()`
2. 取其目录
3. 尝试创建 `<exe目录>/logs`
4. 如果失败，则回退 `user://logs`

如果发生回退，日志系统应立刻记录：

```text
[WARN] [RuntimeLog] executable directory is not writable, fallback to user://logs
```

### Android

直接使用：

- `ProjectSettings.GlobalizePath("user://logs")`

同时建议每次初始化都打印：

- `user://` 实际解析路径
- Android 平台标识

## 与 Godot 输出的关系

第一阶段不建议完全替换 `GD.Print` 的可见性，而是做“镜像输出”：

- `RuntimeLog.Info` 在写文件的同时调用 `GD.Print`
- `RuntimeLog.Warn` 同时调用 `GD.PushWarning`
- `RuntimeLog.Error / Fatal` 同时调用 `GD.PushError`

好处：

- Godot 编辑器和 `logcat` 仍然能看到熟悉输出
- 项目层又可以稳定落盘

后续代码不再直接散落调用 `GD.Print`，而是逐步收敛到 `RuntimeLog`

## 调试面板日志区域设计

日志相关 UI 建议直接接入现有共享调试面板体系。

建议新增一个“日志”区域，包含以下元素：

### 1. 日志摘要信息

显示：

- 当前日志目录
- 当前会话文件名
- 当前完整日志大小
- 当前错误日志大小

### 2. 操作按钮

Windows 与 Android 共用按钮语义，但平台行为允许不同：

- `刷新日志`
  - 重新读取 `latest.log`

- `查看完整日志`
  - 在面板文本区域显示 `latest.log` 末尾一段

- `查看错误日志`
  - 在面板文本区域显示 `latest-error.log`

- `复制日志`
  - 把当前文本区域内容复制到剪贴板

- `清空日志`
  - 删除历史日志并重新创建当前会话文件

- `打开日志目录`
  - Windows：尝试打开目录
  - Android：不显示或替换为“显示日志路径”

### 3. 文本区域

一个只读多行文本框，用于展示：

- `latest.log` 最后若干 KB
- 或 `latest-error.log`

建议默认显示：

- 最近 200 行或最近 12 KB

### 4. 平台行为差异

Windows：

- 显示全部按钮
- `打开日志目录` 可用

Android：

- 不提供“打开日志目录”
- 提供：
  - `复制日志`
  - `查看错误日志`
  - `显示日志路径`

## 推荐接入点

第一阶段建议优先接入以下模块：

- `AppRoot`
  - 启动、页面切换、奖励发放、救助中心刷新

- `GameScene`
  - 开关卡、结算、失败、调试面板操作

- `BoardController`
  - 牌局加载、规则档案切换、提示、死局检测、匹配失败原因

- `PlayerProgressStore`
  - 存档读取、存档保存、回退默认值

- `OfflineLevelJsonLoader`
  - 关卡目录读取与单关 JSON 解析

- `PetCatalog`
  - 宠物表加载失败与回退

## 与现有代码的迁移方式

不建议一次性全量替换所有 `GD.Print`。

建议采用三步迁移：

### 第一步

新增日志系统并在 `AppRoot` 中初始化。

### 第二步

替换关键路径日志：

- `AppRoot`
- `GameScene`
- `BoardController`
- `PlayerProgressStore`
- `OfflineLevelJsonLoader`

### 第三步

把其他零散 `GD.Print / GD.Push...` 逐步收敛到统一入口。

## 实现边界与限制

### 1. 无法完全覆盖“引擎未进入 C# 前”的闪退

如果崩溃发生在：

- Godot 原生层
- C# 程序集加载之前
- 导出包缺失运行时依赖

那么项目日志不一定能写出来。

### 2. Windows 程序目录未必总可写

如果用户把程序放入受保护目录，日志目录必须回退。

### 3. Android 无法像 Windows 一样直接在安装目录旁边看到 `logs/`

Android 必须依赖：

- `user://logs`
- 调试面板
- `logcat`

## 后续可选增强

在第一阶段稳定后，可以考虑增强以下能力：

- 导出日志为 zip
- 调试面板中显示最近多次会话列表
- 一键只复制错误摘要
- 启动时自动记录设备信息与分辨率
- 将引擎级 `--log-file` 与项目日志统一汇总

## 推荐实施顺序

1. 新增 `RuntimeLog` 与日志目录解析逻辑
2. 在 `AppRoot._EnterTree()` 中完成初始化
3. 注册全局未处理异常钩子
4. 接入 `AppRoot / GameScene / BoardController / PlayerProgressStore`
5. 在共享调试面板中加入日志区域
6. Android 上补“复制日志”和“显示日志路径”功能
7. 再评估是否需要 Windows 启动包装层

## 验收标准

完成第一阶段后，应至少满足以下标准：

- Windows 导出包启动后，在可执行文件目录下优先出现 `logs/`
- 若同目录不可写，自动回退到 `user://logs/`
- Android 运行后能在 `user://logs/` 写出会话日志
- 调试面板中可以查看最近日志摘要
- 至少一个未处理异常能被写入 `Fatal` 日志
- `AppRoot / GameScene / BoardController / PlayerProgressStore` 的关键流程有统一格式日志

## 结论

本项目的日志系统应采用“项目级文件日志 + 平台差异化落点 + 调试面板统一入口”的方案：

- Windows 优先写到程序目录旁的 `logs/`
- Android 统一写到 `user://logs/` 并同步到 `logcat`
- 调试面板承担跨平台查看、复制、刷新与清空日志的统一入口
- 先解决项目逻辑层日志问题，再决定是否补引擎级启动日志

这套方案足以支持当前阶段的发布排错与真机调试，也不会把实现复杂度拉得过高。
