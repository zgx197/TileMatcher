# 文档导航约定

## 目标

本约定用于明确 `docs/` 目录中哪些文档是当前有效设计，哪些文档是研发记录，哪些文档只是历史归档，避免后续协作时误把旧方案继续当作主方案使用。

## 目录分层

- `docs/` 根目录只放当前仍然有效、仍然会继续维护的主文档
- `docs/研发记录/` 只放研发过程中的问题记录、演进记录和排查经验
- `docs/归档/` 只放历史方案、废弃方案、阶段性实施文档和被替代的旧说明
- 任何不再作为实现依据的旧设计，都必须移入 `docs/归档/`，不应继续留在 `docs/` 根目录

## 文档状态定义

文档默认分为三类：

- 当前文档
  - 表示当前阶段仍然有效
  - 可以继续修改
  - 可以直接作为实现、重构、讨论和评审依据
- 研发记录
  - 表示真实发生过的问题与演进过程
  - 用于解释“为什么变成这样”
  - 不能替代当前主设计文档
- 归档文档
  - 表示只用于追踪历史背景
  - 不应继续作为当前实现依据
  - 如需引用，必须明确说明“仅作历史参考”

## 使用规则

- 新开一个实现话题前，优先阅读 `docs/README.md` 中“当前主文档”部分
- 如果某份文档在 `docs/归档/` 中，默认不能直接拿来指导当前实现
- 如果当前方案替代了旧方案，旧方案文档必须补充“已归档 / 被谁替代”的说明
- 如果新方案已经成为主方案，必须在 `README.md`、`AGENTS.md`、`docs/README.md` 中同步更新入口
- 如果一份文档只描述某一轮实施拆解、阶段性修复或临时方案，不应长期留在 `docs/` 根目录

## 命名规则

- `…设计.md`
  - 用于长期有效的产品、系统、页面、日志、规则类主文档
- `…说明.md`
  - 用于构建、发布、环境、脚本、维护方式等操作型主文档
- `…记录.md`
  - 只放在 `docs/研发记录/` 中，表示真实问题线和演进过程
- `…草案.md` 或 `…方案.md`
  - 只用于尚未定稿的临时文档
  - 一旦成为正式主方案，应改名为 `…设计.md` 或移入归档
- 不再建议继续使用过于泛化、容易与新方案混淆的名字作为主入口，例如“总结文档”“脚本说明合集”这类名称
- 归档文档文件名应尽量带出历史属性或阶段属性，避免与当前主文档重名

## 迁移规则

当某份文档从当前文档转为历史文档时，按以下步骤处理：

1. 将文件移动到 `docs/归档/`
2. 在归档文档开头说明它为什么被归档、被哪份文档替代
3. 修正 `README.md`、`AGENTS.md`、`docs/README.md` 内的引用
4. 检查其他设计文档中的交叉引用，避免仍然指向旧位置

- 当前产品方向：
  - `docs/产品方向与外围循环设计.md`
- 当前页面与流程：
  - `docs/游戏外围流程与页面架构设计.md`

  - `docs/堆叠框架与网格规则设计.md`

- 当前构建与发布：
  - `docs/构建与发布说明.md`
- 当前画面分析：
  - `docs/画面风格与渲染分析.md`
- 当前文档导航入口：
  - `docs/README.md`
- 历史归档方案：
  - `docs/归档/第一代网格坐标系统设计.md`

## 维护要求

- 只要设计方向发生切换，就要同步更新本文件
- 如果只是补充细节而没有改变主方案，不需要新增归档
- 如果旧文档仍然有保留价值，应归档，而不是删除
