# 代码架构与配置说明

## 文档目标

本文档用于从“代码结构”和“配置流转”两个角度，说明当前 TileMatcher 工程的整体实现方式。

它不是替代详细设计文档，而是作为一个更接近代码落地状态的总览文档，帮助后续开发者或 AI agent 在进入仓库后快速理解：

- 当前哪些层是核心运行时逻辑
- 当前哪些内容已经资源化配置
- 配置如何进入运行时
- 一次布局生成和渲染是怎样流转的
- 哪些边界条件是当前实现明确禁止破坏的

## 当前架构总览

当前代码大体可以分为六层：

1. 数据层
2. 网格与几何层
3. 布局规则与校验层
4. 配置资源层
5. 棋盘控制层
6. 场景 UI 与视图层

它们之间的关系可以概括为：

- 配置资源层负责提供可编辑的配置数据
- 配置在运行时被转换成纯逻辑规则对象
- 规则驱动布局生成器或固定原型工厂输出布局数据
- 布局数据经过校验器检查
- 棋盘控制层把布局数据实例化成视图节点
- 场景 UI 层负责响应用户输入和调试切换

## 目录与职责

### `godot/scripts/data/`

这层负责纯运行时数据定义。

当前关键文件：

- `TileData.cs`
  - 表示单张麻将的数据
  - 采用“左上角锚点 + 矩形 footprint”表达
- `TileShape.cs`
  - 表示牌在逻辑网格中的形状
  - 当前只支持矩形
- `LevelLayout.cs`
  - 表示一整份布局结果

这层不应依赖场景节点，也不应直接依赖 Inspector 资源。

### `godot/scripts/grid/`

这层负责逻辑网格和世界空间之间的映射，以及几何判定。

当前关键文件：

- `GridConfig.cs`
  - 维护视觉尺寸与逻辑尺寸之间的基础参数
- `GridMath.cs`
  - 负责 footprint、投影重叠、完整底面覆盖、世界包围盒等计算
- `GridPosition.cs`
  - 预留的三维逻辑坐标值类型

这里是第二代通用堆叠框架的几何核心。

### `godot/scripts/layout/`

这层负责布局规则、布局校验、固定原型和随机生成。

当前关键文件：

- `LayoutRules.cs`
  - 运行时纯规则对象
- `LayerOffsetMode.cs`
  - 定义上层相对下层的偏移模式
- `LayoutValidationResult.cs`
  - 布局校验结果
- `LayoutValidator.cs`
  - 统一校验布局是否合法
- `PrototypeLayoutFactory.cs`
  - 生成固定原型布局
- `RandomStackLayoutGenerator.cs`
  - 根据当前规则生成随机布局

这层不负责 UI，也不直接负责 Resource 编辑器表现。

### `godot/scripts/config/`

这层是当前资源化配置入口，对应 Unity 里常见的 `ScriptableObject` 思路。

当前关键文件：

- `TileShapeConfig.cs`
  - 牌形资源
- `LayoutRuleConfig.cs`
  - 规则资源
- `LayoutProfileConfig.cs`
  - 规则档案资源
- `LayoutProfileCatalog.cs`
  - 档案目录资源

对应的资源文件在：

- `godot/configs/shapes/`
- `godot/configs/layout_rules/`
- `godot/configs/layout_profiles/`

### `godot/scripts/board/`

这层负责把布局逻辑结果接入实际棋盘。

当前关键文件：

- `BoardController.cs`
  - 当前游戏页里最核心的运行时控制器
  - 负责选择档案、生成布局、校验布局、实例化视图节点、控制显示层过滤

### `godot/scripts/game/` 与 `godot/scripts/tile/`

这层负责游戏页 UI 控制和牌视图。

当前关键文件：

- `GameScene.cs`
  - 负责调试 UI、按钮交互、拖动浮窗、调试状态同步
- `TileView.cs`
  - 负责单张牌的可视化绘制

## 当前核心数据模型

### 1. 牌的逻辑坐标

当前采用：

- `GX`
- `GY`
- `GZ`

其中：

- `GX / GY` 表示牌 footprint 左上角所在的逻辑网格坐标
- `GZ` 表示层级

### 2. 牌的逻辑形状

当前标准麻将逻辑尺寸为：

- `4 x 6`

注意：

- 这不是像素尺寸
- 这是逻辑微单元尺寸
- 它的作用是提高几何表达能力，让“两支撑 / 四支撑”成为结果，而不是底层硬编码规则

### 3. 布局结果

一份 `LevelLayout` 包含：

- `LevelId`
- `Tiles`

每张 `TileData` 都包含：

- 牌 id
- 类型
- `(GX, GY, GZ)`
- `Shape`
- 运行时状态位

## 当前配置系统

## 为什么要资源化

当前项目已经从早期静态代码配置，迁移到 Godot `Resource` 驱动。

这样做的主要原因是：

- 配置可以直接在 Inspector 中编辑
- 不需要每次调参数都改 C# 代码
- 后续更适合让 AI agent、关卡设计和调试工具共享同一套配置入口
- 可以逐步替代早期 `static` 配置类

## 当前配置层级

### `TileShapeConfig`

负责定义牌形：

- 宽度
- 高度

### `LayoutRuleConfig`

负责定义布局规则：

- 层数范围
- 底层最少牌数
- 是否要求完整底面覆盖
- 是否要求上层牌数严格收缩
- 底层随机尺寸范围
- 底层挖洞概率
- 生成重试次数
- 底层铺牌步长
- 上层偏移模式
- 引用的牌形资源

### `LayoutProfileConfig`

负责把“名字 + id + 规则”打包成一份可切换档案。

### `LayoutProfileCatalog`

负责维护：

- 默认档案 id
- 全部可用档案列表

## 当前默认资源入口

当前默认档案目录资源是：

- `godot/configs/layout_profiles/default_catalog.tres`

当前场景中：

- `GameScene.tscn` 里的 `BoardController` 已显式引用这份目录资源

同时 `BoardController` 仍保留默认路径回退：

- `res://configs/layout_profiles/default_catalog.tres`

也就是说：

- 场景显式绑定优先
- 未绑定时使用默认路径兜底

## 配置如何进入运行时

当前数据流是：

1. `LayoutProfileCatalog` 提供当前全部档案
2. `BoardController` 选择一个 `LayoutProfileConfig`
3. `LayoutProfileConfig` 转换成 `LayoutRules`
4. `LayoutRules` 被传给：
   - `PrototypeLayoutFactory`
   - `RandomStackLayoutGenerator`
   - `LayoutValidator`

这里有一个很重要的架构约束：

- Godot `Resource` 只负责“编辑器数据层”
- `LayoutRules` 负责“运行时逻辑层”

不要让布局生成器和校验器直接依赖 Godot Resource 对象。

## 当前布局生成与渲染流程

一次随机生成的大致流程如下：

1. `GameScene` 响应按钮点击
2. `GameScene` 调用 `BoardController.GenerateRandomBoard()`
3. `BoardController` 使用当前 `LayoutRules` 调用 `RandomStackLayoutGenerator`
4. 生成器输出 `LevelLayout`
5. `BoardController` 用 `LayoutValidator` 做统一校验
6. `BoardController` 清理旧的 `TileView`
7. `BoardController` 遍历 `LevelLayout.Tiles` 实例化新的 `TileView`
8. `GridMath.GridToWorld()` 把逻辑坐标换成世界坐标
9. `BoardController` 发出 `BoardGenerated` 信号
10. `GameScene` 更新调试文字与层过滤 UI

固定原型流程与此类似，只是布局来源换成：

- `PrototypeLayoutFactory.CreateSingleLevelPrototype()`

## 当前关键几何规则

### 1. 同层绝不重叠

这是当前硬约束。

同层牌必须：

- 对齐铺放
- 不允许部分覆盖
- 不允许互相挤压

### 2. 相邻层不允许完全重合

当前业务目标中，不允许出现：

- 上层一张牌完全盖住下层一张牌

因此校验器会直接把这种情况视为非法布局。

### 3. 上层必须获得完整底面覆盖

第二代框架采用：

- 全底面都必须支撑

具体实现不是用“二支撑 / 四支撑”去硬编码，而是：

- 逐个微单元检查该牌底面投影
- 看下一层 footprint union 是否完整覆盖

### 4. 上层偏移模式决定支撑观感

当前支持：

- `None`
- `HalfX`
- `HalfY`
- `HalfXY`

其中：

- `HalfX` 更容易形成左右两牌支撑
- `HalfY` 更容易形成上下两牌支撑
- `HalfXY` 更容易形成四牌联合支撑

## 当前固定原型的作用

`PrototypeLayoutFactory` 的目标不是生成正式关卡，而是：

- 提供一份稳定、可重复的调试布局
- 方便人工观察偏移模式、支撑效果和层级显示

它当前使用：

- 逐层累计偏移

而不是：

- 每层相对世界原点重新偏移

这是为了避免高层悬空或层间脱节。

## 当前随机生成器的特点与限制

`RandomStackLayoutGenerator` 当前采用：

- 自底向上生成
- 每层先枚举合法候选点
- 再挑选互不重叠的一组作为上一层
- 外层多次尝试直到校验通过

它的优点是：

- 实现清晰
- 容易调试
- 和当前几何校验模型一致

它当前的限制是：

- 还没有保证“牌型成对分布”
- 还没有保证“可解性”
- 更像布局拓扑生成器，而不是完整关卡生成器

这属于当前阶段的明确非目标，不应误判为 bug。

## 当前棋盘控制器的边界

`BoardController` 负责：

- 规则档案切换
- 布局生成与应用
- 棋盘节点重建
- 层过滤显示
- 规则摘要输出

`BoardController` 不负责：

- 首页或结算页
- 拖拽交互细节
- 完整匹配玩法
- 关卡可解性分析

## 当前游戏页控制器的边界

`GameScene` 负责：

- 调试面板 UI
- DEBUG 按钮拖拽与显隐
- 随机生成 / 固定原型按钮
- profile 下拉切换
- 层过滤滑杆
- 轻量视觉反馈

`GameScene` 不负责：

- 布局几何计算
- 支撑判定
- 规则数据存储

## 对后续开发者 / AI agent 的重要提醒

### 不要回退到第一代 `2 x 2` 思路

当前代码已经落到第二代通用框架：

- 标准牌为 `4 x 6`
- 完整底面覆盖是核心规则
- 支撑数量是结果，不是底层硬编码

因此不要再把：

- 半格错位
- 四点支撑
- 固定 `2 x 2`

这些当成当前主实现基础。

### 不要让 Resource 直接渗入几何核心

配置资源层和运行时逻辑层之间，当前明确有一层转换：

- `LayoutRuleConfig -> LayoutRules`

请继续保持这层分离。

### 不要默认“能显示”就等于“合法”

当前 `BoardController` 在调试阶段即使校验失败，也会继续渲染布局。

这样做是为了方便观察错误布局，但也意味着：

- 屏幕上能看到棋盘
- 不代表这份布局已经合法

调试时要同时看：

- Inspector 配置
- 调试摘要
- 输出日志

### 不要把当前随机生成器当成正式关卡生成器

当前它只解决：

- 堆叠拓扑
- 支撑关系
- 基本层级结构

它还没有解决：

- 可解性
- 正式牌组分配
- 关卡难度控制
