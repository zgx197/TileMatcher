# 代码架构与配置说明

## 文档目标

本文档用于从“代码结构”和“配置流转”两个角度，说明当前 TileMatcher 工程的落地状态。

它不是替代详细设计文档，而是一份更贴近代码的总览，帮助开发者或 AI agent 快速理解：

- 当前代码分层如何组织
- 哪些能力已经资源化配置
- 关卡是如何进入游戏页的
- 随机布局为什么现在能够保证至少存在一条可通关路径

## 当前架构总览

当前代码可以分成七层：

1. 数据层
2. 网格与几何层
3. 布局生成与校验层
4. 配置资源层
5. 棋盘运行时控制层
6. 游戏页与外围流程层
7. 研发记录与文档层

它们之间的关系大致如下：

- 配置资源层提供可编辑的规则与关卡数据
- 配置资源在运行时转换为纯 C# 规则对象
- 布局生成层根据规则生成或验证布局
- 棋盘控制层将布局转成 `TileView` 并维护交互状态
- 游戏页负责承接牌桌并发出通关事件
- 外围流程层负责主页、结算页和下一关切换

## 目录与职责

### `godot/scripts/data/`

运行时纯数据结构：

- `TileData.cs`
- `TileShape.cs`
- `LevelLayout.cs`

职责：

- 描述单张牌、牌形和整份布局
- 不依赖 Godot 场景树
- 作为布局生成、校验和棋盘控制的共同数据基础

### `godot/scripts/grid/`

几何与坐标换算层：

- `GridConfig.cs`
- `GridMath.cs`
- `GridPosition.cs`

职责：

- 负责逻辑网格到世界坐标的换算
- 处理 footprint、层间偏移、重叠判断、完整底面覆盖、边界计算
- 为通用堆叠框架提供几何基础

### `godot/scripts/layout/`

布局生成与校验层：

- `LayoutRules.cs`
- `LayerOffsetMode.cs`
- `LayoutValidator.cs`
- `LayoutValidationResult.cs`
- `PrototypeLayoutFactory.cs`
- `RandomStackLayoutGenerator.cs`
- `TileTypeDeckBuilder.cs`

职责：

- 定义运行时规则对象
- 生成固定原型布局
- 生成随机堆叠布局
- 校验布局是否合法
- 为几何布局分配成对牌面

其中当前最重要的变化是：

- `RandomStackLayoutGenerator` 不再只是“随机摆出一份看起来像堆叠的布局”
- 它现在会在纯几何布局上搜索一条完整移除顺序
- 只有找到完整顺序后，才会按该顺序为牌面成对赋值

这使得“可解性”成为生成器本身的输出约束，而不是运行后的补丁。

### `godot/scripts/config/`

资源化配置层，对应 Unity 中常见的 `ScriptableObject` 思路：

- `LayoutRuleConfig.cs`
- `LayoutProfileConfig.cs`
- `LayoutProfileCatalog.cs`
- `TileShapeConfig.cs`
- `MatchFeedbackConfig.cs`
- `LevelConfig.cs`
- `LevelCatalog.cs`
- `LevelLayoutSourceMode.cs`

对应资源目录：

- `godot/configs/layout_rules/`
- `godot/configs/layout_profiles/`
- `godot/configs/shapes/`
- `godot/configs/effects/`
- `godot/configs/levels/`

职责：

- 把规则、牌形、表现参数、关卡目录都放到 Inspector 可编辑资源中
- 让调参、扩关和 AI 理解都不必依赖硬编码

### `godot/scripts/board/`

棋盘运行时主控制层：

- `BoardController.cs`
- `TileInteractionRules.cs`
- 其他交互状态与阻塞判定相关脚本

职责：

- 加载或生成布局
- 重建棋盘节点
- 计算每张牌当前是否可参与消除
- 维护点击、拖拽、接触容差与配对判定
- 发出局内调试日志、顶部提示和状态变化事件
- 控制成功消除反馈与失败反馈

`TileInteractionRules` 的价值在于把“牌能否参与配对”的规则统一起来，避免点击逻辑和拖拽逻辑各自维护一套判定。

### `godot/scripts/game/`

游戏页表现与编排层：

- `GameScene.cs`

职责：

- 作为正式游戏页脚本
- 承接 `BoardController`
- 连接顶部状态栏、返回主页按钮、调试浮窗
- 根据 `LevelConfig` 启动指定关卡
- 在牌桌清空后发出 `LevelCompleted`

### `godot/scripts/app/`、`godot/scripts/home/`、`godot/scripts/result/`

外围流程层：

- `AppRoot.cs`
- `LevelCompleteResult.cs`
- `DailyRewardSummary.cs`
- `PlayerProgressData.cs`
- `PlayerProgressStore.cs`
- `HomePage.cs`
- `BootLoadingPage.cs`
- `LevelCompletePage.cs`
- `DailyRewardPage.cs`

职责：

- 负责页面流转
- 负责启动页与奖励页串联
- 负责玩家外围进度持久化
- 将关卡配置转成主页/结算页可展示摘要
- 维护“当前应进入哪一关”的最小流程状态

## 当前配置系统

### 1. 规则配置

规则 profile 由以下结构组织：

- `LayoutRuleConfig`
- `LayoutProfileConfig`
- `LayoutProfileCatalog`

运行时流程：

1. `BoardController` 读取 `LayoutProfileCatalog`
2. 用户或关卡选择一个 profile
3. `LayoutProfileConfig` 转换为 `LayoutRules`
4. `LayoutRules` 交给布局生成器、校验器和交互规则使用

边界：

- Godot `Resource` 负责编辑器数据
- `LayoutRules` 负责运行时逻辑

### 2. 关卡配置

关卡由以下资源驱动：

- `LevelConfig`
- `LevelCatalog`
- `LevelLayoutSourceMode`

运行时流程：

1. `AppRoot` 读取 `LevelCatalog`
2. 主页显示当前关卡标题与摘要
3. `GameScene.StartLevel(levelNumber)` 读取对应 `LevelConfig`
4. `GameScene` 根据 `LevelConfig` 切换 profile 并加载布局来源

当前单关已经支持：

- 固定原型牌桌
- 固定种子随机牌桌
- 动态随机牌桌

### 3. 表现配置

成功消除的表现参数已经抽到：

- `MatchFeedbackConfig`
- `godot/configs/effects/default_match_feedback.tres`

当前集中配置的内容包括：

- 接触容差
- 三段式碰撞动画时长
- 预备位间距和抬升高度
- 碰撞白闪
- 分数字号、描边、弹跳和上浮

这意味着后续调手感主要应调整配置，而不是继续把表现数字散落进 `BoardController`。

## 当前游戏启动链路

正式关卡启动流程如下：

1. `project.godot` 主场景进入 `AppRoot.tscn`
2. `AppRoot` 显示 `HomePage`
3. 用户点击开始
4. `AppRoot` 打开 `GameScene`
5. `GameScene.StartLevel(levelNumber)`
6. `GameScene` 读取 `LevelConfig`
7. `BoardController` 切换对应规则 profile
8. 根据 `LevelLayoutSourceMode` 选择：
   - `LoadPrototype`
   - `GenerateRandomBoard`
9. 布局应用到棋盘并开始局内交互
10. 牌桌清空后 `GameScene` 发出 `LevelCompleted`
11. `AppRoot` 打开 `LevelCompletePage`
12. 点击继续后直接进入下一关

## 当前随机布局“可解性”设计

### 核心思路

当前随机生成不直接随机牌面，而是分两步：

1. 先生成一份合法的纯几何堆叠布局
2. 再在该布局上搜索一条完整移除顺序，并按顺序为每一对牌赋相同牌面

这样得到的结果不是“看运气是否可解”，而是“生成结果至少存在一条通关路径”。

### 为什么这样做

如果先随机牌面，再去检查能不能解，会遇到两个问题：

- 可解率不稳定，重试成本高
- 很容易出现后期某一关无解的体验问题

当前方案把“可解”作为生成器内部约束，工程上更可靠。

### 当前边界

当前只保证：

- 至少存在一条完整可移除顺序

当前还不保证：

- 多解丰富性
- 难度曲线稳定
- 一定不会出现中局选择收窄的体验问题

这属于后续可继续演进的关卡设计层问题，而不是当前骨架的缺失。

## 当前外围流程设计

外层流程现在已经落地：

- `AppRoot`
- `BootLoadingPage`
- `HomePage`
- `GameScene`
- `LevelCompletePage`
- `DailyRewardPage`

主页会显示：

- 当前将进入的关卡名
- 规则摘要
- 玩家进度摘要与叶子数量

结算页会显示：

- 本关结果

若奖励触发，则“继续”会先进入奖励页，再进入下一关。

## 当前日志与调试原则

当前日志重点覆盖这些关键节点：

- 规则切换
- 布局加载与生成
- 点击与拖拽链路
- 配对成功与失败原因
- 页面级关卡完成

明确不在类似 `_Process` 或每帧更新里持续刷日志，以避免 Godot 输出窗口被噪声淹没。

## 近期离线关卡链路更新

当前代码库已经把“离线导出正式关卡 -> 同步到 Godot -> 运行时按目录索引消费”这条最小链路接通，运行时默认不再依赖单局调试随机生成。

### 离线侧当前默认产物

- `tools/TileMatcher.Offline/batch-config.sample.json`
  - 当前默认批次规模为 `candidateCount = 120`
  - 当前默认正式导出上限为 `maxAcceptedLevels = 20`
- 说明：`artifacts/mahjong-mvp/` 目录名仍沿用早期历史命名，但当前实际承载的是正式配对关卡导出产物
- `artifacts/mahjong-mvp/runtime-levels/`
  - 由离线工具导出运行时正式关卡目录
- `artifacts/mahjong-mvp/runtime-levels/level-catalog.json`
  - 当前批次的正式关卡目录索引
- `artifacts/mahjong-mvp/runtime-levels/levels/level_001.json` 到 `level_020.json`
  - 当前已导出的前 20 关正式关卡文件

### Godot 侧当前消费方式

- `godot/generated/runtime-levels/`
  - 作为运行时默认消费的生成目录
- `godot/configs/levels/offline_catalog_template.tres`
  - 作为目录索引模板资源
- `godot/configs/levels/default_levels.tres`
  - 当前默认只维护离线目录模板，而不是手工维护大量单关 `.tres`
- `LevelLayoutSourceMode`
  - 已新增 `OfflineJson`
- `LevelConfig`
  - 已支持单关 JSON 路径
  - 已支持目录索引 JSON 路径
  - 已支持模板化目录解析
- `LevelCatalog`
  - 已支持基于目录模板为指定关卡号生成解析后的关卡配置
- `BoardController`
  - 已支持读取单关离线 JSON
  - 已支持通过 `level-catalog.json` + `levels/*.json` 加载正式关卡

### 当前默认运行约定

- 离线工具负责生成、评估、筛选、导出正式关卡数据
- 同步脚本负责把离线导出结果复制到 `godot/generated/runtime-levels/`
- Godot 运行时只负责根据关卡号消费目录索引和关卡 JSON
- 当前默认正式关卡数据已同步为前 20 关

### 调试面板来源标识

为了避免首页文案造成误解，当前只在调试面板明确展示牌局来源：

- `离线正式关卡`
- `调试随机关卡`
- `原型关卡`

这样可以在不干扰首页认知的前提下，快速确认当前实际游玩内容来自哪条链路。

## 当前局内辅助能力

游戏页当前已经新增两类局内辅助按钮，均放在 `GameScene` 底部操作区：

- `重新开始`
  - 重新加载当前关卡的同一份正式数据
  - 不重新随机生成牌局
- `提示`
  - 在当前局面中找出一对可以直接碰撞消除的牌块
  - 对这对牌块播放高亮反馈

这两类辅助能力当前都采用“每关固定次数”的设计：

- 每关最多 `3` 次重新开始
- 每关最多 `3` 次提示

### 当前实现职责

- `GameScene`
  - 负责按钮点击、剩余次数显示和玩家提示文案
- `BoardController`
  - 负责在当前局面中查找一对可直接消除的牌块
- `TileView`
  - 负责把提示结果翻译成牌面高亮反馈
- `AppRoot`
  - 负责把游戏页和外围玩家进度对象绑定起来
- `PlayerProgressData`
  - 负责持久化每关的辅助资源使用情况

### 当前存档约定

玩家存档现在除了外围进度，还会额外保存：

- 每关已使用的重开次数
- 每关已使用的提示次数

也就是说，同一关中消耗过的辅助次数，在重新进入该关时会保持一致；进入新关卡时则默认从未使用状态开始。

### Debug 面板新增局内工具

当前 debug 面板除了展示来源信息，也承担开发期局内回归工具：

- `跳到该关`
- `重置当前关卡辅助次数`
- `自动消除一对`
- `重置账号数据`

其中：

- `跳到该关` 通过 `GameScene -> AppRoot -> ShowGamePage(levelNumber)` 这条外围链路生效
- `重置当前关卡辅助次数` 只修改当前关卡在 `PlayerProgressData.LevelAssistUsageByLevel` 中的计数
- `自动消除一对` 复用 `BoardController` 当前可提示配对搜索逻辑，并继续走正式消除动画与计分流程

这样调试能力可以集中留在 debug 面板中，同时保持正式玩家流程和开发期能力的边界清晰。
