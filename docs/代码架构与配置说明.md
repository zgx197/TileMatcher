# 代码架构与配置说明

## 2026-04-04 补充：交互规则模型重构

当前已经不再让点击消除和拖拽消除各自维护一套合法性判定，而是新增统一规则层：

- `godot/scripts/board/TileInteractionRules.cs`

这层规则的职责分为两部分：

- `Evaluate(tile, activeTiles)`
  - 评估单张牌当前是否被上层压住、是否被左右夹住、是否被上下夹住
  - 产出 `TileInteractionState`
- `TryValidateMatchPair(first, second, activeTiles, out failureReason)`
  - 统一判断两张牌当前是否允许构成一次合法配对
  - 点击和拖拽都必须通过这里

本轮重构后的关键边界是：

- “鼠标点到了谁 / 拖拽碰到了谁”属于输入和几何层
- “这张牌能不能参与消除”属于业务规则层

因此当前拖拽逻辑虽然仍然允许跨层命中候选目标，但不会再因为“碰到了同牌面”就直接消除，
而是必须继续满足统一规则：

- 两张牌牌面相同
- 两张牌都未移除
- 两张牌当前都处于可参与消除状态

这次重构的直接目标，是避免再次出现：

- 点击规则严格
- 拖拽规则放宽
- 同一张被锁住的牌在不同输入模式下行为不一致

## 2026-04-04 补充：消除反馈配置层

当前已经把“配对成功后的表现参数”从 `BoardController` 的硬编码常量中抽离，新增为独立资源：

- `godot/scripts/config/MatchFeedbackConfig.cs`
- `godot/configs/effects/default_match_feedback.tres`

这份资源当前负责：

- 拖拽接触容差
- 三段式消除动画时长
- 预备位展开距离与抬升高度
- 碰撞瞬间的白色闪光 / 小范围爆点
- 单次消除分值
- 分数提示的字号、描边、透明度、弹跳倍率和上浮距离

设计边界如下：

- `LayoutRules` 决定“能不能消除”，属于业务与几何规则
- `MatchFeedbackConfig` 决定“消除时看起来像什么”，属于表现层配置

当前场景绑定关系：

- `godot/scenes/game/GameScene.tscn`
  - `BoardController.ProfileCatalog -> res://configs/layout_profiles/default_catalog.tres`
  - `BoardController.MatchFeedbackConfig -> res://configs/effects/default_match_feedback.tres`

如果场景没有显式绑定 `MatchFeedbackConfig`，`BoardController` 会自动回退加载默认资源；
如果默认资源也缺失，则会创建一份运行时默认值，保证拖拽和消除主流程不会因为表现资源缺失而直接中断。

## 当前架构总览

当前代码可以粗分为六层：

1. 数据层
2. 网格与几何层
3. 布局规则与校验层
4. 配置资源层
5. 棋盘控制层
6. 场景 UI 与牌视图层

它们之间的关系可以概括为：

- 配置资源层提供可编辑的规则数据
- 配置数据在运行时转换为纯 C# 的 `LayoutRules`
- `LayoutRules` 驱动固定原型和随机布局生成
- 布局结果先经统一校验，再交给棋盘控制器
- 棋盘控制器实例化 `TileView` 并管理交互状态
- `GameScene` 负责调试 UI、状态显示和面向用户的反馈

## 目录与职责

### `godot/scripts/data/`

纯运行时数据定义：

- `TileData.cs`
  - 单张麻将的运行时数据
  - 当前使用 `(GX, GY, GZ)` + `Shape` 表示逻辑位置和逻辑形状
- `TileShape.cs`
  - 牌在逻辑网格中的矩形 footprint
- `LevelLayout.cs`
  - 一整份布局结果容器

这一层不应直接依赖 Godot 场景节点和 Inspector 资源。

### `godot/scripts/grid/`

几何与坐标换算层：

- `GridConfig.cs`
  - 定义视觉尺寸、逻辑尺寸和层间视觉偏移
- `GridMath.cs`
  - 处理 footprint、投影重叠、完整底面覆盖、世界包围盒、同层邻接等计算
- `GridPosition.cs`
  - 三维逻辑坐标值对象

这一层是当前第二代通用堆叠框架的几何核心。

### `godot/scripts/layout/`

布局规则与生成校验层：

- `LayoutRules.cs`
  - 运行时纯规则对象
- `LayerOffsetMode.cs`
  - 上层相对下层的偏移模式
- `LayoutValidationResult.cs`
  - 布局校验结果
- `LayoutValidator.cs`
  - 统一校验布局是否合法
- `PrototypeLayoutFactory.cs`
  - 生成固定原型布局
- `RandomStackLayoutGenerator.cs`
  - 按当前规则生成随机堆叠布局

这一层不直接负责 UI，也不应该直接耦合 Godot `Resource`。

### `godot/scripts/config/`

资源化配置入口，对应 Unity 中常见的 `ScriptableObject` 思路：

- `TileShapeConfig.cs`
- `LayoutRuleConfig.cs`
- `LayoutProfileConfig.cs`
- `LayoutProfileCatalog.cs`

对应资源位于：

- `godot/configs/shapes/`
- `godot/configs/layout_rules/`
- `godot/configs/layout_profiles/`

### `godot/scripts/board/`

棋盘运行时主控制层：

- `BoardController.cs`

当前主要职责：

- 选择规则档案
- 生成或加载布局
- 校验布局并重建棋盘
- 计算每张牌是否可移动
- 管理点击选中、点击配对和最小拖拽消除
- 输出关键调试日志
- 控制层过滤显示

### `godot/scripts/game/` 与 `godot/scripts/tile/`

表现与交互显示层：

- `GameScene.cs`
  - 调试 UI、按钮事件、状态栏同步、调试面板拖动
- `TileView.cs`
  - 单张牌的绘制、可动状态视觉、选中状态视觉、命中矩形

## 当前核心数据模型

### 1. 逻辑坐标

当前使用：

- `GX`
- `GY`
- `GZ`

其中：

- `GX / GY` 表示牌的逻辑 footprint 左上角
- `GZ` 表示牌所在层级

### 2. 逻辑形状

当前标准麻将 footprint 为：

- `4 x 6`

注意：

- 这是逻辑网格单位，不是像素
- 它的作用是提高几何表达能力
- “两牌支撑 / 四牌支撑”是几何结果，不是底层硬编码规则

### 3. 运行时状态位

当前 `TileData` 上已有的关键状态位：

- `Removed`
  - 是否已从当前牌桌移除
- `Movable`
  - 当前是否允许交互移动

这些状态由 `BoardController` 在布局应用后和每次消除后刷新。

## 当前配置系统

### 为什么做资源化

项目已经从早期静态代码配置，迁移到 Godot `Resource` 驱动，主要原因是：

- 可直接在 Inspector 中调整规则
- 减少为调参数而频繁改 C# 代码
- 更适合后续关卡设计、规则 profile 切换和 AI agent 读取

### 配置如何进入运行时

当前流转方式：

1. `LayoutProfileCatalog` 提供全部档案
2. `BoardController` 选择一个 `LayoutProfileConfig`
3. `LayoutProfileConfig` 转换为 `LayoutRules`
4. `LayoutRules` 被传给：
   - `PrototypeLayoutFactory`
   - `RandomStackLayoutGenerator`
   - `LayoutValidator`

这里有一个明确约束：

- Godot `Resource` 只负责编辑器数据层
- `LayoutRules` 负责运行时逻辑层

不要让生成器和校验器直接依赖 Godot 资源对象。

## 布局生成与渲染流程

一次随机生成的大致流程：

1. `GameScene` 响应“随机生成”按钮
2. `GameScene` 调用 `BoardController.GenerateRandomBoard()`
3. `BoardController` 使用当前 `LayoutRules` 调用 `RandomStackLayoutGenerator`
4. 生成器输出 `LevelLayout`
5. `BoardController` 用 `LayoutValidator` 做统一校验
6. `BoardController` 清理旧 `TileView`
7. `BoardController` 实例化新的 `TileView`
8. `GridMath.GridToWorld()` 把逻辑坐标换成世界坐标
9. `BoardController` 计算可动状态并发出 `BoardGenerated`
10. `GameScene` 刷新调试文本、统计文本和层过滤控件

固定原型与此类似，只是布局来源换成：

- `PrototypeLayoutFactory.CreateSingleLevelPrototype()`

## 当前交互链路

### 点击链路

当前点击交互为：

1. 鼠标按下时，`BoardController` 先记录按下状态
2. 如果按下后没有进入拖拽，则在松手时按点击处理
3. 点击可移动牌时：
   - 第一次点击：选中
   - 点击另一张同牌面且可移动的牌：消除
   - 再点击同一张牌：取消选中

### 最小拖拽链路

当前拖拽交互为：

1. 鼠标左键按下可移动牌
2. 鼠标移动超过 `DragStartThreshold`
3. 进入拖拽态，牌跟随鼠标移动
4. 松手时检查是否与另一张“可移动且同牌面”的牌主体矩形相交
5. 命中则消除，未命中则回到原位

当前实现刻意保持简单：

- 没有做路径阻挡求解
- 没有做磁吸
- 没有做拖拽过程中的复杂遮挡规则

目标是先把“可拖起、可落下、可判定命中”这条链路跑通。

## 当前关键几何规则

### 1. 同层绝不重叠

这是当前硬约束。

### 2. 相邻层不允许完全重合

上层一张牌不能与下一层某张牌在 footprint 上完全一致。

### 3. 上层必须获得完整底面覆盖

当前统一采用“全底面覆盖”规则，不直接编码“两支撑 / 四支撑”。

### 4. 可动判定是几何结果

当前一张牌不可动的条件是：

- 上方存在任何投影遮挡
- 同层左右同时被邻接牌堵住
- 同层上下同时被邻接牌堵住

这是一版偏保守、可调试的基础判定，后续可以继续演进。

## 当前调试与日志策略

当前在 `BoardController` 中已经为以下关键节点加日志：

- 规则档案切换
- 布局应用开始与结束
- 左键按下
- 命中检测结果
- 开始拖拽
- 结束拖拽
- 点击处理分支
- 消除完成

明确不在每帧输出日志，避免 Godot 输出窗口刷屏导致难以定位真正问题。

## 当前明确边界

### `BoardController` 负责

- 布局应用
- 牌桌重建
- 可动状态刷新
- 点击与最小拖拽交互
- 消除后状态更新
- 面向排查的结构化日志

### `BoardController` 不负责

- 首页和结果页
- 最终拖拽手感调优
- 正式关卡可解性分析
- 商业化内容系统

### `GameScene` 负责

- 调试按钮和调试面板
- 规则 profile 切换
- 统计文本同步
- 视觉反馈

### `GameScene` 不负责

- 布局几何计算
- 支撑判定
- 交互合法性判定
