# 游戏外围流程与页面架构设计

## 文档目标

本文档用于定义当前项目在“核心游戏页之外”的外围流程方案，覆盖：

- 应用入口
- 主页
- 游戏页
- 结算页
- 后续可扩展的加载页、奖励页、个人信息页

当前阶段的目标不是一次性做完所有外围产品内容，而是先把一条可持续迭代的正式流程跑通，让项目从“单场景玩法原型”升级为“有应用外壳和关卡流转的游戏原型”。

## 当前已落地结论

当前版本已经正式采用以下流程骨架：

1. `AppRoot` 作为应用主入口与页面路由控制器
2. `HomePage` 作为主页，显示当前即将进入的关卡信息
3. `GameScene` 作为游戏页，负责实际关卡启动与局内玩法
4. `LevelCompletePage` 作为结算页，展示本关结果和下一关预告
5. 结算页点击“继续”直接进入下一关，不再先回主页

这条流程已经替代“直接把 `GameScene` 当整个应用入口”的早期方式。

## 为什么要这样拆

随着项目推进，`GameScene` 已经承载了越来越完整的局内玩法逻辑，包括：

- 牌桌生成
- 通用堆叠框架
- 点击与拖拽消除
- 失败反馈
- 消除动画与得分反馈
- 调试面板与规则切换

如果继续把主页、结算页、未来的加载页都堆回 `GameScene`，会产生三个问题：

- 页面职责混乱：局内玩法和应用级流转混在一个场景里
- 后续扩展成本高：加载页、奖励页、个人信息页很难自然接入
- AI agent 理解成本上升：很难一眼看清“谁负责页面、谁负责牌桌、谁负责关卡配置”

因此当前做法是把“外围流程”和“局内玩法”彻底分层。

## 当前页面职责

### 1. AppRoot

位置：

- `godot/scenes/app/AppRoot.tscn`
- `godot/scripts/app/AppRoot.cs`

职责：

- 作为主场景入口
- 在主页、游戏页、结算页之间切换
- 加载 `LevelCatalog` 和 `LayoutProfileCatalog`
- 维护“当前应该进入哪一关”
- 为主页和结算页拼装关卡标题、规则摘要、下一关预告

边界：

- `AppRoot` 不负责牌桌逻辑
- `AppRoot` 不负责具体交互规则
- `AppRoot` 只负责页面流转与轻量流程状态

### 2. HomePage

位置：

- `godot/scenes/home/HomePage.tscn`
- `godot/scripts/home/HomePage.cs`

职责：

- 显示玩家基础占位信息
- 显示“当前将进入的关卡名”
- 显示“当前关卡规则摘要”
- 触发进入游戏

当前阶段刻意保持简单，不提前接入复杂的背包、签到、设置或资源系统。

### 3. GameScene

位置：

- `godot/scenes/game/GameScene.tscn`
- `godot/scripts/game/GameScene.cs`

职责：

- 作为正式游戏页
- 按关卡配置启动对应关卡
- 接收 `LevelConfig` 驱动的布局来源与规则档案
- 在局内玩法完成后发出通关事件
- 提供返回主页入口

当前版本已经不再只依赖 `Esc` 返回主页，而是提供了明确的可视按钮。

### 4. LevelCompletePage

位置：

- `godot/scenes/result/LevelCompletePage.tscn`
- `godot/scripts/result/LevelCompletePage.cs`

职责：

- 显示本关得分、配对数、耗时
- 显示下一关关卡名与规则摘要
- 提供“继续”与“返回主页”操作

当前阶段它是正式流程里的主结算页。

## 当前页面流转

已经落地的主流程如下：

1. 应用启动进入 `AppRoot`
2. `AppRoot` 默认显示 `HomePage`
3. `HomePage` 显示当前关卡标题与摘要
4. 点击开始后进入 `GameScene`
5. `GameScene` 按关卡配置生成正式关卡
6. 牌桌清空后触发 `LevelCompleted`
7. `AppRoot` 打开 `LevelCompletePage`
8. 结算页点击“继续”直接进入下一关
9. 结算页点击“返回主页”回到 `HomePage`

## 当前关卡配置接入方式

外围流程不直接写死每一关，而是通过关卡目录资源驱动：

- `godot/scripts/config/LevelConfig.cs`
- `godot/scripts/config/LevelCatalog.cs`
- `godot/scripts/config/LevelLayoutSourceMode.cs`
- `godot/configs/levels/default_levels.tres`

单关当前最关键的配置包括：

- `LevelNumber`
- `DisplayName`
- `LayoutProfileId`
- `LayoutSourceMode`
- `UseFixedSeed`
- `RandomSeed`
- `SourceNameOverride`

这意味着外围流程只需要知道“当前是第几关”，真正的规则与布局来源都由关卡配置决定。

## 当前版本的具体策略

### 主页展示策略

主页当前会显示：

- 当前即将进入的关卡名
- 对应规则档案名
- 布局来源摘要

这样玩家进入前就知道下一关是：

- 固定原型牌桌
- 固定种子随机牌桌
- 动态随机牌桌

### 结算页展示策略

结算页当前会显示：

- 当前关卡结果
- 下一关名称
- 下一关规则摘要

这样“继续”按钮不只是机械地跳下一关，而更接近正式手游里的“下一关预告”。

## 为什么 GameScene 不再直接自己决定流程

`GameScene` 当前仍然负责局内玩法，但已经不再承担应用总入口职责。这样做有几个直接收益：

- 游戏页可以被 `AppRoot` 反复实例化和释放
- 结算页不需要知道牌桌内部实现
- 主页不需要依赖牌桌节点路径
- 后续加载页、奖励页接入时不会污染牌桌逻辑

## 当前技术约束

### 1. 页面间事件传递

当前页面流转优先使用普通 C# 事件，而不是用 Godot Signal 去传复杂 DTO。

原因：

- `LevelCompleteResult` 这类自定义数据结构更适合普通 C# 事件
- 可以绕开 Godot C# signal 参数类型的限制
- 让外围流程逻辑更接近普通应用层代码

### 2. 流程状态尽量保持轻量

当前 `AppRoot` 只维护最小必要状态：

- 当前关卡号

其余信息尽量按需从配置资源重新读取，而不是在页面间传复杂全局状态。

### 3. HomePage / ResultPage 不直连牌桌

主页与结算页都不应该直接读取 `BoardController`。它们只消费 `AppRoot` 传入的轻量显示数据。

## 已实现但仍属阶段性方案的部分

当前流程已经能跑通，但仍有一些明确属于第一阶段骨架的地方：

- 还没有正式加载页
- 还没有每日奖励页
- 玩家信息仍是占位数据
- 主页和结算页的视觉表现仍偏原型
- 还没有长期存档与进度保存

这些不是架构问题，而是当前阶段刻意收口的实现范围。

## 下一阶段可扩展方向

当前架构允许后续自然接入：

- `BootLoadingPage`
- `DailyRewardPage`
- 更正式的个人信息页
- 连续通关奖励
- 关卡章节系统
- 存档与进度恢复

扩展原则是不改变现有分层：

- `AppRoot` 继续负责页面流转
- `GameScene` 继续负责局内玩法
- `LevelCatalog` 继续负责关卡入口配置

## 维护要求

只要以下任一内容发生变化，就应同步更新本文档：

- 页面主流程变化
- `AppRoot` 职责变化
- `HomePage / GameScene / LevelCompletePage` 的边界变化
- 关卡配置入口变化
- “继续进入下一关”相关流程变化
