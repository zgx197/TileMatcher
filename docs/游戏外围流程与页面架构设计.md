# 游戏外围流程与页面架构设计

## 文档目标

本文档用于定义当前项目在“核心游戏页之外”的外围流程方案，覆盖：

- 应用入口
- 启动加载页
- 主页
- 游戏页
- 结算页
- 每日奖励页
- 玩家外围进度与持久化

当前这套方案已经不再是规划状态，而是已落地到工程中的正式外围流程骨架。

## 当前已落地结论

当前版本已经正式采用以下流程链路：

1. `AppRoot` 作为应用主入口与页面路由控制器
2. `BootLoadingPage` 作为启动加载页
3. `HomePage` 作为主页，显示玩家资料、进度摘要和当前关卡
4. `GameScene` 作为游戏页，负责实际关卡启动与局内玩法
5. `LevelCompletePage` 作为结算页，展示本关结果和下一关预告
6. `DailyRewardPage` 作为次级奖励页，承接每日首胜奖励
7. 玩家进度通过本地持久化保存，重新启动后可恢复当前关卡与叶子数量

## 为什么要这样拆

随着项目推进，`GameScene` 已经承载了越来越完整的局内玩法逻辑，包括：

- 牌桌生成
- 通用堆叠框架
- 点击与拖拽消除
- 失败反馈
- 消除动画与得分反馈
- 调试面板与规则切换

如果继续把启动页、主页、结算页、奖励页都堆回 `GameScene`，会产生三个问题：

- 页面职责混乱：局内玩法和应用级流转混在一个场景里
- 后续扩展成本高：奖励、存档、个人信息、加载流程难以自然接入
- AI agent 理解成本上升：很难一眼看清“谁负责页面、谁负责牌桌、谁负责关卡与进度”

因此当前做法是把“外围流程”和“局内玩法”彻底分层。

## 当前页面职责

### 1. AppRoot

位置：

- `godot/scenes/app/AppRoot.tscn`
- `godot/scripts/app/AppRoot.cs`

职责：

- 作为主场景入口
- 串联启动页、主页、游戏页、结算页和奖励页
- 加载 `LevelCatalog` 和 `LayoutProfileCatalog`
- 读取并保存玩家外围进度
- 维护“当前应该进入哪一关”
- 决定通关后是直接进下一关，还是先进入奖励页

边界：

- `AppRoot` 不负责牌桌逻辑
- `AppRoot` 不负责具体交互规则
- `AppRoot` 只负责页面流转、进度数据和奖励分发

### 2. BootLoadingPage

位置：

- `godot/scenes/boot/BootLoadingPage.tscn`
- `godot/scripts/boot/BootLoadingPage.cs`

职责：

- 作为正式启动页入口
- 承担最短展示时长、启动氛围和过渡职责
- 在加载完成后把控制权交回 `AppRoot`

当前阶段它不接入真正的异步资源加载器，而是承担“正式应用启动壳层”的职责。

### 3. HomePage

位置：

- `godot/scenes/home/HomePage.tscn`
- `godot/scripts/home/HomePage.cs`

职责：

- 显示玩家基础资料
- 显示叶子数量
- 显示进度摘要，例如最高解锁和总通关数
- 显示“当前将进入的关卡名”
- 显示“当前关卡规则摘要”
- 触发进入游戏

### 4. GameScene

位置：

- `godot/scenes/game/GameScene.tscn`
- `godot/scripts/game/GameScene.cs`

职责：

- 作为正式游戏页
- 按关卡配置启动对应关卡
- 接收 `LevelConfig` 驱动的布局来源与规则档案
- 在局内玩法完成后发出通关事件
- 提供返回主页入口

### 5. LevelCompletePage

位置：

- `godot/scenes/result/LevelCompletePage.tscn`
- `godot/scripts/result/LevelCompletePage.cs`

职责：

- 显示本关得分、配对数、耗时
- 显示下一关关卡名与规则摘要
- 在存在每日奖励时，明确提示“继续后先领取奖励”
- 提供“继续”和“返回主页”操作

### 6. DailyRewardPage

位置：

- `godot/scenes/result/DailyRewardPage.tscn`
- `godot/scripts/result/DailyRewardPage.cs`

职责：

- 显示每日首胜奖励
- 显示当前叶子总数
- 显示下一关预告
- 提供“继续下一关”和“返回主页”操作

它是通关后的次级奖励页，而不是替代结算页的主页面。

## 当前页面流转

当前已经落地的完整流程如下：

1. 应用启动进入 `AppRoot`
2. `AppRoot` 读取关卡目录与玩家进度
3. `AppRoot` 显示 `BootLoadingPage`
4. 启动页完成后进入 `HomePage`
5. `HomePage` 显示当前关卡标题、摘要和玩家进度
6. 点击开始后进入 `GameScene`
7. `GameScene` 按关卡配置生成正式关卡
8. 牌桌清空后触发 `LevelCompleted`
9. `AppRoot` 更新持久化进度与奖励状态
10. `AppRoot` 打开 `LevelCompletePage`
11. 若今日奖励已触发，则点击“继续”后进入 `DailyRewardPage`
12. 奖励页点击“继续”进入下一关
13. 任何阶段点击“返回主页”都可回到 `HomePage`

## 当前关卡配置接入方式

外围流程不直接写死每一关，而是通过关卡目录资源驱动：

- `godot/scripts/config/LevelConfig.cs`
- `godot/scripts/config/LevelCatalog.cs`
- `godot/scripts/config/LevelLayoutSourceMode.cs`
- `godot/configs/levels/default_levels.tres`

单关当前最关键的配置包括：

- `LevelNumber`
- `DisplayName`
- `LayoutProfileId`
- `LayoutSourceMode`
- `UseFixedSeed`
- `RandomSeed`
- `SourceNameOverride`

这意味着外围流程只需要知道“当前是第几关”，真正的规则与布局来源都由关卡配置决定。

## 当前进度与持久化设计

### 持久化对象

当前玩家外围进度由以下代码负责：

- `godot/scripts/app/PlayerProgressData.cs`
- `godot/scripts/app/PlayerProgressStore.cs`

保存内容包括：

- 玩家名称
- 叶子数量
- 当前关卡号
- 最高解锁关卡
- 累计得分
- 累计配对数
- 累计通关数
- 每日奖励最近领取日期

### 保存策略

当前使用 `user://player_progress.json` 保存本地 JSON。

这样做的原因是：

- 可读性强，便于调试
- 不依赖额外存档框架
- 适合原型阶段快速迭代

### 职责边界

外围进度只保存“外层流程真正关心的状态”，不保存牌桌内部瞬时状态。

## 当前每日奖励策略

每日奖励当前由 `AppRoot` 在通关时判定：

- 按本地日期计算是否为今日首次通关
- 若是，则发放固定叶子奖励
- 奖励先写入持久化进度
- 再由 `DailyRewardPage` 负责向玩家展示

当前默认奖励为：

- `+3` 叶子

这属于外围产品层规则，不进入 `BoardController` 或牌桌交互层。

## 当前主页展示策略

主页当前会显示：

- 玩家名称
- 叶子数量
- 最高解锁和通关进度摘要
- 当前即将进入的关卡名
- 对应规则档案名
- 布局来源摘要

这让主页不再只是一个空按钮页，而是具备正式手游里“出发前确认信息”的作用。

## 当前结算与奖励展示策略

### 结算页

结算页当前会显示：

- 当前关卡结果
- 下一关名称
- 下一关规则摘要
- 是否存在待领取的每日奖励

### 奖励页

奖励页当前会显示：

- 今日奖励内容
- 当前叶子总数
- 下一关预告

因此“继续”按钮不只是机械跳下一关，而是形成：

- 通关反馈
- 奖励反馈
- 下一关推进

这条更完整的手游式外层节奏。

## 当前技术约束

### 1. 页面间事件传递

当前页面流转优先使用普通 C# 事件或轻量 signal 参数，而不是让页面彼此直接读节点树。

原因：

- 页面间 DTO 更适合普通 C# 对象
- 可以绕开 Godot C# signal 对复杂参数的限制
- 让外围流程逻辑保持在 `AppRoot`

### 2. 流程状态尽量保持轻量

当前 `AppRoot` 只维护外层真正必要的状态：

- 当前关卡号
- 玩家外围进度
- 待展示的每日奖励摘要

其余信息尽量按需从配置资源重新读取。

### 3. 页面不直连牌桌

`HomePage`、`LevelCompletePage` 和 `DailyRewardPage` 都不直接读取 `BoardController`。
它们只消费 `AppRoot` 传入的轻量展示数据。

## 当前已完成的原“未完成项”

此前文档中提到的外围缺口，当前已全部补齐：

- 正式启动加载页：已完成
- 每日奖励页：已完成
- 玩家信息不再只是纯占位数据：已完成
- 主页和结算页已提升为正式外围页面骨架：已完成
- 外围进度持久化：已完成

当前仍然保留为后续迭代项的，只剩更高一层的产品扩展，不再是流程堵点。

## 后续可扩展方向

当前架构允许后续自然接入：

- 更复杂的启动加载内容
- 更正式的个人信息页
- 连续通关奖励
- 关卡章节系统
- 云存档或多档位存档
- 更丰富的外层货币与背包系统

扩展原则不变：

- `AppRoot` 继续负责页面流转与外围状态
- `GameScene` 继续负责局内玩法
- `LevelCatalog` 继续负责关卡入口配置

- 页面主流程变化

- 启动页、主页、结算页、奖励页的边界变化

## 当前局内辅助资源接入

为了让正式关卡体验先具备最小辅助闭环，当前已把两类局内辅助资源接入到外围进度体系：

- `重新开始`
- `提示`

### 页面层职责

- `GameScene`
  - 展示底部两个辅助按钮
  - 展示每关当前剩余次数
  - 在点击后消费次数并请求保存
- `AppRoot`
  - 把共享的 `PlayerProgressData` 传给 `GameScene`
  - 继续统一负责真正的保存动作

### 存档层职责

当前这两类次数不会只存在于页面临时状态，而是会按关卡号写入玩家进度：

- 同一关重新进入时，已消耗次数仍然保留
- 不同关卡各自独立记录

这让“辅助资源属于玩家长期进度的一部分”这一点在架构上保持明确，而不是把它做成一次性的局内临时变量。

## Debug 重置账号数据

当前 `GameScene` 的 debug 面板已经提供“重置账号数据”入口，定位为开发期辅助能力。

### 行为约定

- 点击后立即清空玩家当前进度存档
- 当前已通关统计、叶子数、关卡推进和每关辅助资源消耗都会回到默认值
- 操作完成后强制返回主页

### 职责边界

- `GameScene`
  - 只负责暴露 debug 按钮和向外围流程发出重置请求
- `AppRoot`
  - 负责真正替换为新的 `PlayerProgressData`
  - 负责保存新存档
  - 负责清空待展示的奖励状态并切回主页

## Debug 局内调试能力

为了让开发阶段更快回归正式关卡与局内资源状态，`GameScene` 的 debug 面板继续补充以下能力：

- 跳转到指定关卡
- 重置当前关卡的重开次数和提示次数
- 一键自动消除一对当前可消除麻将

### 跳关约定

- 跳关不是在 `GameScene` 内部直接硬切牌桌
- 页面层只发出 `DebugLevelJumpRequested(levelNumber)`
- 真正的跳关由 `AppRoot` 更新当前关卡号、保存进度后重新进入目标关卡

这样可以保证跳关和正常进关复用同一条外围流程，避免页面内残留旧局状态。

### 当前关卡辅助次数重置约定

- 只重置当前关卡对应的 `RestartUsedCount`
- 只重置当前关卡对应的 `HintUsedCount`
- 重置后立即写回玩家进度存档
- 不影响其他关卡的辅助次数消耗记录

这让我们在调试单关时可以快速恢复局内辅助资源，同时不破坏按关卡独立记账的长期存档结构。

### 自动消除一对约定

- 自动消除只作为 debug 能力存在，不进入正式玩家按钮链路
- 复用当前棋盘已经存在的“提示对搜索”逻辑寻找一对可立即消除的麻将
- 找到后直接走现有配对消除动画与计分流程
- 找不到时只提示当前无可自动消除对，不改动局面

这样可以减少为了复测后续状态而手工拖拽同一对牌的重复操作，同时保证调试消除仍然经过正式的局内行为链路。
