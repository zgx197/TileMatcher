## 目标

这份说明用于固定当前项目的 Android 打包与发布链路，避免再次出现下面几类问题：

- 版本号更新了，但 APK 实际内容还是旧代码或旧资源。
- 本地能打包，CI 不能打包，而且两边走的不是同一套流程。
- Godot 已经导出了可用 APK，但外层脚本还在等待进程退出，看起来像卡死。

当前原则是：

1. 本地和 GitHub Actions 共用同一份核心打包脚本。
2. 先让 Godot 正式导出，再做签名和校验。
3. 不依赖误入库的大型 Android 二进制。
4. 把干净环境下缺失的资源和模板归档交给脚本自动补齐。

## 当前标准流程

### 本地脚本会做什么

`build-android.ps1` 现在会按下面顺序执行：

1. 同步 `project.godot`、`export_presets.cfg`、Android manifest 中的构建元数据。
2. 自动补齐 Android 导出所需的主题资源、启动背景资源和项目名称资源。
3. 自动从 Godot 的 `android_source.zip` 中提取模板 AAR，避免依赖本地残留的 `libs/*.aar`。
4. 调用 Godot `--headless --export-debug` 进行正式导出。
5. 在 Godot 没有正常退出但 APK 已稳定生成时，继续复用新鲜产物，而不是无限等待。
6. 使用 `apksigner` 完成签名。
7. 使用 `apksigner verify` 和 `aapt dump badging` 做最终校验。

### 为何现在不容易“卡住”

之前最容易卡在这一步：

```text
==> Sync build metadata
==> Prepare Android export resources
==> Prepare Godot Android template archives
==> Run Godot export
```

问题不一定是 Godot 没有完成导出，而是：

- Godot 进程没有及时退出。
- 外层脚本只盯着进程状态，没有优先盯产物状态。

现在脚本已经补上三层保护：

1. 心跳日志  
   每隔一段时间输出一次当前等待状态，避免终端长时间无反馈。

2. 产物稳定判定  
   同时监控 `TileMatcher-unsigned.apk` 和 Gradle fallback APK，只要任意一个新鲜产物稳定一段时间，就继续后续流程。

3. 总超时保护  
   如果等待时间超出上限，会主动停止进程并输出日志，而不是看起来永久卡住。

这意味着：

- 构建真的失败时，会更快看到真实失败点。
- 构建其实已完成时，不会因为 Godot 进程滞留而误判成卡死。

## 本地使用方式

示例：

```powershell
.\scripts\build-android.ps1 `
  -GodotExe "D:\GodotCSharp\Godot_v4.6.1-stable_mono_win64\Godot_v4.6.1-stable_mono_win64.exe" `
  -AndroidSdkRoot "C:\Users\Guoxi\AppData\Local\Android\Sdk" `
  -JavaHome "C:\Program Files\Android\Android Studio\jbr" `
  -KeystorePath "C:\Users\Guoxi\AppData\Roaming\Godot\keystores\debug.keystore" `
  -KeystorePassword "android" `
  -KeyAlias "androiddebugkey" `
  -KeyPassword "android" `
  -PackageName "com.zgx197.tilematcher" `
  -VersionName "0.1.5" `
  -VersionCode 6 `
  -ManifestOrientation "portrait"
```

默认输出目录：

- `godot/build/android/`

常见产物：

- `TileMatcher-unsigned.apk`
- `TileMatcher-<version>-android-debug.apk`
- `TileMatcher-<version>-android-debug.apk.sha256.txt`

## GitHub Actions 发布方式

当前发布工作流已经切换为：

- 一个 `metadata` 入口 job
- 一个 Android / Windows 矩阵导出 job
- 一个最终的 release 聚合 job

其中 Android 侧仍然保持原有原则：

- 使用固定版本的 `windows-2022`
- 固定安装 Java 17、Android SDK、Gradle 8.11.1、Godot 4.6.1 mono
- 直接调用同一份 [build-android.ps1](d:/UGit/TileMatcher/scripts/build-android.ps1)
- 支持 `workflow_dispatch`
- 支持 `publish_release=false` 只做构建与 artifact 验证
- 支持 `publish_release=true` 把 Android 与 Windows 产物统一挂到同一个 GitHub Release

当前已经确认：

- hosted-runner Android 冒烟验证链路已固定
- Android APK 导出、签名、元数据收集、artifact 上传逻辑仍由 `build-android.ps1` 负责
- release 发布阶段已经从“Android job 直接上传”改为“矩阵产物统一聚合上传”

## 需要配置的 Secrets

GitHub 仓库中需要准备这四项：

- `ANDROID_DEBUG_KEYSTORE_BASE64`
- `ANDROID_DEBUG_KEYSTORE_PASSWORD`
- `ANDROID_DEBUG_KEY_ALIAS`
- `ANDROID_DEBUG_KEY_PASSWORD`

如果使用当前本机 Godot 默认调试 keystore，则常见值为：

- keystore password: `android`
- key alias: `androiddebugkey`
- key password: `android`

将本机 `debug.keystore` 转成 base64 的命令：

```powershell
[Convert]::ToBase64String(
  [System.IO.File]::ReadAllBytes("C:\Users\Guoxi\AppData\Roaming\Godot\keystores\debug.keystore")
)
```

## 这次链路修复解决了什么

这轮 Android 打包链路修复，主要解决了四类问题：

1. hosted-runner 干净环境下缺少主题资源、启动背景资源。
2. hosted-runner 干净环境下缺少 Godot Android 模板 AAR。
3. keystore Secrets 与实际本机 `debug.keystore` 不匹配导致签名失败。
4. Godot 导出完成但不及时退出，导致本地脚本看起来卡在 `Run Godot export`。
