## 1. 说明

TileMatcher：“复刻一套堆叠配对消除玩法的原型”，逐步演进成一个更完整的轻度休闲产品雏形。



## 2. 整体设计思路

整个项目采用的是“先跑通最小闭环，再逐步扩展”的方式。

我没有一开始就做很重的大系统，而是先让最核心的链路稳定下来：

1. 首页进入关卡
2. 局内完成配对与消除
3. 通关或失败后给出明确反馈
4. 让进度、奖励和存档可以正确保存

在这个基础上，再继续往外扩：

- 用离线方式生产正式关卡数据
- 用更清晰的外围页面承接长期体验
- 引入金币和宠物养成，让产品不只依赖单次关卡体验

这种做法的好处是，项目每个阶段都能看到实际结果，也能尽早发现真实问题，而不是在纸面设计里停留太久。

## 3. 为什么采用现在这套整体框架

### 3.1 页面与职责拆分

项目已经明确采用外围页面和局内玩法分离的结构：

- `AppRoot` 负责应用入口、页面切换、进度保存和奖励分发
- `HomePage` 负责首页展示和产品外围入口
- `GameScene` 负责局内玩法
- 结算页、奖励页、失败页负责对玩家做结果反馈

这样做的原因很直接：

- 不把所有逻辑都堆进一个场景里
- 让玩法问题和外围问题可以分开排查
- 后续加金币、宠物、奖励、活动时，不会把局内逻辑越缠越乱

### 3.2 运行时消费与离线生产分离

我已经明确把“关卡生产”和“游戏运行”拆成两段：

- 离线工具负责构造、评估、筛选和导出正式关卡
- Godot 运行时只负责按关卡号读取数据并加载

这个原则非常重要，因为它直接决定了后续内容生产的效率。

如果把关卡构造、验证、筛选都塞进运行时，会有几个问题：

- 性能压力会转移到玩家设备上
- 很难批量生成和筛选关卡
- 策划和开发无法方便地复核关卡质量

现在的方向是：

- 离线导出正式关卡数据
- 通过 `level-catalog.json` 和关卡 JSON 目录供运行时消费
- 后续再让 Web 分析台直接读取离线结果进行浏览和筛选

## 4. 牌局构造与评估系统

### 4.1 为什么不只是“自动布局”

我已经把这套系统正式定义为“配对牌局构造与评估系统”，而不是简单叫“自动布局”。

原因是，真正的问题不是把牌摆出来，而是要回答下面这些更关键的问题：

- 这局能不能通关
- 会不会中途很容易卡死
- 它属于偏简单、偏复杂还是偏危险的关卡
- 它是否适合进入正式关卡池

所以系统目标不是“生成一桌牌”，而是“离线生成候选牌局，再做评估和筛选”。

### 4.2 当前系统的核心要求

这套系统当前强调三件事：

- 生成时就要保证可解性
- 生成后还要做难度评估
- 筛选流程尽量自动化

其中最重要的底线是：

> 正式关卡至少要存在一条能够清空全局的玩家操作路径，不能让玩家陷入无解卡死。

为了更严格地控制体验，我还提出了更高的目标：

- 不只是存在一条解法
- 而是尽量保证存在若干条持续可推进路径
- 并通过死局率、分支数、关键决策密度等维度来衡量难度

### 4.3 为什么坚持离线预计算

离线构造的最大价值，不只是节省运行时性能，更重要的是给项目带来“可批量分析”的能力。

离线阶段可以做：

- 批量生成候选牌局
- 完整求解和验证
- 统计死局风险
- 做多维度难度分档
- 自动输出推荐池、待复核池、淘汰池

这让正式关卡不再是“凭感觉挑”，而是逐渐变成“有依据地筛选”。

### 4.4 Web 分析台为什么合理

由于离线侧会产出大量预计算结果，只靠日志和原始数据文件很难让策划快速理解关卡质量。

因此项目已经明确，后续为这套系统配一套 Web 分析台是合理且必要的。

它的定位不是在线实时生成器，而是：

- 离线分析结果浏览器
- 候选关卡筛选器
- 难度对比和复核工具

第一阶段优先使用成熟开源工具即可，例如：

- `ECharts` 做图表和指标对比
- 常规表格组件做列表筛选和排序

这样既能加快搭建速度，也能让整个工具链更稳、更透明。

## 5. 整体框架设计中遇到的主要问题

### 5.1 网格和堆叠规则过早被旧方案限制

项目早期曾采用更简单的固定占位方案，但很快暴露出几个问题：

- 对“支撑关系”的表达过于僵硬
- 很难自然表达不同层级的真实覆盖关系
- 后续一旦要做更复杂的堆叠结构，扩展性不足

为了解决这个问题，项目转向了第二代通用堆叠框架：

- 底层仍然使用整数网格
- 每张牌用矩形 footprint 表示
- 上层合法性以“底面完整覆盖”为准
- “两支撑 / 四支撑”不再是底层规则，而是分析结果

这套方案更接近通用几何规则，也更适合后续关卡生产和评估。

### 5.2 运行时曾出现死局风险

在实际游玩中，已经暴露过“进入死局后玩家无法继续，但系统又没有明确结束”的问题。

这个问题会直接破坏玩家体验，因为玩家会误以为是游戏出错，而不是正常失败。

项目对此做了两层处理：

- 运行时补上死局检测与失败页，让玩家有明确反馈和出口
- 离线侧继续强化可解性验证，减少正式关卡进入死局的概率

这也让项目进一步明确了一条原则：

> 游戏可以有难度，但不能让玩家在不知所措中卡死。

### 5.3 交互链路曾出现“规则和视觉打架”

在点击、拖拽、提示、高亮、背面牌翻面这些功能逐步叠加后，项目一度出现过：

- 拖拽中状态不一致
- 锁定牌提示反馈不稳定
- 翻面和选中、高亮互相打架
- 动画和规则判定不同步

这类问题的根源不是单个功能坏了，而是状态管理不够清晰。

因此后续实现中逐步强化了统一状态视角、统一失败反馈和更清晰的局内行为链路，避免继续靠零散补丁堆逻辑。

### 5.4 调试面板和普通 UI 层级曾互相遮挡

项目在首页和局内都引入了调试能力，但早期弹窗、调试面板和普通页面内容曾混在同一层里，造成：

- 弹出的调试面板被普通 UI 盖住
- 层级关系不清晰
- 行为不一致，容易误触

后来项目明确了新的 UI 原则：

- 首页弹窗和 Debug 面板统一进入独立高层 UI 容器
- 普通内容层和模态层分离

这个问题看起来像 UI 小问题，但本质上是页面架构问题。把这个规则提前定下来，后续加活动弹窗、奖励弹窗、宠物救助弹窗时就会稳很多。

### 5.5 文案和资源链路曾出现乱码问题

在持续迭代过程中，代码、场景和文档里都曾出现过乱码，这不仅影响显示，也会影响团队判断问题。

项目后来专门做过多轮清理，逐步建立了新的约束：

- 玩家可见文案统一整理
- 技术术语和内部注释逐步同步更新
- 发现乱码就及时修复，不再放任扩散

这类问题虽然不属于玩法设计，但会直接影响产品可信度和团队协作效率。

## 6. 安卓导出和打包问题

安卓链路是当前项目里另一个非常典型的“看起来像导出问题，实际是流程问题”的案例。

### 6.1 当时遇到的问题

项目一度出现过这样的现象：

- 安装包的版本号看起来是新的
- Manifest 里的配置看起来也是新的
- 但真机里实际运行的资源和程序集仍然是旧的

这个问题很隐蔽，因为表面上“包已经打出来了”，但实际运行内容并没有真正刷新。

### 6.2 根因

根因并不是代码没编译，而是打包链路走错了。

一开始如果直接在 Android 工程里跑 Gradle，它只会继续封装已有的资源快照，不会自动刷新 Godot 最新导出产物。

也就是说：

- `Gradle` 负责封装 Android 工程
- `Godot export` 才负责刷新真正会进包的资源和程序集

### 6.3 现在的解决方案

项目已经把安卓打包原则固定下来：

1. 先更新版本与导出元数据
2. 用 Godot `--headless --export-debug` 走正式导出
3. 让 Godot 刷新最新资源和程序集
4. 再对导出的 APK 做签名与校验

同时，项目也补了对应的安卓导出说明和打包脚本说明，把“正确流程”固化下来，避免以后再次出现“本地正常、真机还是旧包”的隐蔽问题。

### 6.4 当前安卓侧状态

目前项目已经补齐了安卓导出骨架和脚本规范，导出配置本身已经准备好。

当前剩余的主要阻塞点，更多是开发机本地环境是否完整，例如：

- Android SDK
- JDK
- Godot Android Export Templates

也就是说，项目已经解决了“流程正确性”的问题，剩下主要是环境配置问题。

## 7. 为什么引入养宠模式

这是当前产品方向里非常关键的一次升级。

### 7.1 只靠关卡推进，长期动力不够

如果产品只有“闯关 - 通关 - 下一关”这一条循环，玩家的动力会主要来自关卡本身。

这会带来两个限制：

- 玩家一旦在短时间内感到疲劳，缺少继续留下来的理由
- 首页和外围页面容易退化成单纯的跳转入口

### 7.2 养宠模式提供了玩法外的长期目标

引入“动物消消乐 + 金币 + 宠物救助 / 领养 + 宠物乐园”之后，产品循环发生了变化：

1. 玩家完成关卡获得金币
2. 玩家用金币领养新的小动物
3. 已领养宠物回到首页持续展示
4. 玩家为了获得更多宠物继续推进关卡

这让关卡收益不再只是一句“过关了”，而是变成可积累、可展示、可期待的长期回报。

### 7.3 它提升的是用户粘性，而不是单次刺激

养宠模式的意义不在于立刻做复杂经营，而在于补上一层温和但持续的情感目标。

它的价值主要体现在：

- 提升留存动机
- 给首页一个真正有生命力的存在理由
- 让金币奖励不再只是数字，而是有明确用途
- 让玩家形成“再玩一关就能救助一个新伙伴”的心理预期

这比单纯堆更多关卡，更有机会形成长期体验。

## 8. 当前已经完成的阶段性成果

截至目前，项目已经取得几项比较明确的阶段成果。

### 8.1 玩法闭环已经跑通

已经形成完整的玩家流程：

- 首页进入关卡
- 局内配对消除
- 通关进入结算
- 死局进入失败页
- 奖励和进度可持久化保存

### 8.2 正式关卡数据链路已经接通

项目已经跑通“离线导出正式关卡 -> 同步到 Godot -> 运行时按目录索引消费”的最小链路。

当前已经导出并接入了前 20 关正式关卡数据，这意味着项目不再完全依赖原型关卡或临时随机牌局。

### 8.3 首页开始具备产品化方向

首页已经从单纯入口页，逐步演进为：

- 金币展示入口
- 宠物救助入口
- 宠物乐园展示区
- 进入关卡赚金币的主入口

这使得首页开始承担“产品外围承接”的职责，而不只是一个开始按钮。

### 8.4 调试与排查能力明显增强

项目已经建立起较稳定的调试和排查能力，包括：

- 共享 Debug 面板
- 跳关、重置、加金币、刷新救助中心等开发辅助
- 更明确的日志抓取和问题定位链路

这些能力虽然不直接面向玩家，但会显著提升后续迭代效率。

## 9. 对外可以怎样理解这个项目

如果用一句更容易理解的话来描述当前项目，可以这样说：

> 这是一个正在成型中的轻度休闲消除产品，它以前台的配对消除玩法为核心，以离线关卡生产能力为内容基础，再通过金币和宠物救助系统补上长期留存动力。

也可以拆成三层来理解：

- 前台：轻度、直观、容易上手的配对消除玩法
- 中台：可批量生产、评估、筛选正式关卡的离线工具链
- 外围：围绕金币、宠物救助、宠物乐园展开的轻养成体验

## 10. 下一阶段重点

接下来更值得继续推进的方向主要有四类。

### 10.1 继续强化正式关卡质量

- 完善离线评估指标
- 强化自动筛选
- 降低正式关卡死局和坏体验风险

### 10.2 推进 Web 分析台 MVP

- 让策划和开发可以直接浏览候选关卡与评估结果
- 减少手工翻日志和手工挑选成本

### 10.3 继续完善首页和养宠体验

- 让宠物乐园表现更自然
- 继续增强宠物救助中心刷新、领养反馈和状态展示
- 逐步建立更完整的外围循环

### 10.4 持续稳定安卓出包能力

- 固化本地与 CI 的统一出包流程
- 降低导出链路和环境差异导致的问题

## 11. 阶段结论

当前项目最重要的变化，不是单独多做了一个功能，而是整体方向已经清晰下来：

- 玩法层面，已经从原型走向可持续迭代
- 内容层面，已经建立离线生产正式关卡的思路
- 产品层面，已经从“只是消除”升级为“消除 + 金币 + 宠物救助”的长期体验

接下来项目的重点，不再只是继续堆功能，而是把这三条主线进一步打磨得更稳定、更清晰、更适合长期演进。
