# 多平台发布脚本说明

## 归档说明

本文档已转入归档。

原因：

- 当前多平台入口、平台支持范围与 GitHub Actions 发布方式已经统一收敛到：
  - [构建与发布说明](../构建与发布说明.md)
- 本文档只保留多平台发布第一阶段落地时的历史记录

## 目标

这份文档用于固定当前仓库第一阶段的多平台出包约定：

- 本地和 CI 最终都应复用同一套脚本入口
- Android 和 Windows 先接通到“可真实产生产物”
- Web 目标先显式保留，但不伪装成已经可用

当前阶段的重点不是一次性把所有平台都做满，而是先把已经能验证的链路固定下来。

## 当前脚本入口

当前仓库已经有以下脚本：

- `scripts/build-android.ps1`
  - 负责 Android 导出、签名和 `sha256` 生成
- `scripts/build-windows.ps1`
  - 负责 Windows Desktop 导出、zip 打包和 `sha256` 生成
- `scripts/build-web.ps1`
  - 当前只负责对 Web 导出阻塞点给出明确报错
- `scripts/build-release.ps1`
  - 统一入口
  - 支持 `-Targets android,web,windows`
  - 当前默认目标为 `android,windows`

## 当前支持状态

### Android

- 已有导出预设
- 已有本地脚本
- 已有 GitHub Actions 工作流
- 当前脚本会直接生成：
  - `TileMatcher-<version>-android-debug.apk`
  - `TileMatcher-<version>-android-debug.apk.sha256.txt`

### Windows Desktop

- 已补 `godot/export_presets.cfg` 中的 `Windows Desktop`
- 已补本地导出与打包脚本
- 当前脚本会直接生成：
  - `TileMatcher-<version>-windows-x64.zip`
  - `TileMatcher-<version>-windows-x64.zip.sha256.txt`

当前 Windows 包的 zip 内至少包含：

- `TileMatcher.exe`
- `TileMatcher.pck`
- Godot .NET 运行时目录 `data_TileMatcher_windows_x86_64/`

### Web

当前项目是 Godot 4 C# / .NET 工程。

现阶段不把 Web 当成“可正常出包”的目标，原因不是脚本没写完，而是引擎约束：

- 官方文档明确说明 Godot 4 的 C# 项目不能导出到 Web
- 当前仓库中的 `build-web.ps1` 会直接抛出清晰错误，而不是生成误导性的空产物

官方文档：

- <https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html>

## 统一入口用法

### 默认构建

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-release.ps1
```

当前默认会构建：

- `android`
- `windows`

### 只构建 Windows

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-release.ps1 -Targets windows
```

### 只构建 Android

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-release.ps1 -Targets android
```

### 显式尝试 Web

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-release.ps1 -Targets web
```

这会直接报错并说明当前 Web 目标被 Godot C# 限制阻塞。

## 当前产物命名

当前已经固定的命名约定如下：

- Android:
  - `TileMatcher-<version>-android-debug.apk`
- Windows:
  - `TileMatcher-<version>-windows-x64.zip`
- Web:
  - 目标名预留为 `TileMatcher-<version>-web.zip`
  - 当前不会生成真实产物

每个平台都配套：

- `<artifact>.sha256.txt`

这轮落地后，第一阶段可以明确视为完成到以下程度：

## GitHub Actions

当前 GitHub Actions 工作流为：

- `.github/workflows/android-export.yml`

虽然文件名还保留 `android-export.yml`，但当前内容已经按多目标发布维护。

### 当前行为

- `push tag` 时：
  - 默认同时构建 Android 和 Windows
  - 最后统一聚合到同一个 GitHub Release
- `workflow_dispatch` 时：
  - 可以分别勾选 `build_android`
  - 可以分别勾选 `build_windows`
  - `publish_release=true` 时统一上传所选平台产物

### 当前 release 聚合方式

工作流内部会拆成三层：

1. `metadata`
   - 解析版本号、tag 和启用的平台
2. `export-targets`
   - 以矩阵方式分别构建 Android / Windows
3. `release`
   - 下载所有矩阵产物
   - 统一上传到同一个 release

## workflow_dispatch 冒烟说明

当前建议把冒烟验证和正式发版分开：

- 冒烟验证：
  - `publish_release=false`
  - 只检查构建、产物和 artifact 上传
- 正式发版：
  - `publish_release=true`
  - 把所选平台产物统一挂到同一个 GitHub Release

### GitHub 页面手动触发

在 Actions 页面手动触发时，建议优先使用以下组合：

- Android + Windows 双平台冒烟
  - `build_android=true`
  - `build_windows=true`
  - `publish_release=false`
  - `prerelease=true`
- 只做 Windows 冒烟
  - `build_android=false`
  - `build_windows=true`
  - `publish_release=false`
  - `prerelease=true`
- 只做 Android 冒烟
  - `build_android=true`
  - `build_windows=false`
  - `publish_release=false`
  - `prerelease=true`

### gh CLI 触发示例

双平台冒烟：

```powershell
gh workflow run ".github/workflows/android-export.yml" `
  -f build_android=true `
  -f build_windows=true `
  -f publish_release=false `
  -f prerelease=true
```

只跑 Windows：

```powershell
gh workflow run ".github/workflows/android-export.yml" `
  -f build_android=false `
  -f build_windows=true `
  -f publish_release=false `
  -f prerelease=true
```

只跑 Android：

```powershell
gh workflow run ".github/workflows/android-export.yml" `
  -f build_android=true `
  -f build_windows=false `
  -f publish_release=false `
  -f prerelease=true
```

### gh CLI 结果检查

触发后建议按这个顺序检查：

1. 查看最近几次运行：

```powershell
gh run list --workflow ".github/workflows/android-export.yml" --limit 5
```

2. 查看某次运行详情：

```powershell
gh run view <run-id>
```

3. 如需看失败日志：

```powershell
gh run view <run-id> --log-failed
```
