# 交互与拖拽调试记录

## 2026-04-04 交互规则模型重构

### 问题现象

在一版拖拽实现中，出现了这样的问题：

- 被上下或左右锁住的牌，仍然可能作为拖拽碰撞目标被消除

这说明问题不只是某个 `if` 条件漏写，而是规则模型本身已经分叉：

- 点击链路要求目标牌可动
- 拖拽链路只要求目标牌同牌面且接触到

两条输入链路实际使用了两套不同的“消除合法性”定义。

### 重构目标

这轮不做补丁式修正，而是把以下概念正式拆开：

1. 输入命中
2. 几何接触
3. 业务合法性

### 实现结果

新增：

- `godot/scripts/board/TileInteractionRules.cs`

核心变化：

- 新增 `TileInteractionState`
  - 保留 `above / left / right / top / bottom` 各方向阻塞信息
- 新增 `TileInteractionRules.Evaluate(...)`
  - 统一评估单张牌当前是否自由
- 新增 `TileInteractionRules.TryValidateMatchPair(...)`
  - 统一判断两张牌是否允许配对
- `BoardController.HandleTileClicked(...)`
  - 不再自行维护一套独立配对合法性
- `BoardController.FindDragMatchTarget(...)`
  - 只负责“候选目标几何筛选 + 统一规则过滤”
- `BoardController.TryStartMatch(...)`
  - 成为点击和拖拽共用的配对入口

### 设计结论

本轮确定了一个后续必须坚持的约束：

- 任何输入方式都不能绕过统一配对规则层

也就是说，以后无论是：

- 点击
- 拖拽
- 提示系统
- 自动求解
- 可解性分析

都应复用同一套“当前哪些牌允许参与配对”的规则入口，而不是各自复制判断。

### 验证

- `dotnet build godot/TileMatcher.sln`
- 结果：`0` warning，`0` error

## 2026-04-04 拖拽交互快照补充

### 新问题

在统一配对规则收敛后，又暴露出一个更细的交互问题：

- 顶层牌已经被成功拿起拖拽
- 但下层原本被它压住的同牌面牌，仍然没有及时变成可参与消除状态

根因不是命中容差，而是当时的规则评估仍然基于“完整静态棋盘”：

- 被拖拽牌虽然视觉上已经被拿起
- 但逻辑上仍然参与阻塞关系计算

### 设计调整

这轮没有采用“鼠标每移动一帧就重算所有麻将真实状态”的方案，
因为那会把拖拽中的视觉位置误当成真实棋盘拓扑，导致规则抖动。

改为引入更稳定的模型：

- 正常状态使用静态棋盘快照
- 一旦成功进入拖拽态，就切换到“拖拽交互快照”
- 拖拽交互快照会临时把拖拽源牌从阻塞判定中排除
- 拖拽结束或消除完成后，再恢复正常快照

### 实现结果

`BoardController` 中新增：

- `GetInteractionTiles()`
- `BeginDragInteractionSnapshot(...)`
- `EndDragInteractionSnapshot()`

当前规则变为：

- 拖拽开始时：刷新一次全场交互状态
- 拖拽进行中：基于稳定的拖拽快照做判定
- 拖拽结束时：恢复正常棋盘快照并重新刷新

### 设计结论

本轮进一步明确：

- 应刷新的是“交互快照”
- 不是“每帧按鼠标位置改写棋盘拓扑”

## 2026-04-04 失败交互反馈补充

### 背景

在成功消除链路逐步完整后，失败链路开始显得反馈不足：

- 点中被锁住的牌，看起来像“没反应”
- 试图拖起被锁住的牌，也缺少明确拒绝反馈
- 拖着一张自由牌去碰一张被锁住的目标牌时，玩家不容易理解失败原因

### 本轮目标

建立一条统一的失败反馈系统，而不是在各个输入分支里零散拼接提示。

### 设计拆分

本轮把失败反馈拆成三层：

1. 规则层
   - `TileInteractionRules` 负责把阻塞状态转换为结构化原因
2. 控制层
   - `BoardController` 负责统一分发失败反馈
3. 表现层
   - `TileView` 负责牌本体闪烁
   - `GameScene` 负责顶部 tip

### 新增内容

- `TileBlockReason`
- `MatchFailureKind`
- `MatchValidationResult`
- `BoardController.InteractionTipRequested`
- `TileView.PlayBlockedFeedback(...)`
- `GameScene` 顶部中央交互 tip

### 当前表现方案

本轮明确不使用锁图标，统一改用颜色反馈：

- 上层压住：顶部边缘橙色闪烁
- 左右锁住：左右边缘黄色闪烁
- 上下锁住：上下边缘蓝色闪烁
- 同时叠加一次短促回弹和面闪

### 当前接入点

失败反馈已接入三个入口：

1. 点击一张被锁住的牌
2. 尝试拖起一张被锁住的牌
3. 已经进入拖拽或点击配对，但统一规则校验失败

### 后续约束

后续继续调整“手感”时，应优先改：

- 颜色
- 时长
- 回弹幅度
- tip 停留时间

而不是重新把失败文案或失败表现散落回点击 / 拖拽分支中。

## 2026-04-04 消除反馈强化与配置化

### 变更目标

本轮不是继续改“能不能消除”的业务逻辑，而是专门强化“消除成功瞬间的表现反馈”：

- 碰撞瞬间增加白色闪光 / 小范围爆点
- `+100` 改成更像手游反馈的样式
- 分数字号继续放大
- 增加描边，避免在浅色牌面上不清晰
- 增强弹跳感，而不是简单线性缩放
- 尽可能把相关参数资源化，方便后续直接在 Inspector 里调

### 实现方案

新增：

- `godot/scripts/config/MatchFeedbackConfig.cs`
- `godot/configs/effects/default_match_feedback.tres`

`BoardController` 中原本属于表现层的参数，开始统一从 `MatchFeedbackConfig` 读取，主要覆盖：

- `DragContactTolerance`
- 消除三段式动画时长
- 预备位展开距离与抬升高度
- 碰撞染色
- 爆点大小 / 时长 / 透明度
- 分数字体大小 / 描边 / 弹跳 / 上浮距离
- 单次消除分数

### 结果

当前消除表现链路变为：

1. 两张牌先左右展开到预备位
2. 飞向中点碰撞
3. 碰撞瞬间出现白色爆点
4. 同时弹出更大的 `+100`，带描边和两段弹跳
5. 两张牌再缩小淡出

### 设计结论

本轮再次确认了一条边界：

- “是否允许配对 / 是否算命中”是逻辑问题
- “命中容差多大 / 成功后反馈多强”是表现问题

因此即使 `DragContactTolerance` 会影响手感，也仍然归入 `MatchFeedbackConfig`，而不归入 `LayoutRules`。

### 验证

- `dotnet build godot/TileMatcher.sln`
- 结果：`0` warning，`0` error

## 背景

在游戏页已经具备：

- 固定原型布局
- 随机布局生成
- 层过滤调试
- 可动状态可视化

之后，项目开始进入第一轮真实玩法交互验证。

这一阶段的目标不是一次性做完最终拖拽体验，而是先让“可动牌可交互、相同牌可消除”这条链路跑通，并且在出现异常时能快速定位。

## 目标

本轮交互阶段的目标分为三步：

1. 先跑通可动判定
2. 先做可验证的点击配对
3. 在点击链路稳定后，再接最小可拖拽链路

这个顺序是刻意选择的，因为如果一开始就直接做完整拖拽，排查成本会非常高，很难分清：

- 是输入没进来
- 是牌不可动
- 是命中错了
- 还是目标判定失败

## 问题 1：点击后看起来“没有反应”

### 现象

用户点击麻将后，感觉麻将没有任何明显交互效果，也无法确认输入到底有没有进入逻辑层。

### 原因

当时代码只有很少的日志，无法快速判断：

- 点击有没有进入 `BoardController`
- 命中的到底是哪张牌
- 这张牌是否可动
- 当前流程是进入点击选中，还是因为不可动直接返回

### 解决方案

在 `BoardController` 中补充结构化日志，只在关键业务节点打印：

- 左键按下
- 命中检测结果
- 点击处理
- 可动判定摘要
- 选中切换
- 消除完成

明确避免在高频更新路径里重复打印。

### 当前结论

交互排查必须保留“关键节点日志”这套策略，否则 Godot 输出窗口虽然有信息，但没有定位价值。

## 问题 2：拖拽失败的真实原因不是“没命中”，而是“根本没实现”

### 现象

用户点击某张可移动麻将后，尝试用鼠标左键拖拽，但牌没有跟着移动。

### 原因

通过日志确认后发现，当时系统只有：

- 点击选中
- 点击取消选中
- 点击第二张同牌面牌后消除

还没有真正实现：

- 按下后进入拖拽候选态
- 鼠标移动超过阈值后进入拖拽态
- 松手时检测目标牌

也就是说，问题不是“拖拽逻辑坏了”，而是“拖拽逻辑尚未接入”。

### 解决方案

补齐最小拖拽链路：

1. 鼠标左键按下时记录 `_pressedTile`
2. 鼠标移动距离超过阈值时进入 `_draggingTile`
3. 拖拽期间让牌跟随鼠标移动
4. 鼠标松开时检测是否与另一张“可移动且同牌面”的牌主体矩形相交
5. 命中则消除，未命中则回到原位

同时保留原有点击配对链路，作为拖拽失败时的兜底输入模式。

### 当前结论

“点击配对”不是临时代码，而是拖拽调试阶段非常重要的兜底交互模型。

## 问题 3：拖拽过程中调试器报错

### 现象

拖拽刚开始时，Godot 调试器报错，运行时日志中出现：

- `Condition "p_z > RenderingServer::CANVAS_ITEM_Z_MAX" is true.`

### 原因

为保证被拖拽的牌显示在最上层，拖拽开始时曾把牌的 `ZIndex` 提升得过高，超过了 Godot `CanvasItem` 的允许上限。

### 解决方案

把拖拽抬层策略改成安全实现：

- 使用较小的 `DragLiftZBoost`
- 增加 `SafeMaxDragZIndex`
- 在真正设置 `ZIndex` 前做 `Min` 夹取

并在日志中打印：

- 原始 `ZIndex`
- 抬升后的 `ZIndex`

方便再次排查同类问题。

### 当前结论

拖拽中的“视觉抬层”也属于需要显式受限的业务逻辑，不能默认无限增大。

## 当前形成的交互约束

截至当前阶段，项目已经形成以下交互层约束：

- 只有 `Movable == true` 的牌才允许被点击选中或进入拖拽
- 点击模式与拖拽模式共存
- 拖拽只在移动距离超过阈值后才真正开始
- 拖拽命中目标时，当前只使用“主体矩形相交”作为最小判定
- 拖拽失败时牌必须回到起始位置
- 调试日志只打在关键状态切换点，不在高频路径刷屏

## 当前结论

本轮交互实现并没有追求最终手感，而是优先建立了一条可排查、可验证、可逐步增强的最小交互链路：

- 可动判定
- 点击配对
- 最小拖拽
- 结构化日志

这套链路已经足够支撑下一轮迭代继续优化：

- 碰撞判定
- 吸附手感
- 拖拽视觉反馈
- 更复杂的阻挡规则

## 后续待验证

后续仍需要继续验证：

- 当前“矩形相交”是否过于严格，是否需要吸附判定
- 拖拽中的牌是否需要半透明、阴影或缩放反馈
- 当前可动判定是否需要继续演进成更细的方向性移动规则
- 拖拽时是否要区分“可碰撞目标高亮”和“不可碰撞目标忽略”
