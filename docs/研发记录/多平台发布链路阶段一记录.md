# 多平台发布链路阶段一记录

## 背景

仓库原先已经把 Android 导出链路固定下来，但多平台发布仍然停留在口头设计阶段：

- 目标上想支持 Android、Web、Windows
- 实现上只有 Android 真正接通
- 统一入口脚本和 Windows 导出脚本还不存在

这使得“多平台发布”虽然方向明确，但没有形成可以直接复用的工程入口。

## 目标

这轮工作的目标不是一次性补完全部平台，而是把第一阶段的链路固定成可执行状态：

1. 补出 Windows Desktop 导出预设
2. 补出 Windows 本地导出脚本
3. 补出统一入口 `build-release.ps1`
4. 把 Web 的真实阻塞点明确写进脚本和文档

## 关键发现

### 1. 当前 Web 不是“差一点就能接通”

在动手实现前，先核实了当前项目的技术前提：

- 本项目是 Godot 4.6.1 Mono + C#
- 官方文档当前明确说明 Godot 4 的 C# 项目不能导出到 Web

这意味着 Web 当前不是“再补一个 preset 和脚本就能通”，而是存在引擎级约束。

因此这轮没有伪造一个看起来存在、实际上必挂的 Web 真导出流程，而是把 `build-web.ps1` 设计成显式报错入口。

## 实施内容

### 1. 导出预设

新增了：

- `godot/export_presets.cfg`
  - `Windows Desktop`

没有把 `Web` 当成真实可用 preset 落地到正式链路里，避免误导后续使用者。

### 2. 脚本层

新增了：

- `scripts/build-common.ps1`
  - 统一公共辅助逻辑
- `scripts/build-windows.ps1`
  - Godot 导出
  - 清理临时文件
  - zip 打包
  - `sha256` 生成
- `scripts/build-web.ps1`
  - 对当前 C# Web 阻塞点做显式说明
- `scripts/build-release.ps1`
  - 统一入口
  - 当前默认目标为 `android,windows`

同时补强了：

- `scripts/build-android.ps1`
  - 现在会直接生成 `sha256` 文件
  - 结尾改为 `return`，便于被统一入口调用

## 真实技术问题

### 1. Windows 导出不是同步落文件

第一次实现 `build-windows.ps1` 时，遇到一个不明显的问题：

- Godot 进程已经返回
- 但目标 `.exe` 还没有立刻出现在导出目录

如果脚本在这个时间点直接断言产物存在，就会误判失败。

最终处理方式是：

- 在公共层增加“等待导出产物稳定”的步骤
- 等待目标文件出现并稳定一小段时间后，再进入打包阶段

### 2. 当前环境是 Windows PowerShell 5.1

初版脚本使用了 `System.IO.Path.GetRelativePath()`，但当前 PowerShell 运行时没有这个 API。

最终改为：

- 使用 `System.Uri.MakeRelativeUri()` 计算相对路径

这样脚本可以兼容当前仓库实际使用的 PowerShell 环境。

## 验证结果

这轮至少完成了以下验证：

- `build-web.ps1`
  - 会明确报出当前 Godot C# Web 导出受阻
- `build-windows.ps1`
  - 已成功生成 Windows zip 产物和 `sha256`
- `build-release.ps1 -Targets windows`
  - 已成功跑通统一入口到 Windows 产物

当前产物路径为：

- `godot/build/windows/TileMatcher-0.1.5-windows-x64.zip`
- `godot/build/windows/TileMatcher-0.1.5-windows-x64.zip.sha256.txt`

## 当前结论

多平台发布链路的第一阶段已经从“讨论方案”进入“仓库内可执行”状态，但结论需要明确分层：

- Android：已接通
- Windows：已接通
- Web：当前被 Godot 4 C# 导出限制阻塞

因此统一入口现在默认只构建：

- `android`
- `windows`

这不是退回原方案，而是把“想支持的目标”和“当前确实能稳定出包的目标”分开处理。

## 后续建议

下一阶段建议按以下顺序继续：

1. 把 GitHub Actions 改成多目标矩阵
2. 让 release 聚合 Android 与 Windows 产物
3. 单独决定 Web 是否需要改技术路线
