# 外围流程与可解关卡演进记录

## 记录目标

本文档记录两类近期关键演进：

- 项目如何从“只有游戏场景”的原型，演进到“主页 -> 游戏页 -> 结算页”的外围流程骨架
- 随机布局如何从“只生成堆叠结构”，演进到“保证至少存在一条可通关路径”

## 一、外围流程从单场景原型到正式骨架

### 初始状态

项目早期主要围绕 `GameScene + BoardController` 迭代：

- 可以看到牌桌
- 可以随机生成布局
- 可以做拖拽和消除验证

但此时仍然存在明显问题：

- 没有主页
- 没有正式结算页
- 项目入口仍等同于单个游戏场景
- 很难验证完整单关流程和后续打包骨架

### 设计判断

当局内玩法已经足够复杂后，继续把主页、结算页和未来加载页堆回 `GameScene` 会导致职责混乱。

因此决定引入外围流程层，并以 `AppRoot` 作为总入口。

### 落地结果

已新增：

- `AppRoot`
- `HomePage`
- `LevelCompletePage`
- `LevelCompleteResult`

主流程调整为：

1. 进入主页
2. 开始关卡
3. 局内通关
4. 打开结算页
5. 点击继续直接进入下一关

### 一个关键实现决定

页面间数据传递没有强行使用 Godot Signal 来承载自定义 DTO，而是使用普通 C# 事件。

原因：

- Godot C# signal 对复杂参数类型不够友好
- 普通 C# 事件更适合页面流转层传递结算数据

## 二、关卡配置从硬编码走向资源化

### 问题背景

如果 `GameScene` 里直接写死：

- 当前关卡号
- 使用哪套规则
- 走原型还是随机生成

那么后续每增加一关都要改代码，工程扩展性很差。

### 设计结论

把单关参数收束为资源配置：

- `LevelConfig`
- `LevelCatalog`
- `LevelLayoutSourceMode`

这样外围流程只关心“进入第几关”，而不关心每关内部细节。

### 当前收益

- 主页可以显示当前关卡摘要
- 结算页可以显示下一关预告
- `GameScene` 可以按关卡号启动正式关卡
- 后续扩关基本不需要改页面流转代码

## 三、随机布局从“几何可看”到“至少可解”

### 原始问题

之前的随机布局更偏向几何原型验证，重点是：

- 牌能不能堆起来
- 层间关系对不对
- 支撑和偏移是否合理

但这并不等于“生成的关卡一定能通关”。

### 风险

如果随机布局没有可解性约束，就可能出现：

- 牌面分配后某一关无解
- 测试看起来像能玩，但实际上无法清空
- 第二关、第三关开始出现稳定卡死

这会直接阻断正式流程验证。

### 设计方案

新的生成策略改为：

1. 先生成合法的纯几何布局
2. 在该布局上模拟“当前规则下哪些牌可参与消除”
3. 尝试构造完整移除顺序
4. 只有构造成功，才为每一对牌分配同样牌面

### 关键点

这里依赖的不是“凭经验猜哪两张可以配”，而是统一复用交互规则模型中的可参与判定能力。

这使生成器和运行时规则尽量保持一致。

### 当前保证的内容

当前阶段保证：

- 生成结果至少存在一条完整通关路径

当前阶段还没有保证：

- 难度梯度
- 多解空间
- 教学性或策略性

这些属于后续更上层的关卡设计问题。

## 四、本轮演进的工程价值

这一轮改动的意义不只是“多了主页和下一关”，更重要的是把项目结构拉直了：

- 外围流程不再和局内牌桌耦合
- 关卡入口不再靠代码硬写
- 随机关卡不再只是调试结构，而能真正用于单关流程验证

从工程视角看，这一轮是项目从“玩法原型”迈向“可串流程原型”的关键节点。

## 五、后续建议

基于当前结果，后续优先顺序建议为：

1. 在现有关卡配置基础上继续完善正式关卡内容
2. 再补加载页、奖励页、个人信息页等外围页面
3. 最后再进入打包与渠道适配阶段

原因是：

- 外围骨架已经具备
- 可解关卡生成已经可用
- 现在最有价值的是继续补足正式单关体验，而不是再次回到入口架构层
