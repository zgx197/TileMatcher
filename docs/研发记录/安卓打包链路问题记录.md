# 安卓打包链路问题记录

## 背景

项目已经具备 Godot 4.6.1 Mono + C# 的安卓导出能力，但在最近一轮真机验证中出现了一个非常隐蔽的问题：

- APK 的 `versionName / versionCode` 是新的
- AndroidManifest 中的方向声明也是新的
- 但真机运行出来的页面逻辑和 DEBUG 面板内容却还是旧版本

这说明问题不在“包有没有重新生成”，而在“真正被打进包里的运行时资源是不是当前代码对应的那一份”。

## 现象

本轮排查中出现过以下现象：

- `0.1.5` 的包已经能正常安装
- 真机上看不到最新加入的 DEBUG 面板内容
- Windows 编辑器里运行却能看到最新逻辑
- 同一个版本号在不同运行环境下表现不一致

这类现象很容易误导成：

- 手机安装了旧包
- AndroidManifest 没生效
- Godot 在安卓上加载了错误场景

但这些都不是根因。

## 关键定位过程

### 1. 对比本地编译 DLL 与实际进包 DLL

排查时直接比较了两份程序集：

- 本地最新 C# 编译产物  
  `godot/.godot/mono/temp/bin/Debug/TileMatcher.dll`
- Android 模板资源目录中的发布产物  
  `godot/android/build/src/main/assets/.godot/mono/publish/arm64/TileMatcher.dll`

结果发现：

- 两者时间戳不同
- 两者文件大小不同
- 两者哈希不同

这说明 APK 真正运行的程序集并不是当前最新代码编译出来的那一份。

### 2. 确认不是单个 DLL 旧，而是整份 assets 快照都旧

继续检查后发现这些文件也停留在旧时间点：

- `project.binary`
- `assets.sparsepck`
- `android/build/src/main/assets/` 下的大量导出资源

说明问题并不是“Gradle 只漏掉了 DLL”，而是整套 Android 导出资源快照都没有被刷新。

### 3. 直接调用 Godot 正式导出验证

随后改为执行 Godot 自己的导出流程：

```powershell
Godot_v4.6.1-stable_mono_win64.exe --headless --path <project> --export-debug Android <apk>
```

这一步执行后，以下文件会立即刷新到最新时间：

- `godot/android/build/src/main/assets/.godot/mono/publish/...`
- `godot/android/build/src/main/assets/project.binary`
- `godot/android/build/src/main/assets/assets.sparsepck`

这说明真正负责刷新导出资源的，不是后面的 Gradle 打包动作，而是 Godot 自己的 export 流程。

## 根因

根因是我们一开始走了错误的打包路径：

- 直接在 `godot/android/build/` 上执行 Gradle 打包
- 但没有在打包前先触发 Godot 导出

这样 Gradle 只会拿现成的 `src/main/assets` 快照继续封包，而不会主动刷新：

- C# publish 产物
- `project.binary`
- `assets.sparsepck`
- 最新场景和资源 remap

于是就出现了：

- 包名和版本号是新的
- 但真正运行的游戏内容仍是旧的

## 解决方案

最终确定的正确链路是：

1. 先同步版本号、包名、方向等构建元数据
2. 使用 Godot `--headless --export-debug` 执行正式安卓导出
3. 让 Godot 刷新 `android/build/src/main/assets` 里的最新导出资源
4. 对 Godot 导出的 APK 做签名
5. 用 `apksigner` 和 `aapt` 做最终校验

已经落地为脚本：

- [构建与发布说明](../构建与发布说明.md)
- [build-android.ps1](../../scripts/build-android.ps1)

## 工程约束

从这次问题之后，项目形成了一条必须遵守的工程约束：

- 不能再把“直接跑 Gradle”当作安卓正式出包流程
- 必须先走 Godot export，再做签名和校验

换句话说：

- `Gradle` 负责“封装 Android 工程”
- `Godot export` 才负责“刷新当前项目的真实运行资源”

这两者不能混为一谈。

## 对 GitHub Actions 的影响

这次问题也直接影响后续 CI 设计：

- GitHub Actions 不能只执行 `gradlew assembleMonoDebug`
- 必须复用本地已经验证过的 `build-android.ps1`
- CI 和本地必须走同一条导出链路，否则极易出现“本地正常、CI 产物过期”的分叉

因此仓库中新增了 Actions 骨架：

- `.github/workflows/android-export.yml`

## 当前结论

当前这条链路已经验证通过：

- Godot 正式导出的 APK 与最新代码一致
- 签名后的 APK 可安装
- `aapt badging` 能正确读到版本号与包名

后续如果再次出现“版本号是新的，但逻辑像旧包”的情况，优先检查以下三点：

1. 是否真的先执行了 Godot export
2. `android/build/src/main/assets/.godot/mono/publish/.../TileMatcher.dll` 是否刷新
3. 最终安装的 APK 是否来自脚本产物而不是旧的手工复制包
