# 牌局分析台与服务化工作台设计

## 文档目标

本文档用于明确 TileMatcher 后续面向策划与研发的“牌局内容生产工作台”设计方向。

它不是玩家页面设计，也不是 Godot 运行时 UI 设计，而是：

- 离线牌局构造与评估结果的浏览台
- 策划筛选、标注与编排工作台
- 正式关卡导出前的内容生产入口

本文档重点回答以下问题：

- 为什么当前静态分析页最终应升级为本地网页服务
- 服务化工作台和 Godot 运行时各自负责什么
- 批次、候选、人工标注、正式关卡池之间如何组织
- 本地服务端、前端和离线工具链应如何分层
- 第一阶段 API、数据产物和页面结构应如何定义

## 当前结论

当前项目正式不再把 Web 分析台仅理解为：

- 一个离线导出的静态 HTML 页面

而应进一步演进为：

**牌局内容生产工作台**

如果从实现形态描述，也可以理解为：

**本地离线牌局分析与正式关卡编排服务**

这一定义和普通网站、后台管理系统、玩家前端都不同。

它的服务对象是：

- 离线牌局构造器
- 自动筛选器
- 策划筛选与人工复核
- 研发分析与回归
- Godot 正式关卡导出链路

## 系统定位

### 1. 这不是玩家页面

该工作台不直接面向玩家，因此不需要承担：

- 游戏流程展示
- 玩家账户系统
- 商业化页面
- 正式游戏级美术还原

它首先是内部工具。

### 2. 这也不是离线求解器本体

工作台不负责重新实现离线构造与评估算法。

离线工具链依然负责：

- 批量生成候选牌局
- 运行可解性验证
- 计算评估指标
- 自动筛选
- 导出批次产物

工作台负责：

- 浏览这些结果
- 对它们进行人工标记、筛选与编排
- 在需要时生成正式关卡导出结果

### 3. 这是内容生产入口

该工作台的核心目标不是“把数据展示出来”这么简单，而是成为：

- 牌局候选池的统一浏览入口
- 难度与风险的分析入口
- 策划人工标注入口
- 正式关卡池编排入口

## 为什么要从静态页升级为服务化工作台

当前静态分析页已经证明了一件事：

- 离线批次结果确实需要一个可视化浏览入口

但如果继续长期停留在静态 HTML 形态，会逐步遇到以下问题：

### 1. 人工标记无法稳定落盘

浏览器 `localStorage` 只能做非常轻量的临时标记，不适合：

- 跨机器共享
- 长期积累
- 按批次回溯
- 正式关卡编排

### 2. 批次切换和多批次比较会变重

当后续存在多批离线结果时，仅靠单个静态页面很难优雅支持：

- 批次列表
- 当前默认批次
- 多批次统计对比
- 重复候选追踪

### 3. 正式关卡编排需要可写层

一旦进入“从候选池中挑出正式关卡池”的阶段，系统需要保存：

- 保留
- 淘汰
- 备注
- 标签
- 顺序编排

这些信息不应回写原始分析 JSON，而应有独立可写层。

### 4. 列表与详情查询应分层

当候选量持续变大时：

- 列表页只需要摘要字段
- 详情页才需要完整布局和细节指标

服务化后更适合按需读取，而不是每次整个页面一次性加载所有大对象。

## 设计原则

### 1. 离线批次是只读源

离线工具导出的批次产物应视为只读来源。

工作台不应直接改写：

- 原始候选数据
- 原始评估结果
- 原始自动筛选结果

### 2. 人工标记是增量层

策划和研发的人工判断应作为独立数据层存在，而不是污染原始候选数据。

例如：

- 保留
- 待复核
- 淘汰
- 适合教学
- 适合盖牌
- 备注

### 3. Godot 运行时继续保持解耦

工作台和 Godot 运行时之间仍然只通过导出数据协作。

Godot 不负责：

- 候选池浏览
- 策划标注
- 候选筛选
- 正式关卡编排

Godot 仍只负责：

- 按目录读取正式关卡数据
- 在运行时加载与消费

### 4. 先查询与标记，再做在线重算

第一阶段不应把重点放在：

- 浏览器内重新生成牌局
- 浏览器内重新计算全量评估

第一阶段更重要的是：

- 先稳定读取批次
- 先稳定筛选与查看
- 先稳定落盘人工标记
- 先稳定输出正式关卡池

### 5. 默认本地单机，不先做重后台

当前阶段更适合采用：

- 本地 Node 服务
- 本地文件数据
- 简单 API
- 本地浏览器前端

而不是一开始引入：

- 复杂用户权限系统
- 远程数据库
- 多人协作后台
- 云端部署体系

## 系统总架构

当前推荐采用三条清晰链路：

1. 离线生产链路
2. 本地工作台服务链路
3. Godot 运行时消费链路

推荐的数据流为：

1. `.NET` 离线工具批量生成候选、评估和筛选
2. 离线工具导出批次产物
3. 本地网页服务读取批次产物
4. 策划与研发在工作台中做浏览、标记、编排
5. 工作台生成正式关卡导出草案或正式导出目录
6. Godot 运行时继续只消费最终正式关卡目录

也就是说：

- 离线工具是“计算核心”
- 工作台是“内容生产入口”
- Godot 是“运行时消费者”

## 数据产物设计

### 1. 当前问题

当前 `candidates.json` 足以支撑离线导出和最小静态分析页，但不适合作为长期服务化查询的唯一载体。

主要问题是：

- 列表页和详情页数据耦合过重
- 单文件会持续变大
- 图表聚合和批次摘要需要服务端二次扫描

### 2. 推荐的批次目录结构

未来每个批次更适合导出为：

```text
artifacts/batches/<batch-id>/
├─ manifest.json
├─ analysis/
│  ├─ summary.json
│  ├─ candidates.index.json
│  ├─ accepted.index.json
│  ├─ needs-review.index.json
│  ├─ charts.json
│  └─ candidates/
│     ├─ candidate_0001_xxx.json
│     ├─ candidate_0002_xxx.json
│     └─ ...
└─ runtime-levels/
   ├─ level-catalog.json
   └─ levels/
```

### 3. `manifest.json`

该文件用于描述批次本身。

推荐至少包含：

- `BatchId`
- `BatchName`
- `GeneratedAtUtc`
- `CandidateCount`
- `AcceptedCount`
- `NeedsReviewCount`
- `RejectedCount`
- `RulesSnapshot`
- `FilterSnapshot`
- `Paths`

### 4. `candidates.index.json`

该文件用于列表页高频查询。

推荐至少包含：

- `CandidateId`
- `BatchIndex`
- `Seed`
- `Decision`
- `DifficultyBucket`
- `RecommendationScore`
- `TileCount`
- `LayerCount`
- `InitialBranchCount`
- `AverageBranchCount`
- `DeadEndRate`
- `RandomPlaySurvivalRate`
- `Tags`
- `RuntimeLevelNumber`
- `HiddenFaceCount`
- `Bounds`
- `DetailFile`

### 5. `candidates/<id>.json`

该文件用于详情页。

推荐至少包含：

- `Layout`
- `Evaluation`
- `FilterResult`
- `PreviewMeta`

后续可继续扩展：

- `LayerHistogram`
- `MovableCurveSummary`
- `PairTypeDistribution`
- `DerivedNotes`

### 6. `charts.json`

该文件用于预聚合图表。

推荐至少包含：

- 推荐分分布
- 死局率分布
- 随机存活率分布
- 难度桶统计
- 标签统计
- 牌数 / 层数散点数据

## 可写数据层设计

### 1. 原则

工作台上的人工标记、筛选预设和导出草案应独立于批次原始产物。

这意味着：

- 不改写原始批次 JSON
- 不改写离线评估结果
- 不把人工判断混入候选详情文件

### 2. 推荐存储位置

当前阶段推荐使用：

```text
storage/workbench/
```

### 3. `reviews.json`

该文件用于保存人工标记和备注。

推荐结构示意：

```json
{
  "mvp-batch-2026-04-06": {
    "candidate_0042_46534889": {
      "mark": "keep",
      "labels": ["good_for_intro"],
      "comment": "结构稳定，适合前期正式关卡",
      "updatedAt": "2026-04-06T16:20:00+08:00"
    }
  }
}
```

### 4. `presets.json`

该文件用于保存策划筛选预设。

推荐结构示意：

```json
{
  "easy-screening": {
    "decision": ["AutoAccept", "NeedsReview"],
    "difficultyBucket": ["easy_core", "normal_core"],
    "minScore": 0.62,
    "excludeTags": ["high_dead_end_risk"]
  }
}
```

### 5. `workspace.json`

该文件用于保存工作台本地状态，例如：

- 当前默认批次
- 最近筛选条件
- 最近对比候选
- 当前视图偏好

### 6. 后续数据库演进

当前阶段先用 JSON 就足够。

后续如果批次数量和候选量明显变大，再考虑迁移到：

- SQLite

但这不应反向影响第一阶段的批次产物格式设计。

## 服务端职责

服务端的职责应严格收敛，不应承接离线求解器的计算逻辑。

当前推荐只承担以下五类职责：

### 1. 批次发现

负责扫描：

- `artifacts/batches/*/manifest.json`

### 2. 查询聚合

负责读取索引文件并完成：

- 列表筛选
- 排序
- 分页
- 图表聚合返回

### 3. 详情读取

负责按候选编号读取：

- 单局详情
- 单局布局
- 单局预览数据

### 4. 可写层落盘

负责保存：

- 人工标记
- 备注
- 筛选预设
- 收藏与保留状态

### 5. 正式关卡导出

负责根据工作台中的保留和排序结果：

- 生成导出草案
- 生成正式运行时目录

## API 设计建议

当前推荐的第一阶段 API 如下。

### 1. 批次与启动

- `GET /api/bootstrap`
  - 返回可用批次、默认批次、全局标签集合、筛选选项、工作台状态

- `GET /api/batches`
  - 返回批次列表

- `GET /api/batches/:batchId/overview`
  - 返回批次摘要和图表聚合数据

### 2. 候选查询

- `GET /api/batches/:batchId/candidates`
  - 支持：
  - `decision`
  - `difficultyBucket`
  - `tag`
  - `mark`
  - `minScore`
  - `maxScore`
  - `sort`
  - `page`
  - `pageSize`
  - `q`

- `GET /api/batches/:batchId/candidates/:candidateId`
  - 返回单局完整详情

- `GET /api/batches/:batchId/candidates/:candidateId/preview`
  - 返回前端预览所需的简化布局数据

### 3. 人工标记

- `GET /api/batches/:batchId/reviews`
- `PUT /api/batches/:batchId/reviews/:candidateId`
- `DELETE /api/batches/:batchId/reviews/:candidateId`

### 4. 筛选预设

- `GET /api/presets`
- `POST /api/presets`
- `PUT /api/presets/:presetId`
- `DELETE /api/presets/:presetId`

### 5. 正式关卡导出

- `GET /api/batches/:batchId/runtime-levels`
  - 查看当前批次哪些候选已进入正式关卡目录

- `POST /api/batches/:batchId/exports/runtime-selection`
  - 根据当前保留与排序结果生成新的导出草案

- `POST /api/exports/:exportId/commit`
  - 将导出草案真正写入正式运行时目录

## 前端页面结构建议

当前推荐第一阶段工作台至少包含五个核心工作区。

### 1. 批次总览

用于查看：

- 当前批次摘要
- 候选总数
- `AutoAccept / NeedsReview / AutoReject` 统计
- 推荐分、死局率、随机存活率分布图

### 2. 候选浏览器

用于：

- 列表浏览
- 多条件筛选
- 多列排序
- 标记保留 / 待复核 / 淘汰

### 3. 候选详情页

用于：

- 查看单局核心指标
- 查看自动筛选结论
- 查看标签与风险
- 查看牌桌结构预览
- 添加备注

### 4. 候选对比页

用于：

- 2 到 4 局并排对比
- 对比结构规模
- 对比分支、死局率、存活率
- 对比标签和预览图

### 5. 正式关卡编排页

用于：

- 查看当前正式关卡池
- 从候选池加入或移出候选
- 调整关卡顺序
- 检查是否满足目标难度节奏

## 前端组织方式

当前推荐前端采用原生模块化组织，不急于引入过重框架。

推荐模块如下：

- `api.js`
  - 调工作台 API

- `state.js`
  - 保存当前批次、候选列表、详情、标记、对比队列等本地状态

- `actions.js`
  - 负责筛选、切批次、保存标记、加入对比、导出正式池等副作用

- `renderers.js`
  - 负责列表、详情、编排、图表输出

- `preview.js`
  - 负责牌桌 SVG 或 Canvas 预览

- `charts.js`
  - 负责 ECharts 图表封装

- `dom.js`
  - 收口 DOM 节点引用

- `presenters.js`
  - 将状态、标签、风险等数据翻译成用户可读文案

## 为什么当前不建议优先使用 SSE

和会话驱动型系统不同，当前牌局工作台的数据变化主要来自：

- 切批次
- 调筛选器
- 保存人工标记
- 重新导出离线批次
- 提交正式关卡池导出

这些变化并不属于持续高频实时流，因此第一阶段更适合：

- 普通 REST API
- 主动刷新
- 必要时低频轮询

SSE 不是当前必须能力。

## 启动与开发方式建议

当前推荐新增本地 Node 工作台入口。

示例脚本如下：

```json
{
  "scripts": {
    "analysis:start": "node app/server/server.js",
    "analysis:dev": "node app/server/scripts/dev.js",
    "analysis:check": "node app/server/scripts/check.js"
  }
}
```

默认开发地址建议为：

- `http://127.0.0.1:3100`

开发脚本建议负责：

- 启动本地服务
- 健康检查
- 自动打开浏览器
- 复用已启动实例

## 与当前离线工具的接口调整建议

如果正式进入服务化阶段，离线工具侧建议逐步补齐以下输出：

- 保留 `summary.json`
- 保留 `accepted.json`
- 保留 `needs-review.json`
- 新增 `manifest.json`
- 新增 `candidates.index.json`
- 新增 `candidates/<id>.json`
- 新增 `charts.json`

这样做的意义是：

- 列表页不需要反复扫描完整候选详情
- 服务端启动更轻
- 前端首屏更快
- 批次切换更稳定

## 推荐推进顺序

当前建议按以下顺序推进：

1. 先搭本地服务骨架与前端骨架
2. 先接 `GET /api/bootstrap`
3. 先接 `GET /api/batches/:batchId/candidates`
4. 先接 `GET /api/batches/:batchId/candidates/:candidateId`
5. 再把当前静态分析页迁移为模块化前端
6. 再接人工标记可写层
7. 再做候选对比页
8. 再做正式关卡编排与导出草案
9. 最后再评估是否需要更强实时能力或数据库

## 面向 8.5 分正式服务后台的后续迭代计划

### 1. 当前实现定位

基于当前已经落地的版本，工作台已经不再只是“服务骨架”，而是具备以下能力的本地单机内容生产后台：

- 可启动的本地网页服务
- 批次列表、候选列表、候选详情与结构预览
- 人工标记落盘
- 候选对比页
- 正式关卡编排页
- 运行时关卡草案生成、草案预览与提交正式目录

如果按工程成熟度粗略评分，当前更接近：

- `7.0 - 7.5` 分的“可用内部工具”

它已经足够支撑策划和研发进行真实浏览、筛选、编排和导出，但还没有达到严格意义上：

- 写入链路足够稳
- 失败恢复足够清晰
- 自动化回归足够完整
- 模块边界足够稳定
- 可持续扩展成本可控

### 2. 这里所说的“8.5 分正式服务后台”标准

当前文档把“8.5 分正式服务后台”定义为以下状态：

- 核心内容生产链路有明确的原子性或可回滚保障
- 关键操作有可追踪的操作记录、草案记录和提交记录
- 主链路有自动化冒烟测试，至少覆盖“编排 -> 草案 -> 提交”
- 前后端模块边界稳定，新增页面不会持续堆积到单文件中
- 对批次规模增长有基本承载能力，不需要立刻重写架构
- 失败时能快速定位，策划和研发知道“哪一步失败、失败后结果落在哪里”
- 保持本地优先、离线优先、与 Godot 运行时解耦的既定原则

它仍然不是：

- 多人在线协作 CMS
- 云端 SaaS 后台
- 复杂权限系统
- 需要实时推流的任务平台

### 3. 推荐拆分为五个迭代阶段

后续建议不要再按“页面功能点”零散推进，而改为按后台成熟度推进。推荐拆成五个阶段：

1. P1：把正式目录写入链路做稳
2. P2：把批次与草案数据模型做厚
3. P3：把前端页面与状态模块拆清
4. P4：把诊断、日志与操作可观测性补齐
5. P5：把规模承载与长期维护成本压下来

### 4. P1：正式目录提交链路加固

这一阶段的目标不是继续堆页面，而是优先解决“提交正式目录”这件事能不能放心用。

#### 目标

- 把正式目录提交从“基本可用”提升到“失败可恢复”
- 明确每次提交的输入、输出、备份和结果状态
- 给策划一个可放心点击的“提交正式目录”操作

#### 关键改动

- 为 `POST /api/exports/:exportId/commit` 增加提交锁
  - 同一批次同一时刻只允许一个提交操作
- 把正式目录写入改为“预写临时目录 -> 校验 -> 原子替换”优先
  - 如果目标平台或文件系统限制原子替换，则至少实现失败自动回滚
- 为每次提交生成 `commit-manifest.json`
  - 记录 `exportId`
  - 记录 `batchId`
  - 记录提交时间
  - 记录提交条目数
  - 记录备份目录
  - 记录写入结果摘要
- 为草案增加“可提交状态校验”
  - 草案为空禁止提交
  - 草案中的候选缺失详情时禁止提交
  - 批次目录缺失时禁止提交
- 提交完成后返回明确结果
  - 是否成功
  - 正式目录路径
  - 备份目录路径
  - 提交摘要

#### 配套验证

- 新增服务端自动化冒烟脚本
  - 保存编排
  - 生成草案
  - 读取草案
  - 提交正式目录
  - 校验 `level-catalog.json`
  - 校验 `levels/*.json`
- 新增失败路径测试
  - 草案缺失
  - 目标目录不可写
  - 提交中断后的回滚结果

#### 完成标准

- 正式目录提交失败时不会留下半写入目录
- 研发可以通过提交记录快速恢复上一个正式版本
- 冒烟测试可一键跑通

### 5. P2：批次、草案与导出数据模型补强

这一阶段重点是把“现在能写”提升到“后续能持续查、能追溯、能复盘”。

#### 目标

- 让工作台中的编排状态、草案状态、提交状态彼此分层
- 让草案不再只是一个临时 JSON，而是有生命周期的内容对象
- 给后续批次比较、导出历史和复盘留出数据结构空间

#### 关键改动

- 为草案补齐标准元数据
  - `status`
  - `createdBy` 或本地来源标识
  - `committedAt`
  - `committedRuntimeDir`
  - `supersededBy`
- 把当前 `runtime-selections.json` 扩展为更清晰的工作台写层
  - `runtime-selections.json`
  - `exports/*.json`
  - `exports/commits/*`
  - `operations.log.jsonl` 或等价日志
- 为批次补充更多只读索引产物
  - `manifest.json`
  - `candidates.index.json`
  - `charts.json`
  - 后续可选的 `runtime-summary.json`
- 增加导出历史查询 API
  - `GET /api/batches/:batchId/exports`
  - `GET /api/exports/:exportId`
  - `GET /api/exports/:exportId/commit-status`
- 增加“当前正式目录来自哪个草案”的追踪关系

#### 配套验证

- 同一批次连续多次生成草案和提交后，历史可追溯
- 可以明确知道某个正式目录是由哪份草案生成的
- 即使后续重新编排，也不会丢失上一次提交记录

#### 完成标准

- 草案、提交、正式目录三者关系清晰
- 后续做“提交历史页”“导出比较页”不需要返工数据层

### 6. P3：前端模块化重构与工作区稳定化

当前前端已经能用，但继续往一个 `actions.js` 和 `renderers.js` 里堆会越来越难维护。这一阶段要把它从“单文件组织的 MVP”升级为“可扩展工作台前端”。

#### 目标

- 降低新增页面和新增交互的改动成本
- 让候选浏览、对比、编排、草案各自独立演进
- 为后续“候选比较增强页”“导出历史页”“诊断页”留出空间

#### 关键改动

- 拆分前端工作区模块
  - `candidate-list-panel.js`
  - `candidate-detail-panel.js`
  - `compare-panel.js`
  - `runtime-selection-panel.js`
  - `export-history-panel.js`
- 拆分状态域
  - 候选列表状态
  - 当前候选详情状态
  - 对比队列状态
  - 编排池状态
  - 草案状态
  - 提交状态
- 统一页面动作约定
  - 加载类动作
  - 提交类动作
  - 提示类动作
  - 刷新类动作
- 补齐前端错误显示层级
  - 列表错误
  - 详情错误
  - 草案错误
  - 提交错误

#### 配套验证

- 修改某一工作区时，不需要连带改大量无关渲染逻辑
- 页面刷新、切换批次、重新提交后状态不串
- 新增一个页面模块时，不需要继续增大主文件复杂度

#### 完成标准

- `actions.js` 与 `renderers.js` 不再承担全部工作区逻辑
- 前端具备可持续扩展的模块边界

### 7. P4：可观测性、诊断与运维辅助能力

这一步决定它是不是“正式后台”。不是看界面更花，而是看出错时能不能迅速定位。

#### 目标

- 让研发能够快速判断是批次数据问题、草案问题，还是正式提交问题
- 让策划在页面里能看到足够明确的状态反馈，而不是只有失败提示

#### 关键改动

- 服务端增加结构化日志
  - 启动日志
  - 批次加载日志
  - 草案生成日志
  - 正式提交日志
  - 异常日志
- 增加诊断接口
  - `GET /api/health`
  - `GET /api/diagnostics`
  - `GET /api/batches/:batchId/integrity`
- 增加批次完整性检查
  - 目录是否存在
  - `manifest.json` 是否完整
  - `runtime-levels` 是否可读
  - 候选详情索引是否缺失
- 前端增加诊断区或状态栏
  - 当前批次健康状态
  - 当前草案状态
  - 最近一次提交结果
  - 最近一次错误提示

#### 配套验证

- 当批次目录残缺时，工作台给出可读错误，而不是无提示失败
- 当正式目录写入失败时，日志与页面都能快速定位
- `analysis:check` 能扩展为更接近“工作台健康检查”

#### 完成标准

- 出现异常时，研发不需要先手动翻多个目录才知道问题在哪
- 策划能知道当前操作是否成功、失败后影响到哪里

### 8. P5：规模承载与长期维护优化

这是把“能用”推到“可持续扩展”的最后一段路。

#### 目标

- 为更大批次规模留出性能余量
- 为后续半年内继续加页、加字段、加批次留出维护空间

#### 关键改动

- 为列表查询引入更明确的读模型
  - 优先消费 `candidates.index.json`
  - 详情按需加载 `candidates/<id>.json`
- 为导出和提交增加缓存友好结构
  - 提交摘要
  - 运行时关卡索引摘要
- 评估是否引入 SQLite
  - 仅在 JSON 文件开始成为维护负担时再引入
  - 不提前为了“看起来正式”而上数据库
- 为 API 预留版本化空间
  - 例如 `/api/v1/...`
- 为后续后台功能预留目录和模块
  - 导出历史页
  - 规则快照页
  - 批次比较页

#### 配套验证

- 批次候选继续增大时，首屏和切换批次仍然可接受
- 新增一个只读工作区时，不需要改写核心数据层
- 后续从 JSON 迁到 SQLite 时，前端 API 形态无需整体推翻

#### 完成标准

- 工程的主要扩展成本来自新增业务本身，而不是修补旧结构

### 9. 推荐落地顺序

如果目标是尽快逼近“8.5 分正式服务后台”，后续推荐按以下顺序实施，而不是继续平均铺开：

1. 先完成 P1：正式目录提交链路加固
2. 再完成 P4 中最小可观测性能力
3. 再完成 P2：草案与提交历史模型
4. 再完成 P3：前端模块化拆分
5. 最后做 P5：规模承载优化

原因是：

- 先把“最危险的写链路”做稳
- 再把“出问题时能定位”补上
- 然后再谈“更好扩展”

### 10. 对应实现任务拆分建议

为了方便后续直接进入实现，当前建议把后续任务拆成以下几批：

#### 第一批：提交链路加固

- 为正式目录提交增加锁
- 为正式目录提交增加临时目录写入
- 为正式目录提交增加失败回滚
- 为每次提交输出 `commit-manifest.json`
- 为提交结果增加服务端冒烟测试

#### 第二批：导出历史与操作记录

- 增加导出历史列表接口
- 增加提交历史列表接口
- 增加工作台操作日志文件
- 前端增加“最近草案 / 最近提交”历史区

#### 第三批：前端模块化

- 拆候选浏览工作区
- 拆候选详情工作区
- 拆正式关卡编排工作区
- 拆草案预览与提交结果工作区

#### 第四批：诊断与健康检查

- 增加批次完整性检查接口
- 增加工作台诊断页
- 增加结构化日志输出
- 扩展 `analysis:check`

#### 第五批：规模优化

- 优先切到索引文件驱动列表
- 评估 SQLite 引入时机
- 预留 API 版本化

### 11. 迭代完成后的目标状态

当上述五个阶段全部完成后，工作台应达到以下状态：

- 本地可长期使用
- 正式目录提交可靠
- 失败恢复明确
- 批次、草案、提交都可追溯
- 前后端结构清晰
- 后续继续扩展“批次比较页”“导出历史页”“规则快照页”时不需要大返工

## 当前结论总结

当前项目已经明确以下方向：

- Web 分析台应继续演进为本地服务化工作台
- 工作台的正式定位是“牌局内容生产工作台”
- 工作台不承担离线评估计算核心职责
- 离线批次产物应保持只读
- 人工标记、筛选预设和导出草案应有独立可写层
- Godot 运行时继续只消费正式关卡目录
- 第一阶段 API 应围绕批次、候选、标记和导出组织
- 第一阶段前端重点是浏览、筛选、对比、编排，而不是实时重算
- 当前默认不需要优先引入 SSE 和复杂数据库

这份文档作为当前阶段“牌局分析台服务化”方向的主设计依据，后续应随着真实实现继续修订。
